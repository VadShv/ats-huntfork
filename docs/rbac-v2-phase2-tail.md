# RBAC v2 — Фаза 2: критичные баги + закрытие хвоста (усиление изоляции)

> Финальная фаза модуля доступов. Цель: (1) починить критичные баги scope,
> (2) унифицировать поведение ролей, (3) закрыть «хвост» (~130 эндпоинтов без
> member-scope) для полной изоляции в Модели B (1 группа = 1 org, юрлица внутри).
> Дополняет `docs/rbac-v2-master-plan.md`, `docs/rbac-v2-final-refinements.md`,
> `docs/rbac-v2-security-invariants.md`.
> Процесс: высокий риск (доступы/PII) → сверка КАЖДОЙ порции ДО прод-деплоя.

---

## Контекст (факты из кода)

- Всего API-эндпоинтов: **418**. Со scope v2: **17**. «Хвост» ≈ **130** эндпоинтов,
  работающих с данными кандидатов/вакансий/откликов, но без member-scope.
- Группы хвоста: `candidates/[id]/*` (22), `jobs/[id]/*` (36),
  `applications/[id]/*` (42) + прочее.
- **Legacy scope-резолвер** `resolveRecruiterScope` (знает только member/owner/
  admin) используется в: `jobs/index`, `dashboard/stats`, `interviews/index`,
  `analytics/recruiters*`, `utils/analytics/scope`. НЕ знает lead_recruiter/hrbp/
  external_recruiter → баги ниже.
- v2 scope-движок `getScopeJobIds` (знает ВСЕ роли: org/departments/jobs/assigned/
  hrbp) — целевой единый резолвер.

## Модель ролей (решение владельца — зафиксировано)

**ДЕФОЛТ scope для member И lead = `org`** (оба видят все вакансии/кандидаты —
«помогаем друг другу»). Ограничение — точечно через scope-override, когда нужно.
Тумблер «Мои/Все» — для удобного рабочего вида, НЕ граница доступа.

**Следствие:** для штатных (member/lead на `org`) хвост — низкий приоритет (они и
так видят всё легитимно). Хвост КРИТИЧЕН для строгих ролей: `external_recruiter`
(assigned), `hrbp` (company/dept) — их назначают точечно.

**Работа с вакансиями/кандидатами — ОДИНАКОВАЯ у ведущего и рекрутера** (единый
scope-механизм + тумблер). Разница ТОЛЬКО в продвинутых функциях:

| Функция | member (Рекрутер) | lead_recruiter (Ведущий) |
| --- | --- | --- |
| Вакансии/кандидаты/отклики (по scope) | ✅ | ✅ (та же логика) |
| Тумблер «Мои / Все» | ✅ | ✅ |
| Песочница воронки (pipeline sandbox) | ❌ | ✅ |
| Приглашение нанимающих менеджеров | ✅ (hiringManager:create) | ✅ |
| Суфлёр переписки (assistant/suggest) | ❌ | ✅ (по умолчанию ВЫКЛЮЧЕН) |
| Банк промптов (prompts) | ❌ | ✅ |
| Аналитика/скоринг view | по scope + тумблер | полнее |

> **Дефолт scope: member И lead = `org`** (оба видят всё). Работают через ЕДИНЫЙ
> scope-механизм и тумблер — расхождений (как сейчас: дашборд 2 / список 6) быть
> не должно.
> **Решено: Суфлёр — ТОЛЬКО ведущий (lead), по умолчанию ОТКЛЮЧЕН** (продвинутая
> функция; включается явно). member суфлёр не имеет.
> Разница ролей: lead = member + продвинутые функции (песочница воронки, промпты,
> суфлёр). Работа с данными идентична — две роли различаются ТОЛЬКО набором
> продвинутых инструментов.

## СПРИНТ A — 🔴 Критичные баги scope + единый резолвер [ПЕРВЫМ]

**Проблема (подтверждена):** ведущий рекрутер видит на дашборде 2 вакансии, в
списке — 6, тумблера «Мои/Все» нет. Причина: (1) `resolveRecruiterScope` не знает
lead → режет неправильно; (2) тумблер захардкожен на `orgRole === 'member'`;
(3) дашборд и список считают из разных источников с дефолтом «mine».

### A1. Единый scope-резолвер
- [ ] Мигрировать `resolveRecruiterScope` → на v2 `getScopeJobIds` (или переписать
      так, чтобы знал ВСЕ роли: member=assigned, lead=org, hrbp=company/dept,
      external=assigned, owner/admin=unrestricted). Единый источник scope для
      списков и дашборда.
- [ ] Потребители: `jobs/index`, `dashboard/stats`, `interviews/index`,
      `analytics/recruiters*`, `utils/analytics/scope` — перевести на единый резолвер.
- [ ] Согласовать `dashboard/stats` и `jobs/index`: одинаковый scope-источник →
      цифры на дашборде и в списке совпадают.

### A2. Тумблер «Мои / Все» для всех широких ролей
- [ ] Показывать тумблер всем, у кого scope шире `assigned` (member на org, lead на
      org, hrbp). Дефолт «Мои» (рабочий вид), «Все» = весь scope.
- [ ] «Мои» = вакансии, где пользователь лично `job_member`/организатор; «Все» =
      весь его scope (org / company / dept).
- [ ] **Дашборд:** тумблер в ШАПКЕ дашборда, рядом с заголовком «Дашборд»
      (решение владельца). Плюс единообразно: вакансии (`jobs/index`), интервью
      (`interviews/index`).
- [ ] member дефолт scope: `assigned` → **`org`** (видит всё, как lead). Точечное
      ограничение — через scope-override.

### A3. Унификация lead ↔ member на данных
- [ ] Убедиться: ведущий и рекрутер работают с вакансиями/кандидатами по ОДНОЙ
      логике (разница только в scope-значении и продвинутых функциях, не в
      механике). Никаких спец-веток «if member» в data-путях.

**Acceptance A:** ведущий (scope org) видит одинаковое число вакансий на дашборде
и в списке; тумблер «Мои/Все» присутствует; «Все» = вся орг, «Мои» = его личные.
Рекрутер (assigned) — та же механика, но scope уже.

Закрыть member-scope + masking на чувствительных эндпоинтах кандидата
(`candidates/[id]/*`, 22 шт). Приоритет — где PII/резюме.

- [ ] `hh-resume.get`, `hh-resume/raw.get` — scope + gate `candidate:read:contacts`
      (резюме содержит контакты).
- [ ] `resume-versions/*` (index, [versionId], promote, attach-document, risk) —
      scope.
- [ ] `ai-summary.get/.post` — scope.
- [ ] `fuzzy-duplicates.get`, `merge.post`, `merge-history.get` — scope
      (кроме дедуп-плашки: факт дубля виден, детали — нет, модель Хантфлоу).
- [ ] `risk-profile.post`, `documents/*` (upload/structure) — scope.
- [ ] `properties/[propId].put`, `fraud-flag.post` — scope.
- [ ] Каждый: out-of-scope → 404; PII по праву.

**Acceptance B:** внешний рекрутер/HRBP по прямому URL к чужому кандидату
(`/api/candidates/<чужой>/hh-resume`) → 404. Резюме/контакты чужого юрлица
недоступны.

## СПРИНТ C — 🟠 Хвост откликов и вакансий

### C1. applications/[id]/* (42)
- [ ] Детали, комментарии, скоркарты, интервью отклика, действия по этапам,
      hh-resync, telegram-* — scope через `isJobInScope`/pre-check. Out-of-scope → 404.

### C2. jobs/[id]/* (36)
- [ ] Вложенные конфиги вакансии (вопросы, критерии AI, форма отклика, воронка,
      трекинг-ссылки, members, assistant-settings) — scope (job вне scope → 404).
- [ ] Мутации — соответствующее право (`job:update` и т.п.) + scope.

### C3. Сорсинг (найдено при аудите — было упущено)
- [ ] `sourcing-candidates/*`, `sourcing-searches/*` — привязаны к вакансии →
      job-scope (вне scope → 404). Сорсинг-кандидаты чужих вакансий недоступны.

### C4. Аналитика по scope + тумблер (решение владельца)
Аналитика следует ЕДИНОМУ scope (тот же `getScopeJobIds(actor)`, что и данные):
- [ ] `analytics/*` (funnel/sources/jobs/overview/sla, 20 шт) — фильтровать по
      scope актора. Для member/lead (scope org) — вся организация; для HRBP —
      только его company/dept; external — только свои вакансии (или без права).
- [ ] **Тумблер «Мои / Вся компания»** в шапке аналитики:
      - **member/lead (org):** «Вся компания» = вся org; «Мои» = только вакансии/
        кандидаты, где работает лично. Это УДОБСТВО (оба в пределах их scope=org).
      - **HRBP:** «Все» = все его юрлица/подразделения (весь его scope);
        «Мои» = личные внутри его scope. «Вся org» НЕДОСТУПНА — это его
        SCOPE-ГРАНИЦА (безопасность): сервер не отдаёт агрегаты чужих юрлиц,
        что бы ни выбрал тумблер. Подписать срез («Аналитика · ООО X»).
      - **external:** без аналитики по умолчанию (нет права), либо только свои.
- [ ] Ключевое: тумблер НЕ расширяет доступ за scope — сервер всегда режет по
      `getScopeJobIds`. Для HRBP «Все» ≠ вся org.

**Acceptance C:** доступ к под-сущности отклика/вакансии/сорсинга вне scope → 404;
аналитика строгих ролей не раскрывает чужие юрлица.

## Порядок и приоритет

1. **Спринт A** (🔴 баги scope + единый резолвер) — ПЕРВЫМ, чинит ведущего/HRBP.
2. **Спринт B** (high-PII кандидата) — главная изоляция чувствительных данных.
3. **Спринт C** (хвост откликов/вакансий).
4. **Спринт D** (integration-гейты + добить остаток).
5. **Спринт E** (чистка ролей, UX, мелочи).
6. **Спринт F** (RLS) — опционально, v2.1.

Каждая порция: реализация → `npm run test` + typecheck → коммит → отчёт на
сверку → OK → push + деплой. Дробить крупные спринты (B/C/D) на порции по группам
эндпоинтов. Соблюдать security-invariants (A3/A4/D1). Миграции — аддитивны, бэкап.

## Карта покрытия эндпоинтов (418 всего)

**Закрывается scope в Фазе 2:**
- candidates/[id]/* (~22) → Спринт B
- applications/[id]/* (~42) → Спринт C1
- jobs/[id]/* (~36) → Спринт C2
- interviews (8) → A (index) + C ([id])
- documents (8) → B (привязаны к кандидату)
- sourcing-candidates/searches → C3
- hh/calendar/telegram управляющие (~11) → D1
- legacy: dashboard/stats, analytics/recruiters* → A

**Org-wide by design (scope НЕ нужен, гейт по праву):**
- access/* (18, member:update), ai-config/* (9), pipelines/* (10, воронки орга),
  prompts/* (8), comms/* (настройки), companies/departments (read для scope),
  геймификация, auth, webhook-и по секрету.

**Решено владельцем:**
- **Аналитика — по scope** (единый механизм) + тумблер «Мои / Вся компания» для
  member/lead (удобство, оба в org); HRBP — жёстко по его company/dept («Все» =
  его юрлица, не вся org); external — без аналитики. (C4)

**Решено владельцем (все вопросы закрыты):**
- **tracking-links / source-tracking** — по scope (job-scope), как остальные
  данные вакансии. Спринт D2.
- **Суфлёр** — только ведущий (lead), по умолчанию отключён. Спринт E
  (гейт продвинутых функций lead).
- member дефолт scope → `org` (видят всё). Спринт A2.

## Definition of Done (Фаза 2)
- Ведущий и рекрутер работают с данными по единой логике; цифры дашборд/список
  совпадают; тумблер «Мои/Все» у всех широких ролей.
- Все эндпоинты с данными кандидатов/вакансий/откликов — scoped (out-of-scope →
  404); либо в явном списке «org-wide by design».
- Чувствительные PII-эндпоинты закрыты по праву + scope; прямые URL к чужому
  юрлицу не отдают данные.
- Integration-мутации под правом орга; webhook-и по секрету не тронуты.
- Роли вычищены (нет дубля recruiter-синонима); матрица понятна (scope-подсказка).
- (v2.1) RLS — при необходимости.
