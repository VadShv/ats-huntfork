# ADR: Секции описания вакансии (обязанности/требования) — надстройка, не замена

> **Статус:** принято 19.08.2026, реализация — в бэклоге (предпосылка Фазы D публикации на hh).
> Связано: `docs/tz-hh-vacancy-publishing.md`, `docs/funnel-architecture.md` (тот же паттерн «канон + проекция»).

## Контекст

Обсуждалась идея разделить `job.description` на два поля: «Обязанности» и «Требования».
Аудит показал: описание вакансии читают 20+ мест — весь AI-контур (скрининг, авто-скоринг,
авто-отказ, генерация критериев и вопросов, сорсинговые запросы, ассистент), публичная
страница отклика, SEO (`JobPosting`), а hh-импорт (`vacancyParser.ts`) пишет описание
одним HTML-блобом.

## Решение

**Секции добавляем как опциональную надстройку; каноническое `description` остаётся
и автособирается.** Жёсткая замена поля отвергнута.

1. Новые **nullable**-поля в `job`: `responsibilities`, `requirements`
   (опционально позже — `conditions` «Условия»).
2. Если секции заполнены — каноническое `description` **автособирается** из них при
   сохранении (композер на сервере). Если нет — редактируется как раньше.
3. **Все существующие потребители не меняются**: скрининг (Qwen — заморожен), SEO,
   публичные страницы, ассистент читают каноническое `description`.
4. hh-импорт продолжает писать одним куском в `description`; секции остаются пустыми —
   это допустимо (резать hh-блоб эвристиками/AI не пытаемся).
5. hh-публикация: секции есть → собираем структурированный HTML
   (`<strong>Обязанности:</strong><ul>…</ul><strong>Требования:</strong>…`);
   секций нет → конвертация `description` (как в ТЗ публикации).

## Причины

- Замена = правка 20+ потребителей + миграция существующих описаний (резать руками/AI)
  + нерешаемая проблема hh-импорта. Дорого и рискованно.
- Надстройка = форма редактирования + композер + одна nullable-миграция. Ломаться нечему.
- Выгоды разделения сохраняются: «Требования» — готовые критерии для скрининга (Фаза 2+,
  отдельным решением, контур заморожен), структурированный HTML для hh, вход для
  генератора ДИ и аналитики качества вакансий.

## Правило (общий паттерн системы)

**Каноническое поле — источник истины; всё остальное — производные проекции.**
Так же, как: воронка → легаси-`status` (проекция), карточка вакансии → hh-пейлоад
(проекция), секции → `description` (композиция). Редактируем всегда канон/секции
в системе, проекции собираются автоматически — не наоборот.
