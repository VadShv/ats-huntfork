# ТЗ — Подэтап «На рассмотрении» в «Все неразобранные»: очередь нанимающего менеджера

Дата: 25.08.2026 · Статус: к реализации
Связанные документы: [funnel-architecture.md](./funnel-architecture.md) (канонический словарь воронки), [role-model-and-permissions.md](./role-model-and-permissions.md) (роль НМ), `tz-sprint-22-funnel-canonical.md` (подэтапы и ролл-ап)

---

## 1. Суть и мотивация

Сейчас нанимающий менеджер (НМ) в своём кабинете видит **всех** кандидатов на этапе типа `new`/`applied` — то есть весь корень «Все неразобранные» вместе с подэтапом «Подходящие». Рекрутер не управляет тем, что попадает к НМ: любой импорт с hh.ru сразу «светится» в кабинете НМ, включая явный мусор, который рекрутер ещё не отсеял.

**Целевой процесс:**

1. Рекрутер разбирает «Все неразобранные» и отправляет отобранных кандидатов на новый подэтап **«На рассмотрении»** (действие «На рассмотрение НМ»).
2. НМ видит в кабинете **только** кандидатов на подэтапе «На рассмотрении» — это его рабочая очередь.
3. Решение НМ:
   - **«Одобрено»** → кандидат переходит на подэтап **«Подходящие»** (уже существует в hh-пресете под «Все неразобранные»);
   - **«Отклонено»** → как сейчас, терминальный этап-причина `not_fit` («Не подходит»).

Итоговая структура корня «Все неразобранные» (системная hh-воронка):

```
Все неразобранные (корень, type=new)          ← сюда падает импорт с hh.ru (entry stage)
├── На рассмотрении (НОВЫЙ, type=new)         ← очередь НМ; ставит рекрутер
└── Подходящие (существует, type=new)          ← одобрено НМ; шорт-лист для дальнейшей работы
```

Семантика состояний не меняется: все три этапа — `type=new`, `bucket=working` → «Состояние» = «В работе», легаси-`status` = `new`.

## 2. Что уже есть (фиксация текущего состояния)

| Компонент | Текущее поведение |
| --- | --- |
| hh-пресет (`server/utils/pipeline-seed.ts`, `HH_STANDARD_STAGES`) | Корень `unsorted` («Все неразобранные», order 0) и подэтап `suitable` («Подходящие», order 1, `parentKey: 'unsorted'`). Подэтапа «На рассмотрении» нет |
| Кабинет НМ (`server/api/hm/dashboard.get.ts`) | Выборка по `inArray(pipelineStage.type, ['new','applied'])` — весь корень + «Подходящие» |
| Решения НМ (`server/api/hm/decisions/index.post.ts`) | Guard: решение допустимо, только если отклик на этапе `type in (new, applied)`. First-decision-wins, отмена 24 ч |
| Резолвер целей (`server/utils/hm-stage-resolver.ts`) | «Одобрено» → следующий **корневой** working-этап по displayOrder (для hh-воронки это «Подумать», не «Подходящие»!); «Отклонено» → `not_fit`-подэтап |
| Отмена решения (`hm/decisions/[id]/cancel.post.ts`) | Этап назад **не** двигает — рекрутер возвращает вручную (осознанно, прозрачно в аудите) |
| Канбан вакансии (`app/pages/dashboard/jobs/[id]/index.vue`) | Колонки — корни; выбор подэтапа показывает только его (Спринт 12.3); дети группируются по `parentStageId` |
| Перемещения | Только через `moveApplicationStage()` — guard, activity, синк легаси-статуса |
| Идентификация этапов | Только по `type`/имени. Machine-readable ключа пресета в БД нет |

Известное ограничение v1 роли НМ сохраняется: НМ работает в отдельном кабинете `/hm/*` через `/api/hm/*`-эндпоинты, read-only к общим страницам.

## 3. Модель данных

### 3.1. Новая колонка `pipeline_stage.preset_key` (П1)

Проблема: серверу нужно надёжно находить «На рассмотрении» и «Подходящие» в воронке организации. Поиск по имени хрупок (переименования, локали), по `type` — неоднозначен (все три этапа `new`).

Решение — **machine-readable ключ пресета**:

```sql
ALTER TABLE pipeline_stage ADD COLUMN preset_key text;
CREATE UNIQUE INDEX ux_pipeline_stage_preset_key
  ON pipeline_stage (pipeline_id, preset_key) WHERE preset_key IS NOT NULL;
```

- Заполняется **только** сидером/миграцией из `StageSeed.key` (`unsorted`, `suitable`, `hm_review`, `notfit`…). Пользовательские этапы — `NULL`.
- В конструкторе воронки не редактируется и не показывается.
- Бэкфилл существующих строк: матчинг по (`pipeline.isSystem` через `name` пресета, `stage.name` + `parentStageId`-структура) в рамках системных воронок. Не сматчившиеся строки остаются `NULL` — это допустимо (сработают фолбэки, §5).
- Дальше ключ пригодится всем будущим фичам, завязанным на семантику конкретного этапа (например, `docs/idea-hh-stage-distribution-import.md`).

### 3.2. Новый подэтап в hh-пресете (П1)

В `HH_STANDARD_STAGES` после корня `unsorted`:

```ts
{ key: 'hm_review', name: 'На рассмотрении', type: 'new', color: STAGE_COLORS.new,
  displayOrder: 1, bucket: 'working', isTerminal: false, isSystemStage: true, parentKey: 'unsorted' },
// 'suitable' и все последующие displayOrder сдвигаются на +1
```

- `isSystemStage: true` — нельзя удалить/переименовать/сменить тип; можно скрыть (`isHidden`) — поведение при скрытии см. §5.4.
- Цвет — оттенок корневого `new`-цвета (различимость в чипах; точный тон на усмотрение реализации, из палитры `STAGE_COLORS`).

### 3.3. Миграция данных для существующих организаций (П1)

Миграция `00XX_hm_review_substage.sql` (runtime-мигратор, идемпотентная):

1. Добавить колонку и индекс из §3.1.
2. Бэкфилл `preset_key` в системных воронках (по матчингу имён пресетов «Простой» / «Стандартный hh.ru»).
3. Для каждой воронки, где есть этап `preset_key='unsorted'` и **нет** `preset_key='hm_review'`: вставить подэтап «На рассмотрении» (`parentStageId` = id корня, `displayOrder` = order корня + 1, остальные этапы воронки с `displayOrder > order корня` сдвинуть на +1). Вставка в системную воронку миграцией легальна: запрет на редактирование действует для пользователей, не для системных сидов.
4. Кандидатов **не перемещать**: все, кто был в корне «Все неразобранные», там и остаются. Очередь НМ начинается пустой — рекрутеры наполняют её действием (§6).

Клонированные и кастомные воронки миграция не трогает (у них нет `preset_key`) — для них работают фолбэки (§5).

## 4. Серверная логика

### 4.1. Резолвер целей НМ (`server/utils/hm-stage-resolver.ts`) (П2)

`resolveApprovedTargetStage()` — новый приоритет:

1. **Основной путь:** найти в воронке вакансии подэтап `preset_key='suitable'` с тем же `parentStageId`, что у корня текущего этапа отклика (не скрытый, не архивный) → цель «Одобрено».
2. **Фолбэк 1:** любой не скрытый подэтап `type='new'` того же корня, чей `displayOrder` больше, чем у «На рассмотрении» (кастомные воронки, где админ сделал свои подэтапы без ключей).
3. **Фолбэк 2 (текущее поведение):** следующий корневой working-этап по displayOrder.

`resolveRejectedTargetStage()` — **без изменений**.

Новая функция `resolveHmReviewStage(pipelineId)` → `{ stageId, stageName } | null`: подэтап `preset_key='hm_review'`, не скрытый, не архивный. Единая точка — используется дашбордом, guard'ом решений и действием рекрутера.

### 4.2. Кабинет НМ (`server/api/hm/dashboard.get.ts`, `hm/applications/[id].get.ts`) (П2)

Для каждой вакансии НМ:

- если `resolveHmReviewStage()` вернул этап — выборка откликов **только** по `currentStageId = hm_review.stageId`;
- если вернул `null` (кастомная воронка без подэтапа, или он скрыт) — **легаси-режим**: текущее поведение (`type in (new, applied)`), чтобы не сломать работающие инсталляции.

В ответе дашборда добавить `reviewMode: 'queue' | 'legacy'` на вакансию — UI кабинета НМ показывает подзаголовок «Очередь на рассмотрении» либо прежний «Неразобранные».

### 4.3. Guard решений НМ (`server/api/hm/decisions/index.post.ts`) (П2)

- `reviewMode='queue'`: решение допустимо **только** если `app.currentStageId === hm_review.stageId`. Отклик в корне или на «Подходящие» → 409 с понятным сообщением («Кандидат не находится на рассмотрении»).
- `reviewMode='legacy'`: прежний guard (`type in (new, applied)`).
- Repair-ветка (повтор решения после сбоя между insert и move) использует новый резолвер — досдвигает на «Подходящие», а не на следующий корневой этап.
- First-decision-wins, отмена 24 ч, compensating delete — **не меняются**.
- Отмена решения по-прежнему **не двигает** этап назад; в UI отмены добавить подсказку: «Верните кандидата на „На рассмотрении", если требуется повторное решение».

### 4.4. Действие рекрутера «На рассмотрение НМ» (П3)

Специального эндпоинта **не требуется**: перемещение выполняется существующим `PATCH /api/applications/:id/stage` → `moveApplicationStage()`. Изменения только в UI (§6) + один guard:

- В `moveApplicationStage()` дополнительных запретов не вводим: перемещение на «На рассмотрении» и обратно подчиняется общим правилам working-переходов. Ручной перенос сразу в «Подходящие» остаётся возможным (рекрутер может одобрить в обход НМ — это сознательное решение, соответствует ролевой модели: рекрутер главный в воронке).

### 4.5. Что НЕ трогаем (инварианты)

| Инвариант | Почему выполняется |
| --- | --- |
| Импорт с hh.ru | Entry stage = корень «Все неразобранные» (`getEntryStageForPipeline()`), подэтапы на entry не влияют. Ни одна строка импорта не меняется |
| Легаси `application.status` | Подэтапы наследуют `type=new` → `stageTypeToLegacyStatus()` даёт `new`. Sidekick `check`, dedup, hh-sync видят прежние значения |
| Скрининговый контур (Qwen/YC) | Не затрагивается вообще |
| Аналитика и ролл-ап | `getOrgStageRollup()` схлопывает подэтапы в корень — счётчики «Все неразобранные» в jobs API, source-tracking и аналитике не меняются |
| Единственный путь перемещений | Все переходы (действие рекрутера, решения НМ) — через `moveApplicationStage()` |
| Системные этапы | Ничего не удаляем и не переименовываем; только добавляем подэтап (разрешено по словарю воронки, §2.2) |

## 5. Поведение в краевых случаях

1. **Воронка без «На рассмотрении»** (кастомная/клон) → `reviewMode='legacy'`, всё как сегодня. Админ может добавить подэтап руками в конструкторе; без `preset_key` он не станет очередью НМ — в конструкторе воронки для подэтапов корня `new` появляется бейдж-подсказка «Очередь НМ доступна только в системной воронке» (v1; назначение роли произвольному этапу — в бэклог).
2. **Подэтап «На рассмотрении» скрыт** (`isHidden=true`) → `resolveHmReviewStage()` возвращает `null` → легаси-режим. Кандидаты, оставшиеся на скрытом этапе, видны в общих списках (стандартное поведение скрытых этапов), но в очередь НМ не попадают — при скрытии этапа с кандидатами конструктор показывает предупреждение с count.
3. **«Подходящие» скрыт** → «Одобрено» идёт по фолбэкам §4.1 (подэтап `new` того же корня → следующий корневой этап).
4. **Кандидат ушёл с «На рассмотрении» до решения НМ** (рекрутер передвинул) → guard §4.3 вернёт 409; карточка исчезает из очереди НМ при следующем обновлении. Гонка «двое решают одновременно» уже закрыта `ux_hm_decisions_effective_per_app`.
5. **Несколько вакансий, одна воронка** — очередь НМ фильтруется по `jobId` через `job_member`, как сейчас; подэтап общий, конфликтов нет.
6. **Повторная отправка после отмены решения** — рекрутер возвращает кандидата на «На рассмотрении» обычным перемещением; слот решения свободен (отмена сняла `is_effective`), НМ решает заново.

## 6. UI

### 6.1. Кабинет рекрутера (П3)

- **Быстрое действие «На рассмотрение НМ»** в `ApplicationQuickActions.vue`:
  - показывается, когда отклик на корне «Все неразобранные» (или его подэтапах, кроме самого «На рассмотрении»), воронка имеет `hm_review` и **у вакансии назначен хотя бы один НМ** (`job_member` c `member_role='hiring_manager'`);
  - без назначенного НМ — действие скрыто (не disabled), чтобы не захламлять меню;
  - выполняет обычный move на подэтап; тост «Отправлено на рассмотрение НМ».
- **StagePicker / канбан** — работают из коробки: подэтап приходит из `/api/pipelines/:id` и `stages-summary`, канбан уже умеет показывать подэтапы выбранного корня. Отдельных правок нет, только проверка в QA.
- **Счётчик** на странице вакансии: в шапке колонки «Все неразобранные» бейдж «На рассмотрении: N» (данные уже есть в выборке канбана; если нет — из stages-summary + counts).
- Строка отклика: чип этапа показывает «На рассмотрении» с его цветом (стандартный механизм, правок нет).

### 6.2. Кабинет НМ (П3)

- Дашборд: заголовок списка — «На рассмотрении» + count; в `reviewMode='legacy'` — прежний вид. Пустое состояние: «Рекрутер ещё не отправил кандидатов на рассмотрение».
- Карточка кандидата: без изменений (решения «Одобрить»/«Отклонить» уже есть). После «Одобрить» тост: «Кандидат перемещён в „Подходящие"».
- Плашка результата решения показывает целевой этап из ответа API (`targetStage`) — уже реализовано, проверить текст.

### 6.3. Конструктор воронки (П3)

- Новый подэтап отображается как системный (замок, нельзя удалить/переименовать), доступно скрытие.
- Подсказка у подэтапа «На рассмотрении»: «Очередь нанимающего менеджера. Кандидаты, отправленные на рассмотрение, видны НМ в его кабинете».

### 6.4. Уведомления (П4, отдельный пакет)

- НМ: существующий механизм notices дашборда — «N новых кандидатов на рассмотрении» (count по своим вакансиям). Push/email — вне рамок этого ТЗ.
- Рекрутеру: активити-записи о решении НМ уже пишутся `moveApplicationStage()` + hm_decision; отдельного канала не добавляем.

## 8. Приёмочные сценарии

**Основной путь:**

1. Импорт кандидата с hh.ru → отклик на корне «Все неразобранные», `status='new'` — импорт не изменился.
2. Рекрутер: действие «На рассмотрение НМ» → отклик на подэтапе «На рассмотрении», activity-запись о переходе, состояние «В работе», `status='new'`.
3. НМ открывает кабинет → видит кандидата в очереди (и только его: кандидаты в корне и «Подходящих» не видны).
4. НМ «Одобрить» → отклик на «Подходящие», hm_decision записано, тост с целевым этапом; в кабинете НМ кандидат исчез из очереди.
5. НМ «Отклонить» → отклик на «Не подходит» (терминал), состояние «Отказ», `status='rejected'`.

**Краевые:**

6. Решение НМ по кандидату, которого рекрутер уже унёс с «На рассмотрении» → 409, очередь обновляется.
7. Отмена решения (в окне 24 ч) → этап не двигается, слот свободен; повторная отправка на рассмотрение → новое решение проходит.
8. Кастомная воронка без `hm_review` → кабинет НМ в легаси-режиме (все `new`), «Одобрено» → следующий корневой этап (как сегодня).
9. Скрытие «На рассмотрении» в конструкторе → предупреждение с count; кабинет НМ переключается в легаси-режим.
10. Канбан: выбор корня «Все неразобранные» показывает сумму (корень + оба подэтапа), выбор подэтапа — только его; счётчики jobs API не изменились.
11. Миграция идемпотентна: повторный прогон не создаёт дублей (проверка по `ux_pipeline_stage_preset_key`).
12. Sidekick `extension/check` и дедупликация видят прежний `status` — регрессий нет.

**Телеметрия приёмки:** activity-события переходов + `hm_decision.decidedAt` позволяют построить метрику «время от отправки на рассмотрение до решения НМ» (в аналитические дашборды — бэклог).

## 9. Риски

- **Бэкфилл `preset_key` по именам** — единственное хрупкое место миграции: организации могли скрыть этапы (скрытые матчим тоже) — при не-матче фича деградирует в легаси-режим, ничего не ломается. На копии прод-БД прогнать миграцию до релиза.
- **Сдвиг `displayOrder`** затрагивает выборки «следующего этапа» — покрыть тестом резолвера на hh-воронке после миграции.
- **НМ, привыкшие видеть всех `new`** — смена содержимого кабинета; смягчается `reviewMode`-подзаголовком и пустым состоянием с объяснением.
- **Двойная семантика «Подходящих»** (руками рекрутера и решением НМ) — осознанно: источник различим в activity/hm_decision.

## 10. Чего осознанно не делаем (v1)

- Не назначаем роль «очередь НМ» произвольным этапам кастомных воронок (только системный `preset_key`) — бэклог.
- Не двигаем кандидатов автоматически при отмене решения НМ.
