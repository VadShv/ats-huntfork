## 3. 🔴 СРОЧНЫЙ БАГ: ловушка view-as для роли НМ

**Симптом:** owner нажал «Посмотреть как» на пользователе с ролью `hiring_manager`
→ перекинуло в кабинет НМ (`/hm/dashboard`) → **выйти нельзя**, даже перелогин не
помогает (cookie `access_view_as` живёт 30 мин и переживает сессию).

**Причина:** `getActorContext` в режиме view-as возвращает роль НМ →
`require-approved-member.global.ts:57` насильно редиректит НМ из `/dashboard/*` в
`/hm/dashboard`. А кнопка выхода из view-as живёт в /dashboard-layout, куда НМ не
пускают → замкнутый круг. `deleteCookie` (stop) не вызвать.

**Фикс (комбинированный):**
1. **Middleware не должен применять HM-редирект в режиме view-as.** Если
   `isViewAs === true` — НЕ редиректить в `/hm/`, показывать `/dashboard` глазами
   НМ (со scope НМ), с баннером view-as и кнопкой выхода. Смысл view-as —
   «увидеть, что видит НМ», а не «запереть смотрящего».
2. **ViewAsBanner + кнопка выхода доступны на ВСЕХ layout** (включая /hm/*), как
   fail-safe.
3. **stop-эндпоинт fail-safe** (уже есть — любой залогиненный чистит свою cookie).
**Acceptance:** owner → view-as НМ → видит /dashboard как НМ → кнопка «Выход»
работает → вернулся под себя. Перелогин тоже сбрасывает (доп. проверка).

## 1. HRBP: назначение через карточку компании/департамента (авто-scope)

**Модель (решение владельца):** HRBP назначается НЕ в модалке прав, а в карточке
**компании** или **департамента** (при создании/редактировании — поле «HRBP:
[пользователь]»). Scope HRBP выводится автоматически из этих привязок.

**Структура Astra Group:**
- Головная компания → деление по департаментам → HRBP на департамент(ы).
- Отдельные юрлица (company) → HRBP на компанию целиком.
- Один HRBP может отвечать за НЕСКОЛЬКО компаний/департаментов → связь
  многие-ко-многим (не одно поле).

**Реализация:**
- Роль-пресет `hrbp` — **ФИКСИРОВАННЫЙ пресет** (права заданы в коде, как у
  рекрутера/lead; НЕ настраивается через матрицу). Единственная переменная часть —
  **назначение компаний/департаментов** (в карточке оргструктуры). То есть все
  HRBP имеют одинаковый набор прав, отличаются только срезом данных (scope).
- Привязка: `company.hrbp_user_ids[]` / `department.hrbp_user_ids[]` (или таблица
  связи `org_scope_assignment`). НЕТ сейчас в схеме — добавить.
- `getScopeJobIds` для HRBP: вакансии, где `job.companyId ∈ (компании, где юзер
  HRBP)` ИЛИ `job.departmentId ∈ поддерево(департаменты, где юзер HRBP)`.
  → нужен **смешанный scope** (компании + департаменты одновременно).
- Новый scope-тип `company` (фильтр по `job.companyId`; колонка+индекс уже есть) +
  расширение `member_scope` полем `company_ids[]`, ЛИБО scope выводится из
  привязок в оргструктуре (предпочтительно — меньше дублирования состояния).
- UI: в карточке company/department — селектор HRBP (multi-user). Назначение →
  bump `permissions_version` затронутых.

**Acceptance:** назначил Иванова HRBP юрлица X и департамента Y головной → Иванов
видит вакансии/кандидатов X и Y, остальное — как дубль-плашки без перехода.

## 4. Фильтр «Только мои / Все в scope» на списках-событиях

Дефолт «Мои» (чистота), тумблер «Все в моём scope».
- **Вкладка «Интервью»** (`interviews/index`): дефолт — интервью, где юзер
  организатор/интервьюер; тумблер «Все (в моём scope)».
- **Дашборд вакансий** (`dashboard` / `jobs/index`): дефолт — «мои вакансии»
  (assigned/created); тумблер «Весь org».
- **Ключевые события/таймлайн** — аналогично, где применимо.
- **ВАЖНО:** фильтр списка = чистота UI; доступ к КАРТОЧКАМ остаётся по scope
  (переход в интервью из карточки отклика работает → подмена заболевшего коллеги).
  Фильтр НЕ ограничивает доступ, только дефолтный вид списка.

## 5. Ассистент: персональная история чатов + гейт по ИИ-праву

- **История диалогов** с ИИ-ассистентом — по владельцу (`userId`), не org-wide.
  Каждый видит только свои прошлые запросы. Проверить хранение чат-сессий
  (per-user привязка); фильтр по создателю.
- **Гейт доступа к ассистенту (связано с §8):** сейчас `conversations/suggest`,
  chatbot-эндпоинты гейтятся `requireAuth` (любой залогиненный). Заменить на
  проверку ИИ-права (напр. `scoring` или будущий `aiConfig`/`assistant`), чтобы
  роли без ИИ (внешний рекрутер) НЕ имели доступа к ассистенту. Это закрывает
  дыру «requireAuth-only» и выполняет требование «внешний без ИИ».
- Данные, которые ассистент ПОКАЗЫВАЕТ, уже ограничены member-scope (Спринт 3 #1).

## 7. Старая вкладка «Участники» (members.vue): видимость по ролям

- **Список рекрутеров** (member/lead/junior/recruiter) — видят только **owner/admin**.
- **Список НМ** (hiring_manager) — видят и рекрутеры; рекрутеры могут **добавлять
  НМ**.
- **Нюанс безопасности:** создание НМ сейчас требует `member:['create']`
  (owner/admin only). Чтобы рекрутер мог добавлять ТОЛЬКО НМ (не рекрутеров/
  админов) — ввести отдельное право `hiringManager:['create']` и выдать его
  member/lead. НЕ давать рекрутеру полный `member:create`.
- members.vue уже разделяет списки (recruiters vs hiring_manager) — добавить гейт
  видимости первого списка + переключить invite-HM на новое право.

## 8. Роль «Внешний рекрутер» (замена «Младшего рекрутера»)

**Решение владельца:** роль `junior_recruiter` (Младший рекрутер) **ПЕРЕИМЕНОВАТЬ**
в `external_recruiter` (Внешний рекрутер) с **минимальным** набором прав — под
агентства/внешних подрядчиков.

- Ключ пресета: `junior_recruiter` → **`external_recruiter`**.
  nameRu: «Внешний рекрутер», nameEn: «External Recruiter».
- scope `assigned` (только свои вакансии). Видит только своих кандидатов; чужие —
  как дубль-плашка без перехода (модель Хантфлоу, проверено владельцем — работает).
- **Минимальные права** (решение владельца):
  - `candidate: ['create', 'read']`, `application: ['create', 'read', 'update']`
    (двигать по этапам своих вакансий), `job: ['read']`, `document: ['read']`,
    `comment: ['create', 'read']`, `organization: ['read']`,
    `company/department: ['read']`.
  - **`interview: ['create', 'read', 'update']`** — внешний ДОЛЖЕН создавать
    интервью (по своим вакансиям).
  - **БЕЗ ЛЮБЫХ ИИ-функций** (решение владельца): НЕ давать `scoring` (скринер),
    НЕ давать доступ к ассистенту/чат-боту, авто-анализу, генерации, AI-конфигу.
    Полное отсутствие ИИ. Если для конкретного внешнего рекрутера понадобится
    скоринг — владелец выдаст точечно через override, вручную.
  - **БЕЗ PII** по умолчанию (нет `candidate:read:contacts`/`:salary`) — контакты
    скрыты, выдаются точечно через override.
  - Также без `activityLog` (журнал) — внешнему не нужен.

  **Важно про ассистента:** сейчас чат-бот/`conversations/suggest` гейтятся
  `requireAuth` (любой залогиненный). Чтобы внешний НЕ имел доступа к ИИ-ассистенту,
  ассистент-эндпоинты должны проверять наличие ИИ-права (напр. `scoring` или
  будущий `aiConfig`/`assistant`), а не просто `requireAuth`. Внешний без ИИ-права
  → ассистент недоступен (баннер «нет прав», §6). Это закрывает и дыру
  «requireAuth-only на ассистенте».
- **Миграция:** обновить упоминания `junior_recruiter` в коде
  (`comments/visibility.ts` — тип Role и правило видимости внутренних
  комментариев: внешний НЕ видит внутренние; `rbac.ts` комментарий-список;
  `role.post.ts` комментарий). Существующим членам с ролью junior (если есть) —
  перевести на external_recruiter в backfill/сиде идемпотентно.
- **Дубли:** внешний видит факт дубля + карточку отклика с плашками, БЕЗ перехода
  в чужую вакансию (уже работает по модели §... Спринта 3, проверено).

## 9. Модалка прав: бейдж «по роли ✓/✗» (UX)

- Пустая ячейка override = «по роли» — это ПРАВИЛЬНО (override — исключение, не
  полный список). НЕ заполнять ячейки значениями роли.
- Рядом с селектором «по роли/разрешить/запретить» показывать ЭФФЕКТ роли:
  «по роли: ✓ разрешено» / «по роли: ✗ нет» — чтобы админ видел базу и где стоит
  исключение.

- **HRBP — фиксированный пресет** (права в коде). Переменная часть — только
  назначение компаний/департаментов в оргструктуре. Матрица (Спринт 7) для HRBP
  НЕ требуется → §1 делается сейчас целиком.

  `junior_recruiter` → `external_recruiter`, минимальные права, без PII по умолчанию.
- Порядок: сначала весь этот документ (порциями), ПОТОМ Спринт 7, потом Спринт 6.
