## Блок A — Контекстные быстрые действия (ApplicationQuickActions)

### A0. Текущее состояние

`app/components/ApplicationQuickActions.vue` показывает статичный набор для любой этапной воронки: **Пригласить** (→ первый root-этап `contact`, hotkey 1), **Подумать** (`on_hold`, 2), **Отказать** (подэтап `not_fit`, 3), **Ещё ▾** (4), плюс отдельная кнопка **Запланировать интервью** (5). Набор не зависит от текущего этапа кандидата — «Пригласить» видна даже на оффере, а логичных действий «вперёд по воронке» после теста нет.

### A1. Целевая матрица наборов

Набор быстрых кнопок вычисляется от **типа текущего root-этапа** отклика (`currentQuickStage`: для подэтапа берём тип родителя; для подэтапов «Отказа» — ветку `rejected`). Порядок кнопок — строго как в таблице; **«Ещё ▾» всегда последняя** (инвариант).

| Текущий этап (type) | Кнопки (в порядке слева направо) |
|---|---|
| Нет этапа / `unsorted` / `on_hold` / `contact` (и их подэтапы) / custom-working | Пригласить · Подумать · Отказать · **Ещё ▾** (как сейчас) |
| `assessment` («Тестовое задание») | Подумать · Отказать · **Интервью** · **Ещё ▾** |
| `interview` («Интервью») | **Предложение о работе** · Подумать · Отказать · **Ещё ▾** |
| `offer` («Предложение о работе») | **Выход на работу** · **Кандидат отказался** · **Ещё ▾** |
| `hired` («Выход на работу») | **Кандидат отказался** · **Ещё ▾** |
| bucket `rejected` (любой отказной) | только **Ещё ▾** (решение O1); возврат в работу — через меню с guard G1 (комментарий) как сейчас |

Правила:

1. **«Пригласить» исчезает начиная с этапа «Тестовое задание»** и на всех этапах правее (`assessment`, `interview`, `offer`, `hired`).
2. **«Ещё ▾» всегда последняя по расположению** в любом наборе — закрепить как инвариант компонента (не рендерить кнопки после неё).
3. Новые кнопки — это переводы на этапы через существующий `quickMoveToStage` → `moveApplicationStage` (никакой новой серверной логики):
   - **Интервью** → первый root-этап `interview`; сохранить текущее поведение `emit('schedule')` (открытие календаря планирования) после перевода;
   - **Предложение о работе** → первый root-этап `offer`;
   - **Выход на работу** → первый root-этап `hired`; срабатывает существующий guard G2 «подтверждение найма»;
   - **Кандидат отказался** → подэтап `withdrawn` родителя «Отказ» (поиск как у `rejectStage`: сначала подэтап, потом корневой legacy). Терминальный перевод, hh-push в discard по существующей цепочке шаблонов (вакансия → этап → дефолт).
4. Если в воронке нет этапа нужного типа (например, кастомная воронка без `offer`) — кнопка просто не показывается, деградация без ошибок.
5. Кнопка уже-текущего этапа не показывается (а не disabled): например, на `on_hold` нет кнопки «Подумать».
6. **Горячие клавиши** 1…N переназначаются динамически по фактическому порядку видимых кнопок; «Ещё ▾» — всегда следующая цифра после последней кнопки-действия; «Запланировать интервью» — последняя. Подсказки `<kbd>` обновляются автоматически.
7. Стили: первая кнопка набора — акцентная (как нынешняя синяя «Пригласить»), «Кандидат отказался» — красная схема как у «Отказать», остальные — нейтральные. Иконки: Интервью — `CalendarClock`, Предложение о работе — `FileCheck`/`Handshake`, Выход на работу — `PartyPopper`/`BadgeCheck`, Кандидат отказался — `UserX`.

### A2. Реализация

Ввести в компоненте вычисляемый «дескриптор набора»: `quickActionSet = computed<QuickAction[]>` — массив `{ key, label, icon, targetStage, tone }`, строящийся от `currentQuickStage` по матрице A1; шаблон рендерит массив циклом (вместо четырёх захардкоженных кнопок), «Ещё ▾» — вне массива, всегда после. Логика guard-диалогов (G1/G2/G3), обработка ошибок и `emit('stage-changed')` не меняются.

### A3. Критерии приёмки (блок A)

- На отклике этапа «Тестовое задание» видны ровно: Подумать, Отказать, Интервью, Ещё ▾ — в этом порядке; «Пригласить» нет.
- На «Интервью»: Предложение о работе, Подумать, Отказать, Ещё ▾; клик по «Предложение о работе» переводит на оффер (история + активность + PostHog как при любом переводе).
- На «Предложение о работе»: Выход на работу (с G2-подтверждением), Кандидат отказался, Ещё ▾.
- На «Выход на работу»: Кандидат отказался, Ещё ▾.
- «Кандидат отказался» с hh-вакансии уводит кандидата на hh в discard с корректным шаблоном сообщения.
- Горячие клавиши соответствуют видимому порядку; в списке откликов и в карточке отклика поведение идентично.

## Блок C (Часть B) — Аналитика уровня Хантфлоу: раздел /dashboard/analytics

### C0. Принципы

- **Не убить прод**: все тяжёлые агрегации — из материализованного представления, обновляемого раз в 15 минут; интерактивные запросы — только по индексам. Импорт hh и скрининг (Qwen) не затрагиваются вообще.
- Единица анализа — **отклик × этап** (вход/выход/длительность), первоисточник — `application_stage_history` (уже пишется единым `moveApplicationStage` для всех путей, включая систему и авто-отказ — данные консистентны с Спринта 22).
- Все страницы наследуют общий набор фильтров: период (с пресетами: 7д/30д/квартал/год/кастом), вакансия, воронка, рекрутер, источник; сравнение с предыдущим периодом.

### C1. Модель данных

**М1. Время на этапе и SLA** (решение O3: главное — видеть, сколько в среднем кандидаты находятся на каждом этапе)

- **Базовая метрика — фактическое время на этапе** (среднее + медиана + p90), считается из mv без каких-либо настроек — показывается везде: в воронке, в Обзоре, в Скорости, в разрезе вакансий.
- **SLA — опциональный порог поверх факта**, миграция `0066_stage_sla.sql`:

```sql
ALTER TABLE pipeline_stage ADD COLUMN IF NOT EXISTS sla_days integer;        -- норма, дней (null = не задана)
ALTER TABLE pipeline_stage ADD COLUMN IF NOT EXISTS sla_alert_days integer;  -- порог тревоги, дней
```

- Редактирование — в настройках воронки (`settings/pipelines/[id].vue`), поле у root-этапов working-ветки; для системных этапов разрешено (это настройка, не структура — по аналогии с `rejectMessageTemplate` PATCH-исключением). Дефолтов в сиде нет — поля пустые, пока пользователь не задаст.
- **«Замедления сейчас»** работают и без настроенного SLA: если `sla_days` задан — порог = SLA; если нет — порог = p90 фактической длительности этого этапа за последние 90 дней («дольше, чем 90% остальных»). В UI видно, какой порог сработал.

**М2. Материализованное представление** — миграция `0067_mv_stage_durations.sql`:

`mv_application_stage_durations`: по одной строке на посещение этапа откликом —
`organization_id, application_id, candidate_id, job_id, pipeline_id, stage_id, root_stage_id (подэтап схлопывается в родителя), stage_type, bucket, entered_at, exited_at (null = сейчас на этапе), duration_hours, moved_by (user id | null=система), via, source (hh/manual/…), to_stage_id (куда ушёл — для матрицы переходов), is_terminal_exit`.

- Строится из `application_stage_history` + `application` + `pipeline_stage` (LEAD() OVER по отклику для exited_at/to_stage_id).
- `UNIQUE INDEX` по `(application_id, stage_id, entered_at)` — обязателен для `REFRESH MATERIALIZED VIEW CONCURRENTLY`.
- Обновление: Nitro scheduled task (серверный плагин с интервалом 15 мин, `REFRESH ... CONCURRENTLY`), лог длительности рефреша; первый рефреш — при старте приложения. Без pg_cron — ничего не ставим на ВМ.
- Дополнительные обычные индексы: `(organization_id, entered_at)`, `(job_id)`, `(root_stage_id)`.

**М3. Подписки на отчёты — ИСКЛЮЧЕНЫ ИЗ ОБЪЁМА** (решение O2: без доставки, только дашборд). Миграция 0068 не делается. Экспорт CSV/XLSX по кнопке остаётся.

### C2. API

Все под `/api/analytics/*`, все читают только mv (кроме `now`-виджетов, читающих текущие этапы напрямую с лимитами), все принимают общие фильтры `?from&to&jobId&pipelineId&recruiterId&source&compare=prev`:

| Endpoint | Отдаёт |
|---|---|
| `GET /api/analytics/overview` | KPI: активные отклики, новые за период, наймы, отказы, Time-to-Hire p50/p90, Offer Acceptance, дельты к прошлому периоду |
| `GET /api/analytics/funnel` | По root-этапам активной воронки: вошло, сейчас, ушло дальше, конверсия в следующий этап, конверсия от входа, медиана/среднее время на этапе; + матрица переходов from→to |
| `GET /api/analytics/funnel/dropoff?stageId=` | Drill-down: список отсеянных на этапе (кандидат, вакансия, причина отказа, кто, когда) с пагинацией |
| `GET /api/analytics/speed` | Time-to-Hire/Time-to-Reject p50/p90 по периодам (тренд), длительности по этапам, топ «медленных» вакансий |
| `GET /api/analytics/sla` | Текущие «замедления»: отклики, сидящие на этапе дольше `sla_days`/`sla_alert_days`, с сортировкой по просрочке |
| `GET /api/analytics/sources` | Разрез по источникам (hh/manual/transfer/…): объём, конверсия до интервью/оффера/найма, Time-to-Hire |
| `GET /api/analytics/rejections` | Причины отказов (по подэтапам «Отказа»): распределение, динамика, разрез по этапу-откуда, вакансиям, инициатору (рекрутер/НМ/авто-скрининг) |
| `GET /api/analytics/team` | По рекрутёрам: перемещений, интервью, офферов, наймов, средняя скорость реакции на новый отклик, просрочки SLA |
| `GET /api/analytics/jobs` | По вакансиям: воронка-мини, дни в работе, активные/всего, наймы, прогноз узкого места |
| `GET /api/analytics/export?report=...&format=csv|xlsx` | Экспорт текущего среза; XLSX — `exceljs`, стриминг |

Метрики (фикс определений):
- **Time-to-Hire** = `hired.entered_at − application.created_at`, p50/p90 по наймам периода.
- **Offer Acceptance** = наймы ⁄ (наймы + отказы с этапа `offer`) за период.
- **Конверсия этапа** = ушли на этап правее ⁄ всего покинувших этап (отказ = не прошёл).
- Подэтапы всегда схлопываются в root (кроме страницы «Причины отказов»).
