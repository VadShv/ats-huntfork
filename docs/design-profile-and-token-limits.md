# Личный кабинет, публичный профиль и персональные лимиты на ИИ

Черновик для обсуждения. Опирается на текущий код HuntFork (ветка `feat/ai-usage`, PR #18).

## 0. Коротко

- **Две страницы вместо одной.** Личный кабинет — то, что видит только сам пользователь (пароль, имя, аватар, свои лимиты и расход ИИ). Публичный профиль — витрина для коллег: ранг, достижения, метрики найма, экипированные косметика и титул. Между ними нет общих блоков, кроме шапки с именем и аватаром.
- **Лимиты — в деньгах, а показывать — в процентах и токенах.** Лимит в деньгах защищает от того, от чего нужно защититься (счёт провайдера), не ломается при смене модели и уже посчитан на каждое событие (`ai_usage_event.cost_base`). Операции и токены как единица лимита хуже — почему, в §3.
- **Один дефолт на организацию + точечные переопределения.** Owner/admin задают «лимит по умолчанию для всех» (день и месяц), а для отдельных людей — свои значения. Пользователь видит свой лимит и его заполнение; суммы — только при `aiUsage:view_costs`, иначе проценты и токены.
- **Персональный лимит блокирует всё, оргбюджет — только фон.** Это разные механизмы с разным назначением: оргбюджет (уже есть) — страховка от неожиданного счёта, персональный лимит — защита от одного человека, который «увлёкся».

## 2. Личный кабинет и публичный профиль

### 2.1 Разделение

| | Личный кабинет | Публичный профиль |
|---|---|---|
| Адрес | `/dashboard/settings/account` (уже есть) | `/dashboard/people/[userId]` (новый) |
| Кто видит | Только сам пользователь | Любой активный участник той же организации |
| Отвечает на вопрос | «Мои настройки и мои ограничения» | «Кто этот человек и как он работает» |
| Данные | Имя, аватар, email, пароль; **мой расход ИИ и лимиты**; активные сессии (есть в better-auth); уведомления | Имя, аватар, роль, команда; ранг и дивизион; достижения; метрики найма; HuntPass; экипированные рамка/титул/акцент; полученные kudos |
| Чего нет | Геймификации (она в «Лиге») | Денег, токенов, лимитов, email, баланса монет, незаработанных достижений |

### 2.2 Личный кабинет: что добавить

Третий блок после «Профиль» и «Пароль» — **«Мой ИИ»**:

1. Две полосы заполнения: «Сегодня» и «В этом месяце» — `израсходовано / лимит`, цвет по порогу (зелёный < 50 %, жёлтый < 80 %, красный ≥ 80 %), подпись «лимит не задан», если ограничений нет.
2. Под полосами — токены за день и месяц (вход / выход, доля кэша), число вызовов, топ-3 операции. Суммы в ₽ — только при `view_costs`; без него проценты и токены.
3. Если лимит исчерпан — плашка «Лимит на сегодня исчерпан, ИИ-действия приостановлены до 00:00 МСК. Запросить увеличение» — кнопка создаёт уведомление owner/admin (тип `ai_budget`, уже есть) с текстом «Иван просит увеличить дневной лимит».
4. Ссылка «Подробный журнал» → `/dashboard/ai-usage?userId=me`.

Данные: один новый `GET /api/me/ai-limits` (лимиты + заполнение + токены), остальное — существующий `summary` с `scope: 'own'`.

### 2.3 Публичный профиль: состав

Страница `/dashboard/people/[userId]`, компонент `UserProfileCard`:

| Блок | Источник | Примечание |
|---|---|---|
| Шапка: аватар в экипированной рамке, титул, имя, роль в организации, команда | `user`, `member.role`, `user_inventory.equipped`, `gamification_team_member` | Роль — человекочитаемая подпись из каталога ролей |
| Ранг: дивизион, подранг, позиция в сезоне, тренд 8 недель | `user_rank`, `rank_history`, `computeUserRp` | Повторяет `RankWidget`, но для чужого `userId` |
| Метрики найма за сезон / всё время: наймов, офферов, закрыто вакансий, средний срок закрытия, интервью в неделю | `computeUserRp`, SQL из `metrics/summary.get.ts` | Переключатель периода как в `MetricsSummaryWidget` |
| Достижения: заработанные, с датами, сначала редкие | `user_achievement` | Незаработанные не показываем |
| HuntPass: тир сезона | `user_season_progress` | Без прогресса SXP до следующего тира |
| Kudos: сколько получено за сезон, последние 3 с текстом | `kudos` | Отправители видны — это их публичное признание |
| Вакансии в работе | `job_member.is_primary` | Только те вакансии, к которым смотрящий имеет доступ (`requireJobInScope`) |

Что делать с API: вынести расчёты из `rank/index.get.ts`, `metrics/summary.get.ts`, `achievements/index.get.ts`, `huntpass/index.get.ts` в утилиты с параметром `userId`, добавить `GET /api/people/[userId]/profile`, который собирает всё одним ответом. Проверка: смотрящий и цель — активные участники одной организации. Собственный эндпоинт лучше четырёх существующих с `?userId=`: один запрос, одно место, где решено, что публично.

Куда ведут ссылки на профиль: лидерборд ранга, лидерборд достижений, упоминания в комментариях (`@имя`), список рекрутёров вакансии (`JobRecruitersSection`), страница «Участники», карточка команды в «Лиге». Везде — `NuxtLink` на `/dashboard/people/[userId]`.

### 2.4 Приватность

- Видимость профиля — в рамках организации, без публичного интернета (`robots: noindex`, `requireAuth`).
- Owner/admin уже могут отключить геймификацию (`gamification_settings`); при отключении профиль показывает только шапку и метрики найма.
- Личный переключатель «скрыть мои достижения от коллег» — не делать сейчас: лидерборды и так публичны внутри организации, второй контур видимости усложнит без запроса от пользователей.

## 3. Персональные лимиты на ИИ: в чём считать

### 3.1 Сравнение единиц

| Критерий | Операции («20 скорингов в день») | Токены («500 тыс. в день») | Деньги («300 ₽ в день») |
|---|---|---|---|
| Понятность пользователю | Высокая | Низкая: никто не знает, сколько «стоит» резюме в токенах | Средняя: суммы понятны, но без `view_costs` показывать нельзя |
| Защищает от большого счёта | Слабо: одна генерация карты поиска стоит как 30 скорингов; вызов на 100 тыс. токенов и на 2 тыс. — одна «операция» | Частично: не учитывает цену модели — у вас модели отличаются в цене в 20 раз (gpt-4o-mini vs o1), 1 млн токенов — это и 15 ₽, и 1 500 ₽ | Напрямую: лимит выражен в том, что защищаем |
| Устойчивость к смене модели / конфигурации | Устойчив | Нет: при переходе на дорогую модель лимит в токенах «молча» становится в 10 раз дороже | Да: цена уже зафиксирована в событии |
| Что уже есть в данных | `count(*)` по `operation` | `input_tokens`, `output_tokens`, `cached_input_tokens`, `reasoning_tokens` | `cost_base` на каждом событии, курс, бюджеты по `scope = 'user'` |
| Слабое место | Разная «цена» операций | Разная цена токена | Конфигурация без цены даёт `cost = null` → в лимит не попадает |

### 3.2 Рекомендация

**Лимит — в деньгах (базовая валюта организации), на пользователя, два периода (день и месяц), с режимом «блокировать».** Пользователю показывать заполнение в процентах и токены; абсолютные суммы — только при `view_costs`.

Закрыть слабое место денег двумя правилами:
1. Событие без цены (`cost IS NULL`) учитывается в лимите по **резервной цене организации** (поле `fallback_price_per_1m` в `ai_usage_settings`, по умолчанию — цена самой дорогой конфигурации организации). Так неоценённые вызовы не обходят лимит, а в журнале они по-прежнему помечены «без цены».
2. В настройках ИИ, если у конфигурации нет цены, — предупреждение «лимиты и бюджеты не защищают от этой конфигурации».

Почему не «токены для рекрутёра, деньги для админа»: два разных числа для одного и того же лимита путают при разборе («у меня 60 %, а у админа написано 80 %»). Одна единица хранения — деньги, разные **представления**: процент, токены, сумма.

Почему не операции: хорошая единица для квот на дорогие действия («не больше 3 генераций карты поиска в день»), но не для защиты бюджета. Если понадобится — это отдельный, более поздний слой поверх денежного лимита (`scope = 'operation'` на пользователя), не вместо него.

### 3.3 Как устроить

**Модель данных** — расширить `ai_usage_budget`, не заводить новую таблицу:

| Изменение | Зачем |
|---|---|
| `scope` += `'member_default'` | Один лимит «для всех участников без личного»; `scope_key = null` |
| `on_exceed` += `'block_all'` | Персональный лимит останавливает и ручные вызовы |
| Уникальный индекс `(organization_id, scope, scope_key, period)` где `is_active` | У человека не может быть двух активных дневных лимитов |
| `ai_usage_settings.fallback_price_per_1m` (вход, выход) | Резервная цена для событий без цены |

Разрешение лимита для пользователя: `scope = 'user' AND scope_key = userId` → иначе `scope = 'member_default'` → иначе без лимита. Owner и admin по умолчанию без лимита (их действия и так в оргбюджете), но admin может поставить лимит и себе.

**Проверка** — обобщить `guardBackground()` в `guardCall()`:
- `trigger = 'background'` → как сейчас (оргбюджеты с `block_background`) **плюс** персональный лимит того, от чьего имени задача (`userId` в контексте).
- `trigger ∈ {user, extension}` → только персональный лимит пользователя.
- `trigger = 'system'` (проверка подключения) → без проверки.
- Статус лимита кэшируется 60 с на `(orgId, userId)`; инвалидация после `flushAiUsage` для затронутых пользователей (хук `onAiUsageFlushed` уже есть). Один вызов может «перелезть» за лимит — это допустимо и честно описано пользователю.
- Отказ — `AiBudgetExceededError` (429) с текстом «Дневной лимит ИИ исчерпан: 300 ₽ из 300 ₽. Сброс в 00:00 МСК. Запросить увеличение у администратора». На клиенте одна общая обработка 429 с `code = 'AI_BUDGET_EXCEEDED'` → тост с кнопкой «Запросить».

**Пороги и уведомления** — переиспользовать `checkBudgets()`: 80 % → уведомление самому пользователю (новый адресат, сейчас — только owner/admin), 100 % → пользователю и owner/admin. При `block_all` на 100 % — текст про приостановку.

**Права**: управление лимитами — существующее `aiUsage:manage_budgets` (owner, admin). Видеть свой лимит — `view_own` (есть у всех). Новое право не нужно.

### 3.4 Интерфейс для owner/admin

На вкладке «Настройки → ИИ → Бюджет и валюта» (существующая `AiUsageBudgetSettings.vue`) добавить секцию **«Лимиты участников»**:

- Строка «По умолчанию для всех»: день — [300 ₽], месяц — [4 000 ₽], режим — «предупреждать / блокировать».
- Таблица участников: имя, роль, лимит день / месяц (пусто = по умолчанию, значение = личный), заполнение сегодня и за месяц в процентах, кнопка «изменить» → инлайн-поля, кнопка «сбросить к умолчанию».
- Фильтр «только с превышением».

Отдельно на странице «Учёт токенов» во вкладке «Сотрудники» — колонка «Лимит» и заполнение, чтобы владелец видел картину в контексте расхода.

### 3.5 Разумные стартовые значения

Для калибровки: средний скоринг отклика на gpt-4o-mini — несколько рублей, генерация карты поиска — десятки рублей, на o-серии — на порядок дороже. Для первого месяца: дневной лимит по умолчанию — порядка 10× типичной дневной нормы рекрутёра на текущей модели, месячный — 20× дневного (с запасом на пики). Через месяц — пересмотреть по данным дашборда (вкладка «Сотрудники», распределение). Конкретные цифры лучше брать из журнала, а не из головы.

## 4. Порядок работ

| Шаг | Состав | Зависимости |
|---|---|---|
| **1. Лимиты (ядро)** | Миграция (`scope member_default`, `on_exceed block_all`, индекс, резервная цена); `guardCall()`; уведомление пользователю; обработка 429 на клиенте | ветка `feat/ai-usage` |

## 5. Открытые вопросы

1. Owner и admin — без лимита по умолчанию или тоже под «дефолтом для всех»? Предложение: без лимита, но с возможностью поставить.
2. Расширение браузера (`trigger = 'extension'`) — блокировать так же, как ручные действия? Предложение: да, это тоже действия пользователя.
3. Фоновые задачи, запущенные пользователем (автоскоринг пакета): при исчерпании его лимита — остановить пакет или довести до конца? Предложение: остановить, остаток помечается «отложено: лимит», как уже сделано для оргбюджета.
4. Показывать ли в публичном профиле «вакансии в работе» коллег, у которых нет доступа к этим вакансиям? Предложение: только название без ссылки, или скрыть полностью — зависит от того, насколько закрыты вакансии между командами.
