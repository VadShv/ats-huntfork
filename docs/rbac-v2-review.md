## 2. Что сделано отлично (подтверждено фактами)

1. **Правильный корневой диагноз.** better-auth AC статичен (роли из кода при
   инициализации) и не поддерживает per-tenant кастомные роли → «свой `can()` +
   права в БД» обоснован. Соответствует реальному ограничению better-auth.
2. **Три оси не смешаны в «роль»** (Role / Scope / Overrides, §4.1) —
   архитектурно зрелое разделение.
3. **Shadow-mode миграция** (Спринт 1: `can()` параллельно старому `hasPermission`
   с логом расхождений) — профессиональная замена критичной системы без простоя.
4. **Сохранение сигнатуры `requirePermission`** (§3.4) — 295 эндпоинтов не надо
   трогать массово, меняется только реализация гарда. Сильный ход.
5. **Defense-in-depth**: route guard → `scopedDb` → field masking → RLS.
6. **Фундамент вперёд** (Спринты 0-2 до UI) — права как сквозная инфраструктура.
7. **Учтены реальные баги** из `audit-rbac.md` (visibility `recruiter`, HM в
   клиенте, роль на SSR, 5 дублей резолва) с привязкой к спринтам.

## 4. Корректировки к плану (5 пунктов)

### 4.1 🔴 RLS (Спринт 4) → вынести в отдельную фазу v2.1
- **Проблема:** `server/utils/db.ts` — глобальный пул `postgres.js` (`max:10`),
  запросы НЕ обёрнуты в транзакции. `SET LOCAL app.org_id` работает только внутри
  транзакции; иначе при пуле контекст протекает в чужой запрос (worst-case —
  показ данных чужой орги).
- **Масштаб недооценён:** потребуется обернуть в транзакцию с установкой контекста
  практически каждый запрос к мультитенантным таблицам — это изменение всего слоя
  доступа к БД, не «1.5 недели».
- **Рекомендация:** `scopedDb` + masking + тесты изоляции закрывают ~95% риска на
  уровне приложения. RLS как «последний барьер» — ценно, но выносим в v2.1 после
  того, как app-уровень доказал надёжность. НЕ блокировать весь модуль на RLS.

### 4.2 🔴 `scopedDb()` (Спринт 3) — переоценить объём на пилоте
- ~295 мест с ручным `eq(organizationId, orgId)` используют РАЗНЫЕ паттерны (raw
  drizzle, джойны, агрегаты аналитики, сложные фильтры). Универсальный `scopedDb`
  либо тонкий (легко обойти), либо толстый (огромный объём). 2 недели оптимистично.
- **Рекомендация:** пилот на 5-10 самых чувствительных эндпоинтах
  (candidate/document/application/export/AI-ассистент), замерить стоимость,
  затем экстраполировать сроки.

### 4.3 🟠 Одна роль на участника в v2 (union ролей — отложить)
- `member_roles` допускает несколько ролей (union прав), но это усложняет `can()`,
  UI и ментальную модель. Overrides (allow/deny) покрывают ~90% потребности
  «роль + чуть-чуть».
- **Рекомендация:** v2 — одна роль на участника; union вынести в v3 (в §15 это
  уже открытый вопрос).

### 4.4 🟢 Тест-инфраструктура есть — использовать
- Факт: `vitest ^4.1.11` + `@playwright/test ^1.62.1`; `npm run test`,
  `test:watch`, `test:e2e`; **37 unit** в `tests/unit/`, **46 e2e** в `e2e/`;
  уже есть security-тесты (`auth-security-hardening`, `security-fixes`,
  `sso-security`); `TESTING-SECURITY.md` в корне.
- **Рекомендация перед Спринтом 1:** (а) прогнать `npm run test`, зафиксировать
  зелёную базу; (б) матричные тесты `can()` делать чистыми юнитами БЕЗ БД (быстро,
  генерируются сотнями); (в) тесты изоляции/scope — в существующий
  `e2e/critical-flows/`.

### 4.5 🟠 Добавить план отката ПОСЛЕ переключения enforcement (Спринт 2)
- Shadow-mode защищает ДО переключения. Нужен и план отката ПОСЛЕ: если в проде
  после перехода на `can()` вскроется проблема — как быстро вернуться на старый AC
  (feature-flag переключения enforcement old↔new).

## 5. Пробелы (чего в плане нет)

1. **Производительность `scopedDb` на списках/аналитике.** `job_id IN (…сотни…)` +
   JOIN аналитики — нужны индексы и проверка планов запросов. NFR (§1.4) покрывает
   `can()` p95<5мс, но не стоимость scope-фильтров в тяжёлых запросах.
2. **Инвалидация прав при нескольких инстансах.** Кэш контекста в памяти процесса
   (§5.1) + `permissions_version`: для single-instance self-hosted ок; для облака
   (упоминается) нужен внешний кэш/pub-sub — не проговорено.
3. **Миграция старых `activity_log` при hash-chain.** Доисторические записи без
   `prev_hash`/`entry_hash` — как верификатор трактует границу цепочки.
4. **Разделение ролей БД для аудита (§7.3).** Сейчас приложение ходит под одной
   ролью (`db.ts`). `REVOKE UPDATE/DELETE` на `activity_log` + `BYPASSRLS` для
   миграций = разделение прав БД, требует продумать миграционный доступ.
5. **2FA (§10.6) недооценена по объёму.** Better-auth-плагин + UI (enroll, recovery
   codes) — это неделя сама по себе, а не строка в Спринте 8.
6. **Field masking по умолчанию.** Маскирование в сериализаторе легко обойти на
   «сыром» эндпоинте (аналитика, экспорт, AI-контекст, вебхуки). Должно быть
   masking-on-output ПО УМОЛЧАНИЮ, а не опционально; реестр ресурсов (§6) помогает,
   но нужна дисциплина на каждом новом эндпоинте.

«14-16 недель» реалистично при полной занятости одним человеком без отвлечений.

критика плана, а ожидание по срокам.

## 7. Итоговая рекомендация
**Принять план за основу.** Применить 5 корректировок (§4): RLS → v2.1; пилот
`scopedDb`; одна роль в v2; использовать готовую тест-инфру; добавить план отката.
Учесть 6 пробелов (§5) при детализации спринтов. Порядок спринтов и архитектурное
решение (свой `can()`) — верные, менять не нужно.

Приоритет для немедленной пользы (и снятия мигания UI): **Спринт 0.5**
(роль на SSR + единый `getActorContext`) — самостоятельная ценность даже до
полного RBAC v2.
