# Идея: разовый импорт кандидатов с распределением по этапам как на hh.ru

> **Статус:** зафиксированная идея, ждёт детального ТЗ (точный маппинг коллекций hh → системная воронка будет описан отдельно).
> Связано: `docs/funnel-architecture.md` (раздел 7), Спринт 22 (индикатор расхождения A3).

## Проблема

При внедрении системы у клиента уже идёт подбор на hh.ru: по вакансии есть отклики,
часть кандидатов приглашена, часть в отказе. Сейчас привязка вакансии импортирует всех
на входной этап — рекрутеру приходится вручную повторять раскладку, которая уже сделана на hh.

## Решение (согласовано 19.08.2026)

При **первичной привязке** вакансии hh.ru — опция (чекбокс, по умолчанию выключен):

> «Распределить кандидатов по этапам как на hh.ru»

Кандидаты импортируются и сразу раскладываются по этапам системной hh-воронки
в соответствии с коллекциями переговоров hh (response, consider, phone_interview,
assessment, interview, offer, hired, discard и кастомные этапы работодателя).

## Зафиксированные принципы

1. **Разовость.** Распределение выполняется один раз при привязке. Постоянной двусторонней
   синхронизации перемещений НЕ делаем — для расхождений есть индикатор (Спринт 22, A3).
2. **Опциональность.** Без флага поведение прежнее (все на входной этап).
3. **Защита от авто-правил.** Кандидаты, импортированные сразу на продвинутый этап,
   помечаются источником (например, `stageSource='hh_distribution'`) и **исключаются из
   авто-скрининга и авто-отказа**. Человек, который на hh уже на «Интервью», скрининг
   в реальности прошёл; авто-отказ такого кандидата при внедрении недопустим.
   Скрининговый контур (Qwen/Yandex) не модифицируется.
4. **Фолбэк для несмапленных.** Маппим коллекцию hh на этап: по типу → по названию.
   Что не смапилось (кастомные этапы работодателя на hh) — на входной этап + отчёт
   «N кандидатов не распределены» с перечнем.
5. **Перемещения — только через `moveApplicationStage()`** (bulk-режим, без спама уведомлений),
   легаси-статус деривируется штатно.
6. **Опциональный фоновый скоринг** — только информационный (оценка без перемещений),
   отдельным решением.

## Что будет в детальном ТЗ (следующий шаг)

- Точная таблица маппинга: коллекции hh (включая employer states) → этапы системной воронки
  `a57a11a0-0000-4000-8000-000000000001`.
- Поведение для вакансий с кастомной (не системной) воронкой.
- UX отчёта о распределении (сколько куда, кто не смапился).
- Идемпотентность при повторной привязке / ре-синке.
