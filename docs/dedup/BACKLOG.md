## Приоритет 1 — то, что закрывает явные дыры в текущем флоу

### 1.1. Rollback merge (Этап 6, изначально в плане)
- Бэкенд `mergeCandidates` уже пишет `rollback_until` и поддерживает `action='rollback'` в `candidate_merge_log`, но UI кнопки в журнале и карточке отключены с tooltip.
- Нужно:
  - POST `/api/dedup/merges/[id]/rollback` — транзакция: восстановить `mergeStatus='active'`, обнулить `mergedIntoId`, перенести обратно identity-записи если были перемещены, записать `action='rollback'` в `candidate_merge_log`.
  - Что делать с application/activity/document, созданными ПОСЛЕ merge на primary — оставить у primary, при rollback ничего не трогать (нужно решить на дизайне).
  - UI: активировать кнопку «Откатить» в журнале и на карточке (где `canRollback=true`), модалка подтверждения, refetch.
- Срок жизни rollback: 30 дней (значение в `rollback_until`).

### 1.2. Объединение истории стадий заявки при коллизии при merge
- Сейчас: если у primary и merged есть `application` на одну и ту же `(jobId, candidateId)` — uniqueIndex заставляет удалять одну. Мы удаляем merged application и его историю стадий.
- Нужно:
  - Сохранить timeline-историю стадий из merged → склеить с primary, отсортировать по timestamp.
  - Объединить квалификационные оценки, AI-скоры, заметки на стадиях.
  - Решить конфликт «разные финальные стадии у двух заявок»: оставить более позднюю как актуальную, остальное в журнал стадий с пометкой «слито из merged».

### 1.3. PATCH-сценарий «обновить существующего» из формы создания
- При exact-дубле сейчас две кнопки: «Открыть существующего» и «Изменить данные».
- Можно добавить третью: **«Дополнить существующего из этой формы»** — мерж полей черновика в карточку существующего (если у него пусто `phone`, а в форме введено — записать; добавить `quickNotes` в начало).
- Полезно, когда recruiter получил уточнение по существующему и кладёт его как «новый» по привычке.

## Приоритет 2 — качество дедупа

### 2.1. Fuzzy-матчинг по 4-у сигналу: образование/последний работодатель
- Сейчас `computePairScore` использует ФИО (55%), город (20%), ДР (25%).
- Без ДР и города fuzzy не дотягивает до 85 даже при идеальном совпадении ФИО — это видно в smoke (Юрий Мосцеев одно ФИО → fuzzy пусто).
- Идея: добавить сигнал `lastEmployer` (last_experience.company из hh_resume_raw) и `educationInstitution`. Веса перераспределить, threshold не трогать.

### 2.2. Fuzzy при ручном создании — поле «город» в форме
- В check-duplicates `city` уже принимается, но в форме `/candidates/new` поля города нет.
- Если добавить опциональный input «Город» в форме — fuzzy начнёт срабатывать на ФИО+город (что критично для дублей без ДР).

### 2.3. Identity-резолв для linkedin/telegram/github при ручном вводе
- Сейчас identity ставятся только из hh-resume и при ручном создании — только email/phone.
- В форме создания нет полей для linkedin/telegram/github.
- Идея: добавить блок «Контакты» (свернутый) с этими полями + поле «Источник» уже есть (UI-only), но не персистится. Сделать источник полноценной FK на справочник.

### 2.4. Пере-расчёт fuzzy-очереди по триггеру
- Сейчас fuzzy запускается только при создании кандидата и hh-sync.
- Если recruiter поменял ФИО/ДР существующему кандидату через PATCH — fuzzy не пересчитается, и потенциальные дубли могут не обнаружиться.
- Идея: при PATCH полей `firstName/lastName/dateOfBirth/email/phone` запускать `findFuzzyDuplicatesForCandidate(id)` и upsertить пары.

### 2.5. Сильный сигнал «нормализованный hh_owner_id»
- `candidate_identity` поддерживает `hh_owner_id` (resume owner), но при ручном создании мы его не ставим. При hh-sync — да.
- Сейчас если рекрутер сначала вручную добавил, а потом синкнул то же резюме с hh — попадёт в fuzzy ≥95 или exact (если email/phone совпали). Но если email/phone разные, а hh_owner_id один — мы не свяжем.
- Идея: сделать `hh_owner_id` обязательным для resume-based exact матча.

## Приоритет 3 — UX/полировка

### 3.1. Журнал слияний — экспорт в CSV/XLSX
- Сейчас только просмотр. Юристам/комплаенсу нужен выгружаемый отчёт.

### 3.2. Журнал слияний — фильтр «cross-org»
- Текущие фильтры: статус, тип merge, пользователь, даты, поиск. Добавить тогл «только cross-org слияния» — важно для группы Astra.

### 3.3. Дашборд дублей — приоритезация
- Сортировка по score уже есть. Добавить:
  - Бейдж «фрод-флаг есть у одного из» — приоритет ручной обработки.
  - Бейдж «есть активные заявки у обоих» — критично, чтобы не потерять.
  - Сортировка по «времени в очереди».

### 3.4. Live-проверка при создании — спиннер прямо в полях
- Сейчас спиннер только в заголовке боковой панели. Можно добавить маленький лоадер справа от полей email/phone, пока идёт debounce-проверка.

### 3.5. Подсветка различающихся полей в модалке merge
- При side-by-side показе primary vs merged в модалке слияния — подсвечивать поля, которые различаются, чтобы recruiter сразу видел что именно «съест» merge.

### 3.6. История слияний в карточке кандидата
- Сейчас на карточке primary не видно, что в него уже что-то сливали. Добавить блок «Объединён с N кандидатами» с раскрытием → список merged + ссылки в общий журнал.

## Приоритет 4 — техдолг

### 4.1. Drizzle-схема для `organization_group`
- Сейчас доступ через raw SQL и хелпер `getOrgGroupId(orgId)`. Из-за этого нет типизации и автокомплита.
- Идея: добавить `organization_group` в Drizzle schema → можно безопасно использовать `.where(eq(organization.groupId, ...))` напрямую.

### 4.2. Тесты на fuzzy/identity
- Unit-тесты на `computePairScore`, `normalizePhone`, `nameSimilarity` (есть Levenshtein с транслитом — кейсы «Юрий Мосцеев» / «Yury Mostseev» должны давать ≥85).
- Интеграционные на `findDuplicatesForDraft`: кросс-org, merged-редирект на primary, выбросить из exact'a уже выбранных.

### 4.3. Очередь fuzzy при создании — фоновый воркер
- Сейчас в POST /api/candidates fuzzy-детект бежит синхронно — добавляет 100-300мс к ответу при большой базе.
- Идея: вынести в очередь (BullMQ / pg_cron / setImmediate) — пользователь получает 201 быстро, fuzzy крутится в фоне.

### 4.4. baseline TypeScript ошибок
- `npx nuxi typecheck` показывает кучу ошибок, не связанных с нашим кодом (legacy). Хорошо бы один раз почистить — pre-commit / CI будет полезнее.

### 4.5. Логирование дедупа в structured format
- Сейчас `console.error` в catch-блоках. Добавить structured logging через pino/winston с тегом `dedup`, чтобы ловить регрессии в проде.

## Приоритет 5 — стратегия (R&D, на потом)

### 5.1. Векторный матчинг (как в общей архитектуре Huntfork)
- В memory есть план: 70% pgvector + multilingual-e5-small, 30% FTS.
- Для дедупа можно эмбеддить fullName + city + опыт работы → косинусная близость как дополнительный сигнал в `computePairScore`. Решит кейсы транслита, опечаток, разных форматов имени.

### 5.2. AI-арбитр merge-кандидатов
- YandexGPT/Opus получает оба кандидата как контекст, отвечает «дубль / не дубль» + объяснение.
- Не для авто-merge, а как доп. сигнал в UI: «AI считает: 92% дубль, причина: одинаковая трудовая история 2018-2023 в Сбере и одинаковый возраст».

### 5.3. Merge с N>2 кандидатами за раз
- Сейчас merge только парный. Иногда в очереди появляются «грозди» (A↔B, B↔C, A↔C) — recruiter должен трижды нажать merge.
- Идея: модалка «Объединить все 3 в одного» с выбором primary.

### 5.4. Дедуп при импорте через CSV/XLSX
- Сейчас при импорте файла дедупа нет (если такая функция вообще есть). При появлении импорта — переиспользовать `findDuplicatesForDraft` построчно.
