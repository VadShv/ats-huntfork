# Huntfork — Ролевая модель и права доступа (v1)

Дата: 18.08.2026 · Статус: актуально после коммита `3a8bce7` (Sprint 20)
Источник истины в коде: `shared/permissions.ts` (движок — Better Auth access control, deny-by-default).

---

## 1. Два уровня ролей

В системе два независимых уровня:

| Уровень | Где хранится | Что определяет |
|---|---|---|
| **Org-роль** | `member.role` (owner / admin / member / hiring_manager) | Что пользователь может делать в организации в целом |
| **Назначение на вакансию** | `job_member.member_role` (recruiter / hiring_manager) | К каким вакансиям пользователь «прикреплён» и в каком качестве |

Org-роль отвечает на вопрос «что можно», назначение — «где именно». Сейчас назначения влияют на видимость («Мои кандидаты» у НМ) и командную панель вакансии; фильтрация «рекрутёр видит только свои вакансии» — задел на будущее (см. §5).

---

## 2. Org-роли: матрица прав

Deny-by-default: всё, что не указано, — запрещено.

| Ресурс | owner | admin | member (рекрутёр) | hiring_manager (НМ) |
|---|---|---|---|---|
| organization | R U D | R U D | R | R |
| job (вакансии) | CRUD | CRUD | R U | R |
| candidate | CRUD | CRUD | C R U | R |
| application (отклики) | CRUD | CRUD | C R U | R |
| document | CRUD | CRUD | C R | R |
| comment | CRUD | CRUD | C R D | R* |
| interview | CRUD | CRUD | C R U | R |
| emailTemplate | CRUD | CRUD | C R U | — |
| activityLog | R | R | R | R |
| scoring (ИИ-оценка) | CRUD | CRUD | C R | R |
| sourceTracking | CRUD | CRUD | R | — |
| pipeline (воронки) | CRUD | CRUD | R | R |
| Участники org (создание НМ, инвайты) | ✔ | ✔ | — | — |

\* НМ видит только не-внутренние комментарии (`is_internal=true` скрываются на сервере, `server/utils/comments/visibility.ts`).

Ключевые следствия:

- **Создание и удаление вакансий** — только owner/admin. Рекрутёр (member) ведёт вакансию (`job:update`): настройки, воронка, назначение НМ и рекрутёров.
- **НМ read-only везде**; его действия «одобрить/отклонить» идут через отдельные `/api/hm/*`-эндпоинты, которые выполняют переход этапа в системном контексте.
- **Приглашение участников** (в т.ч. создание учёток НМ по invite-link) — только owner/admin, раздел Настройки → Участники.

## 3. Назначения на вакансию (`job_member`)

| member_role | Кого можно назначить | Кто назначает | Как |
|---|---|---|---|
| `recruiter` | Участник с org-ролью owner / admin / member | Любой с `job:update` | Настройки вакансии → «Рекрутёры»; создатель вакансии назначается **автоматически** при создании |
| `hiring_manager` | Только пользователь с org-ролью hiring_manager | Любой с `job:update` | Настройки вакансии → «Нанимающие менеджеры» |
| `watcher`, `assignee` | — | — | Зарезервированы (API вернёт 501) |

Свойства:

- На вакансии может быть **несколько** рекрутёров и несколько НМ.
- Вставка идемпотентна (уникальный индекс job+user+role), снятие — через DELETE с указанием `memberRole`.
- Все назначения/снятия пишутся в activity log (`resource_type='job_member'`).

### Что даёт назначение сегодня

| Назначение | Эффект |
|---|---|
| НМ на вакансии | Кандидаты вакансии появляются у НМ в «Мои кандидаты»; НМ выносит решения об интервью (first-decision-wins) |
| Рекрутёр на вакансии | Отображается в команде вакансии; создатель фиксируется автоматически. Основа для будущей фильтрации «мои вакансии» и аналитики загрузки |

## 4. Кто что видит в UI (сводка)

| Раздел | owner/admin | member (рекрутёр) | hiring_manager |
|---|---|---|---|
| Панель, Вакансии, Кандидаты, Отклики, Интервью | ✔ | ✔ | — (свой кабинет) |
| «Мои кандидаты» (кабинет НМ) | — | — | ✔ (только свои вакансии) |
| Настройки вакансии (вкл. секции «Рекрутёры», «НМ») | ✔ | ✔ | — |
| Кнопки «Пригласить нового», удаление назначений | ✔ | ✔ (job:update) | — |
| Настройки → Участники | ✔ | — | — |
| Зарплатные ожидания кандидатов | ✔ | ✔ | только при `hmCanViewSalary=true` |
| Внутренние комментарии (`is_internal`) | ✔ | ✔ | — |

Известное ограничение: роль `hiring_manager` не зарегистрирована в клиентском `auth-client.ts`, поэтому клиентский `usePermission` для НМ возвращает false на всё — НМ работает в отдельном кабинете `/api/hm/*`, на общие страницы не полагается. Это осознанное решение v1.

## 5. План: настройка прав в UI (Настройки → Участники)

Цель — чтобы owner/admin могли настраивать права ролей прямо в интерфейсе, без деплоя.

### Этап A — прозрачность (быстро, без миграций)

Вкладка «Роли и права» в Настройки → Участники: read-only матрица из §2, рендерится из `shared/permissions.ts` (единый источник истины). Владелец видит, «кто что может», прямо в продукте.

### Этап B — переопределения per-org

1. Таблица `org_role_permission`:
   `organization_id`, `role` (member / hiring_manager), `resource`, `actions text[]`, `updated_by`, `updated_at`.
   Роли owner/admin **не редактируются** (защита от самоблокировки).
2. Сервер: `requirePermission()` мержит статические права из `shared/permissions.ts` с переопределениями org (кэш в памяти с инвалидацией по `updated_at`).
3. UI: в матрице из этапа A появляются переключатели для ролей member и hiring_manager; изменение пишет строку в `org_role_permission` + activity log.
4. Ограничители: нельзя отнять `*:read` у роли целиком, если это ломает базовые экраны; подтверждение при сужении прав; кнопка «Сбросить к стандартным».

### Этап C — гранулярность по вакансиям (опционально)

Использовать `job_member` как фильтр области действия: опция org «рекрутёр видит только вакансии, где он назначен». Это переключатель поведения списков (`WHERE job_id IN (SELECT ...)`), а не новая роль.

Рекомендуемый порядок: A → B; C — после обратной связи от команды.

## 6. Открытые вопросы

1. **Давать ли member право `job:create`?** Сейчас создавать вакансии могут только owner/admin (осознанное решение при внедрении ролей). Авто-назначение создателя рекрутёром уже работает для любых создателей. Если рекрутёры должны заводить вакансии сами — это одна строка в `shared/permissions.ts`, предлагаю решить при внедрении этапа A.
2. Снятие последнего рекрутёра с вакансии сейчас не блокируется — оставить как есть или запретить «осиротевшие» вакансии?
3. Нужен ли отдельный org-уровень «наблюдатель» (read-only member) — или хватит этапа B с урезанием прав member?
