# Спринт H — Модель «Рекрутер = свои / Ведущий = все» + UX-полировка дашборда

> Финализация ролевой модели рекрутинга + UX. Один спринт, коммиты по частям.
> Дополняет `docs/rbac-v2-phase2-tail.md`, `docs/rbac-v2-security-invariants.md`.
> Процесс: доступы = высокий риск → сверка ДО прод-деплоя. Полная `npm run build`
> (клиент + СЕРВЕР до «Server built»); деплой `--no-cache` (урок C1).

---

## Продуктовая модель (решение владельца)

**Рекрутер (member) — БАЗОВАЯ роль, scope = свои вакансии:**
- Видит только вакансии, где он `job_member(recruiter)` (или создатель).
- Дашборд, «Вакансии», «Кандидаты», «Отклики» — только свои.
- Карточка ЧУЖОЙ вакансии (где не назначен) → 404 (вход закрыт).
- Карточка кандидата: доступна если он ДОБАВИЛ кандидата ИЛИ кандидат откликнулся
  на ЕГО вакансию. Тогда видит всё (все версии резюме, историю). Чужой отклик
  того же кандидата — плашка без перехода.
- НЕ рыщет по общей базе: список кандидатов = только его. НО дедуп при добавлении
  ищет по всей орге → покажет «уже есть» (плашка) → рекрутер «встаёт в очередь»
  (тегает в обсуждении первого рекрутера). Это рабочая схема, НЕ блокировать.
- Может добавлять/откликать кандидата, который уже есть у коллеги (кандидат общий).

**Ведущий (lead) — ДОВЕРЕННЫЕ, scope = вся орг:**
- Видит всё, тумблер «Мои/Все».
- Доступ к любым вакансиям/кандидатам.

**Роли не меняем по правам** — только scope-дефолты и UX. Продвинутые функции
ведущего (песочница/промпты/суфлёр) — как в Спринте E.

## ЧАСТЬ 1 — Scope-дефолты и миграция (backend)

### 1.1 member дефолт scope: org → assigned
- [ ] `role-presets.ts`: `member.defaultScope` = `org` → **`assigned`**.
- [ ] `defaultScopeTypeForRole`: member → `assigned`.
- [ ] Ведущий (lead) остаётся `org`. external — `assigned` (как есть). HRBP —
      company/dept (как есть).

### 1.2 Миграция: рекрутеры не теряют свои вакансии
- [ ] Идемпотентная seed-миграция: для каждой вакансии, где `job.createdBy = X`
      и X — активный член с ролью member/lead → создать `job_member(userId=X,
      memberRole='recruiter', isPrimary=true)` если ещё нет. Чтобы создатель
      видел свою вакансию под scope assigned.
- [ ] Обновить member_scope существующих member: org → assigned (только тех, кто
      на дефолте, без явного сужения — как §A2, но обратно).
- [ ] bump permissions_version затронутых.

### 1.3 Создатель вакансии → авто primary-рекрутер
- [ ] `jobs/index.post` (создание вакансии): после создания — автоматически
      `job_member(userId=creator, memberRole='recruiter', isPrimary=true)`.
      Чтобы создатель сразу видел свою вакансию (scope assigned) и был основным.

**Acceptance 1:** новый рекрутер видит только вакансии где он job_member/создатель;
создав вакансию — сразу видит её (он primary recruiter); действующие рекрутеры
после миграции видят свои (по createdBy).

## ЧАСТЬ 2 — Доступ к карточкам (backend, проверить/добить)

Большинство уже closed в Спринте G. Проверить под scope assigned:
- [ ] Карточка вакансии `jobs/[id].get` — рекрутер вне scope → 404 (есть, проверить).
- [ ] Карточка кандидата `candidates/[id].get` — рекрутер видит если кандидат в
      его scope (добавил ИЛИ откликнулся на его вакансию) → иначе 404 (есть).
- [ ] «Плашка чужого отклика без перехода»: в карточке кандидата заявки НЕ
      фильтруются (видна вся история), но переход в чужую вакансию → 404 +
      `jobInScope`-флаг для UI (есть от §5, проверить для member).
- [ ] Дедуп `check-duplicates`/добавление — ищет по орге (показывает дубль вне
      scope) — НЕ трогать (нужно для «встал в очередь»).

**Acceptance 2:** рекрутер по прямому URL к чужой вакансии/кандидату → 404; свой
кандидат — все версии резюме/история; чужой отклик общего кандидата — плашка без
перехода.

## ЧАСТЬ 3 — UX дашборда (frontend)

### 3.1 Рекрутер: дашборд только свои, без тумблера
- [ ] Убрать тумблер «Мои/Все» у member (scope assigned → нечего переключать).
- [ ] Подпись дашборда «Мои вакансии» (для member).
- [ ] ВСЕ блоки дашборда рекрутера по его scope: вакансии в воронке, счётчики
      (открытые вакансии/кандидаты), **последние отклики** (только по его
      вакансиям), **предстоящие интервью** (только его). Чтобы не было каши
      «отклик от неизвестной вакансии».

### 3.2 Ведущий: тумблер + корректные блоки
- [ ] Тумблер «Мои/Все» остаётся.
- [ ] **Предстоящие интервью — ВСЕГДА персональные** (где он организатор/
      интервьюер), даже при тумблере «Все» (иначе каша чужих интервью).
- [ ] Последние отклики — по тумблеру (Мои → по его вакансиям; Все → по всем).
- [ ] Вакансии в воронке — по тумблеру.

### 3.3 Фикс багов дашборда
- [ ] **Кэш useFetch:** список воронки не меняется при «Мои/Все». Причина —
      фиксированный `key: 'dashboard-stats'`. Фикс: key включает scope
      (`dashboard-stats-${scope}`). Файл `useDashboard.ts`.
- [ ] **Группировка по рекрутерам при «Все»:** сейчас только owner/admin
      (`groupTopJobs`). Показывать и ведущему при scope='all' (раскрывающиеся
      табы по рекрутерам). Файл `dashboard/index.vue` + проверить jobs/index.vue
      (`groupByRecruiter`).

### 3.4 Плавное переключение (убрать скачки)
- [ ] `keepPreviousData`-паттерн: при смене scope НЕ обнулять data — держать
      старый список, заменить когда пришли новые (индикатор загрузки поверх).
- [ ] `min-height` контейнера списка + сохранять позицию скролла (не прыгать
      наверх). Опц. fade-переход.

## ЧАСТЬ 5 — Поиск и массовые действия под scope (проверить/добить)

Проверить, что поиск/bulk НЕ раскрывают чужих кандидатов рекрутеру (scope assigned):
- [x] `candidates/index.get` (основной поиск+список) — уже scoped (candidateScopeCondition). Проверить, что при assigned ищет ТОЛЬКО своих.
- [x] `org-search` — это поиск ОРГАНИЗАЦИЙ по slug (не кандидатов) → scope НЕ нужен, не трогать.
- [ ] `extension/search-run.post`, `extension/search-batch.post`, `search-map.post`
      (сорсинг через браузер-расширение) — ПРОВЕРИТЬ scope: результаты/доступ к
      кандидатам под assigned. Если возвращают чужих — заскоупить или обосновать
      (сорсинг привязан к вакансии → job-scope).
- [ ] `dedup/ai-arbitrate-batch.post` (массовый AI-арбитраж дублей) — ПРОВЕРИТЬ:
      обрабатывает только кандидатов в scope актора (рекрутер не арбитрит чужих).
- [x] `candidates/[id]/merge-batch`, `jobs/[id]/batch-score` — уже scoped (B/C).
- [ ] Если есть иные bulk-эндпоинты (массовое отклонение/перемещение/экспорт) —
      прогнать через scope; экспорт кандидатов под assigned → только свои.
- [ ] Аналитика рекрутера — по его scope (ожидаемо, не org-wide).

**Acceptance 5:** рекрутер (assigned) через поиск/расширение/bulk НЕ получает
чужих кандидатов; экспорт — только свои.

## НЕ ломать
- Дедуп по орге (нужен для «встал в очередь»).
- Обсуждение-комментарии (всем в scope), переписка-модель (Спринт G).
- job-роль recruiter, HM-контур, webhook-и.
- owner/admin/lead/hrbp/external поведение.

## DoD Спринта H
- member scope = assigned: видит только свои вакансии/кандидатов/отклики/интервью
  везде (дашборд, списки, карточки); чужие → 404; дашборд без тумблера, подпись
  «Мои вакансии».
- Создатель вакансии → primary recruiter (видит свою).
- Ведущий: тумблер Мои/Все; интервью всегда персональные; группировка при «Все».
- Дашборд: список меняется при переключении (кэш-фикс); без скачков.
- Тумблер вакансий — в фильтрах.
- Дедуп/очередь, обсуждение, переписка — не сломаны. audit-coverage = 0.
