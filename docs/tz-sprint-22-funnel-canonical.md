### Дополнительные находки встречного аудита (не вошли в исходный)

**A1. 🔴 ТРИ параллельные реализации перемещения по воронке.**
- `server/utils/pipeline-move.ts:moveApplicationStage` — канонический утиль (используют только HM-decisions и cancel);
- `server/api/applications/[id]/stage.patch.ts` — **собственная inline-копия** той же логики (не использует утиль!) с дублем `stageTypeToStatus`;
- `server/utils/ai/autoReject.ts:230-256` — **третья копия** (свой транзакционный блок).

Любая правка логики перемещения требует синхронного изменения трёх мест. Это ровно та рассинхронизация «статусов, состояний и действий», которую мы решили не допускать.

**A2. 🔴 Push на hh.ru вызывается ТОЛЬКО из stage.patch.ts.**
`grep pushStageChangeToHh` по всему репо: единственный вызов — `stage.patch.ts:174`. Следствие:
- **отказ через решение НМ** (`/api/hm/decisions`) двигает этап локально, но кандидат на hh.ru остаётся в активной коллекции;
- **авто-отказ по скору** (`autoReject.ts`) — то же самое;
- **отмена решения НМ** (`cancel.post.ts`) — то же;
- **массовый перевод** из `applications/index.vue:544` — работает (каждый вызов идёт через stage.patch), но N параллельных запросов = N последовательных push без батчинга.

Кандидаты, отклонённые НМ или авто-скорингом, «висят» на hh.ru как активные. Рассинхрон с воронкой hh.ru уже в проде.

**A3. 🟠 Входящий синк не двигает локальный этап — и никак не сигнализирует о расхождении.**
`sync.ts:310-320`: для существующих откликов обновляется только `hhNegotiation.hhCollection`. Это осознанный дизайн (наша воронка — master), но UI нигде не показывает «на hh.ru кандидат в другой коллекции». Рекрутёр, работающий в двух окнах, не видит расхождения.

**A4. 🟡 Схема UI-маппинга усечена против возможностей push.**
`stage-mappings.put.ts:16` разрешает 8 коллекций, включая только `discard_by_employer`. `pushAction.ts` умеет 3 discard-коллекции (`discard_by_employer`, `discard_after_interview`, `discard_visible_by_opponent`) с матрицей приоритетов. Настроить «отказ после интервью» через UI нельзя.

**A5. 🟡 Мёртвый код и лживый тип в sync.ts.**
`mapApplicationStatus(): 'new' | 'reviewing' | 'rejected' | 'hired'` — статус `reviewing` не существует в `application_status`; функция всегда возвращает `'new'`. Убрать/типизировать.

**A6. 🟡 `transferred` («Перевод на другую вакансию») — терминал без механики перевода.**
Этап существует, но нет действия «перевести»: никто не создаёт новую application на целевой вакансии, нет связи между старой и новой заявкой. Сейчас это просто «отказ с другим названием».

**A7. 🟢 pipeline-move.ts не обновляет PostHog.** Комментарий в утиле честно говорит «external side-effects делает вызывающий», но HM-flow PostHog-событие о смене этапа не шлёт. Аналитика product-воронки недосчитывается HM-переводов.

## Часть 1. Целевая модель воронки

### 1.1 Принципы (зафиксировать в docs/)

1. **Одна рабочая воронка** — системный пресет «Стандартный hh.ru». Ключевые (системные) этапы не редактируются и не удаляются — только скрытие и переупорядочивание (уже реализовано через `isSystemStage`).
2. **Подэтапы — единственный инструмент кастомизации.** Пользователь может создавать custom-подэтапы (1 уровень) под любым системным этапом, включая «Отказ».
3. **`application.currentStageId` — единственный источник правды** о позиции кандидата. `application.status` — derived-проекция, поддерживается автоматически, на запись закрыта (409 уже есть).
4. **Все перемещения — через один утиль** `moveApplicationStage` со всеми side-effects внутри.
5. **Наша воронка — master, hh.ru — slave.** Исходящий push обязателен из всех путей; входящий синк локальный этап не двигает, но расхождение видно в UI.

### 1.2 Реструктуризация отказов: родитель «Отказ» + подэтапы-причины

**Целевая структура bucket=rejected:**

```
Отказ (новый системный этап, type=not_fit*, bucket=rejected, isTerminal=true)
├─ Не подходит            (был not_fit  → становится подэтапом)
├─ Кандидат отказался     (был withdrawn → подэтап)
├─ Не выходит на связь    (был no_show  → подэтап)
├─ Вакансия закрыта       (был job_closed → подэтап)
├─ Перевод на другую вакансию (был transferred → подэтап)
└─ [custom-подэтапы пользователя: «Отклонил оффер», «Не прошёл СБ», …]
```

\* Тип родителя — см. решение D1 ниже.

**Почему подэтапы, а не 5 отдельных колонок:** канбан сжимается с 13 до 9 колонок; причины отказа — это справочник, а не воронка; аналитика отказов (Часть B будущего дашборда) получает естественную группировку «этап → причина»; пользователь может добавлять свои причины, не raspухая доску.

### 1.3 Совместимость с hh.ru — детальный разбор (главный вопрос)

**Вердикт: перевод отказов в подэтапы полностью совместим с синхронизацией hh.ru.** Обоснование по коду:

1. **Исходящий push работает per-stage, а не per-type.** `hh_stage_mapping` привязывает `pipelineStageId → hhCollection` — подэтап это такой же stage со своим id. Каждый подэтап-причина может иметь свой маппинг и **свой `messageTemplate`** — то есть кандидату при «Не подходит» и «Вакансия закрыта» уйдут разные тексты отказа. Это апгрейд, а не деградация.
2. **Fallback-маппинг устойчив к иерархии.** `pushAction.ts:200-209`: для custom-подэтапа берётся тип родителя. Если подэтапы сохранят свои нынешние типы (`not_fit`, `withdrawn`, …) — fallback сработает напрямую: все 5 типов уже мапятся в `discard_by_employer` (`pushAction.ts:99-106`).
3. **У hh.ru нет гранулярных причин отказа.** В API работодателя всего 3 discard-коллекции: `discard_by_employer`, `discard_after_interview`, `discard_visible_by_opponent`. Наша гранулярность причин живёт только на нашей стороне — hh получает «отказ + сообщение». Терять нечего.
4. **Входящий импорт не затрагивается вообще.** Новые отклики входят на entry-этап `new` (`sync.ts:504-506`); существующие — обновляется только `hhCollection`. Структура отказной ветки на импорт не влияет. **Импорт с hh.ru не пострадает.**
5. **Discard требует сообщения** — уже реализовано (`DEFAULT_DISCARD_MESSAGE` + `messageTemplate`), для подэтапов ничего не меняется.

Единственный нюанс: `COLLECTION_PRIORITY` перебирает discard-коллекции при 400/403/404 — поведение сохраняется без изменений.

## Часть 2. Ключевые решения (согласовать до реализации)

**D1. Тип родительского этапа «Отказ».**
Рекомендация: **вариант (а)** — добавить в enum новое значение `rejection_parent` (или переиспользовать legacy `rejected` как тип родителя — он уже в enum, мапится в `discard_by_employer` и legacy-статус `rejected`). Переиспользование `rejected` не требует миграции enum и «легализует» legacy-значение вместо его убийства. Вариант (б) — родитель типа `not_fit`, но тогда «Не подходит»-подэтап дублирует тип родителя. **Предлагаю: родитель = type `rejected` (переосмысленный как «группа отказов»), подэтапы сохраняют свои типы.**

**D2. Можно ли бросить кандидата НА родителя «Отказ» без выбора причины?**
Рекомендация: **нет.** Родитель — группирующий контейнер: при дропе на колонку «Отказ» UI открывает пикер причины (подэтапа) + опциональный комментарий. API: `moveApplicationStage` отклоняет перевод на этап, у которого есть активные подэтапы, с кодом 422 и списком подэтапов (см. 4.3). Это гарантирует, что аналитика причин отказа всегда заполнена.

**D3. Модель переходов: жёсткая матрица или свободный граф?**
Рекомендация: **свободный граф + 3 guard-правила** (не копировать матрицу hh):
- **G1 (из терминала — только назад в работу):** из этапа `hired` и из отказной ветки разрешён только переход «Вернуть в работу» (на любой working-этап), требует `application:update` + комментарий обязателен. Прямой `hired → offer` и `not_fit → interview` без комментария запрещён.
- **G2 (в hired — подтверждение):** перевод в `hired` в UI требует явного confirm-диалога («Кандидат выходит на работу?»).
- **G3 (в отказ — причина):** см. D2.
Жёсткая матрица «только вперёд» отвергается: реальный рекрутинг ходит назад (кандидат вернулся, оффер переиграли), а страдать будет UX. Полная свобода тоже отвергается (см. F2-риски). Guards покрывают 95% реальных ошибок.

**D4. Судьба legacy `application.status`.**
Рекомендация: **оставить как derived, зачистить потребителей постепенно.** В этом спринте: (1) миграция-нормализация — пересчитать `status` из `currentStageId` для всех заявок (устранить накопившийся рассинхрон custom-этапов); (2) инвариант-чек в `moveApplicationStage`; (3) для custom-этапов производить статус от **типа корневого родителя**, а не «не трогать» (сейчас статус замирает). Удаление колонки — не в этом спринте (19 потребителей, включая расширение и дашборды).

**D5. «Перевод на другую вакансию» — делать ли механику перевода?**
Рекомендация: **да, минимальную** (см. 4.6): диалог выбора целевой вакансии → создание новой application на entry-этапе + отказ старой с причиной `transferred` + перекрёстные ссылки в metadata. Без этого этап-причина лжёт пользователю.

## Часть 3. Миграции БД

Все — идемпотентные, через штатный drizzle-пайплайн (`server/database/migrations/`), без прямого psql.

### M1. `0062_rejection_parent_stage.sql` — реструктуризация отказов

Для **каждой org** с системной воронкой «Стандартный hh.ru»:

1. Создать этап «Отказ»: `type='rejected'`, `bucket='rejected'`, `isTerminal=true`, `isSystemStage=true`, `displayOrder` = max(working)+1, цвет `#ef4444`.
2. Существующим 5 системным отказным этапам проставить `parentStageId = <id Отказа>` (имена, типы, id, маппинги hh — не меняются; заявки не трогаем: `currentStageId` продолжает указывать на те же id).
3. Валидация после: подэтапы наследуют bucket родителя (уже так), терминальность сохраняется.

**Ничего не ломается:** id этапов стабильны → `application_stage_history`, `hh_stage_mapping`, снапшоты вакансий остаются валидными. Меняется только отображение (группировка).

### M2. `0063_status_normalization.sql` — нормализация legacy-статуса

```sql
-- Пересчитать application.status из типа корневого этапа (custom → тип родителя)
UPDATE application a SET status = <проекция>::application_status
FROM pipeline_stage s LEFT JOIN pipeline_stage p ON p.id = s.parent_stage_id
WHERE a.current_stage_id = s.id AND a.status IS DISTINCT FROM <проекция>;
```

Проекция = `stageTypeToLegacyStatus(coalesce(p.type при s.type='custom', s.type))`. Выполнить в миграции разово; количество затронутых строк — в лог миграции.

### M3. Сид (`pipeline-seed.ts`) — обновить пресет

«Стандартный hh.ru» для новых организаций сидится сразу с родителем «Отказ» и 5 подэтапами. Пресет «Простой» — пометить `isArchived`/убрать из выдачи для новых org (решение «работаем только по одной воронке»).

### M4. Опционально (если принят D5): `application.transferredToApplicationId text NULL REFERENCES application(id)`.

## Часть 4. Бэкенд

### 4.1 Канонизация: один путь перемещения (главная задача спринта)

`server/utils/pipeline-move.ts` становится **единственной** реализацией. Расширение:

```ts
export interface MoveStageOptions {
  // …существующие поля…
  /** Пропустить push на hh (например, при массовых операциях — батчим снаружи). */
  skipHhPush?: boolean
  /** Событие PostHog шлётся всегда, распознаётся по activityAction. */
}
```

Внутрь утиля переносятся (fire-and-forget, как сейчас в stage.patch):
- `pushStageChangeToHh` — **из всех путей**: ручной перевод, HM-решение, HM-отмена, авто-отказ, bulk;
- PostHog `application stage_changed` (с полем `via: 'manual' | 'hm_decision' | 'auto_reject' | 'bulk' | 'transfer'`);
- инвариант-чек legacy-статуса (см. 4.4).

Рефакторинг вызывающих:
- `stage.patch.ts` — удалить inline-копию (~120 строк), вызвать утиль. Удалить локальный дубль `stageTypeToStatus`;
- `autoReject.ts` — удалить свой транзакционный блок, вызвать утиль с `actorUserId: null`, `comment: reasonComment`;
- `hm/decisions/*` — уже на утиле; получат hh-push и PostHog автоматически.

### 4.2 Guard-правила переходов (D3) — внутри `moveApplicationStage`

```ts
// G1: из терминального этапа — только с комментарием («вернуть в работу»)
if (fromStage?.isTerminal && !opts.comment) → 422 'Возврат из терминального этапа требует комментария'
// G3: на этап с активными подэтапами — нельзя, только на подэтап
if (targetHasActiveChildren) → 422 { code: 'CHOOSE_SUBSTAGE', substages: [...] }
```

G2 (confirm на hired) — чисто клиентский. Guards не применяются при `actorUserId === null` только для авто-отказа? **Нет** — применяются ко всем: авто-отказ всегда идёт с комментарием, HM-отказ — на подэтап «Не подходит» (см. 4.5).

### 4.3 API-изменения

- `PATCH /api/applications/:id/stage` — тонкая обёртка над утилём; в ответ добавить `parentStageId` и `parentStageName` целевого этапа (для тостов «Отказ → Не подходит»).
- `GET /api/applications/:id/stages` (питает QuickActions/StagePicker) — уже отдаёт иерархию; проверить, что родитель с подэтапами помечается `selectable: false`.
- `PUT /api/hh-vacancy-links/:id/stage-mappings` — расширить `HH_COLLECTIONS` всеми 3 discard-коллекциями (A4).
- **Новое** `POST /api/applications/:id/transfer` (D5): `{ targetJobId, comment? }` → транзакция: создать application на целевой вакансии (entry-этап, source сохранить, скопировать документы-ссылки) → перевести старую на подэтап `transferred` с comment и `transferredToApplicationId` → activity на обе заявки. Push на hh — только по старой заявке (discard).

### 4.4 Инвариант-чек статуса

В `moveApplicationStage` после транзакции (dev/test — throw, prod — console.error + метрика): прочитать заявку, сверить `status === stageTypeToLegacyStatus(effectiveType(currentStage))`. Плюс изменение проекции: для `custom` брать тип корневого родителя (fix «замирания» статуса).

### 4.5 Отказ НМ — на подэтап

`hm-stage-resolver.ts`: `resolveRejectedTargetStage` сейчас ищет этап типа `not_fit`/`rejected`. После M1 родитель «Отказ» типа `rejected` станет первым кандидатом — а на него переводить нельзя (D2). Исправить: резолвить **подэтап «Не подходит»** (type=`not_fit`, parentStageId NOT NULL). Комментарий НМ уже пишется.

### 4.6 Индикатор расхождения с hh (A3)

`GET /api/applications/:id` (и карточка в канбане для hh-заявок): добавить в ответ `hhCollection` из `hhNegotiation` + вычисленный флаг `hhOutOfSync` (ожидаемая коллекция от текущего этапа ≠ фактическая). UI — бейдж «hh.ru: Подумать» с тултипом. Кнопка «Синхронизировать» = повторный push (уже есть идемпотентность).

### 4.7 Мелкие фиксы

- `sync.ts:mapApplicationStatus` — убрать мёртвый тип `'reviewing'` (A5).
- `pipeline-validation.ts:ALL_STAGE_TYPES` — legacy-типы `applied` исключить из допустимых при **создании** этапов; `rejected` — разрешён только для системного родителя «Отказ» (F4).
- `pipeline-snapshot.put.ts` — валидация `все currentStageId заявок вакансии ∈ snapshot.stages` при сохранении снапшота, иначе 422 со списком «осиротевших» заявок (F6).
- Логика «активных заявок»: `grep bucket.*working` по репо — заменить на `bucket='working' AND NOT isTerminal` (F5, `hired` не активный).

## Часть 5. Frontend

### 5.1 Канбан вакансии (`jobs/[id]/index.vue`, `candidates.vue`)

- Колонка «Отказ» — одна, свёрнутая по умолчанию (как отказная зона сейчас), с счётчиком по подэтапам: «Отказ 12 · Не подходит 8 · Отказался 3 · …».

- Жёсткую матрицу переходов «как hh.ru» — guards вместо неё (D3).
- Удаление `application.status` — только нормализация и derived-контракт (D4).
- Двустороннюю синхронизацию (hh → наш этап) — наша воронка master; только индикатор расхождения.
- Мультиворонки/редактор новых воронок — работаем на одном системном пресете; «Простой» скрывается для новых org.
- SLA этапов, аналитический дашборд — Часть B (Спринт 23), фундамент (чистая history + причины отказов) закладывается здесь.
- Иерархию подэтапов глубже 1 уровня.

## Часть 7. План работ и порядок

**Этап 1 — канонизация путей (без изменения UX):**
1. Расширить `moveApplicationStage` (hh-push, PostHog, инвариант-чек, custom→родительский статус).
2. Перевести `stage.patch.ts` и `autoReject.ts` на утиль, удалить дубли.
3. Фиксы: `mapApplicationStatus`, `ALL_STAGE_TYPES`, snapshot-валидация, `HH_COLLECTIONS`.
4. Миграция M2 (нормализация статусов) + лог расхождений.
5. Смоук: ручной перевод, HM-решение, авто-отказ — все три пишут историю, двигают статус, пушат на hh.

**Этап 2 — отказы-подэтапы:**
6. Миграция M1 + обновление сида M3.
7. `resolveRejectedTargetStage` → подэтап «Не подходит».
8. Guards G1/G3 в утиле; G2 + `RejectReasonDialog` в UI.
9. Канбан/QuickActions/таймлайн — группировка «Отказ / причина».

**Этап 3 — доводка:**
10. Индикатор `hhOutOfSync` + кнопка ре-синка.
11. Перевод на другую вакансию (M4 + API + диалог).
12. Настройки: «+ причина отказа», шаблоны сообщений per-причина.
13. Обновить `docs/` (модель воронки, контракт перемещения) и ТЗ-аудит.

**Критерий приёмки (сквозной сценарий):**
отклик импортирован с hh → скрининг → НМ отклонил → заявка на «Отказ / Не подходит», legacy-статус `rejected`, запись в history с actor=система, activity `hm_rejected`, кандидат на hh.ru переведён в discard с сообщением, PostHog-событие есть; «Вернуть в работу» с комментарием возвращает на working-этап и (вручную) ре-синкает hh; импорт новых откликов работает без изменений.

## Часть 8. Риски

| Риск | Митигация |
|---|---|
| Миграция M1 на проде затронет живые заявки | Не затронет: id этапов неизменны, меняется только `parentStageId` у 5 этапов + добавляется 1 новый. Rollback = обнулить parentStageId и удалить родителя |
| hh-push из авто-отказа устроит «шторм» сообщений кандидатам при массовом скоринге | Батч-скоринг вызывает утиль с `skipHhPush` + отдельная пост-обработка с rate-limit (hh и так лимитирует); идемпотентность `hhActionLog` уже защищает от дублей |
| Guards сломают привычный drag-and-drop | G1/G3 дают 422 с внятным `code` — UI перехватывает и открывает диалог, а не показывает ошибку |
| Custom→родительский статус изменит цифры на дашборде | Ожидаемо и правильно (сейчас цифры врут). В релиз-нотах предупредить; M2 логирует число исправленных строк |
| `resolveRejectedTargetStage` найдёт родителя вместо подэтапа в старых воронках без M1 | Резолвер: сначала подэтап типа `not_fit`, затем корневой `not_fit` (fallback для не мигрированных воронок) |
