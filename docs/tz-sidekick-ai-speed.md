# ТЗ — Ускорение ИИ-генерации в Sidekick: первый токен < 2 сек, стриминг везде

Дата: 22.08.2026 (ред. 2 — модели не меняем) · Репозиторий: reqcore-astra · Затрагивает: `server/api/extension/*`, `server/utils/ai/*`, `extension/`
**Не трогаем:** скрининговый контур (Qwen на Yandex Cloud, `autoScore`/`structureResume`), импорт с hh.ru, продуктовый AI-ассистент ATS.

---

## 1. Результаты аудита

### 1.1. Главная причина медленности — модель analysis-контура

Проверено на проде (read-only SELECT из `ai_config`):

| Контур | Провайдер | Модель (по записи в БД) | max_tokens | Кто использует |
| --- | --- | --- | --- | --- |
| **analysis** (по умолчанию) | cloud_ru | **Qwen/Qwen3.5-397B-A17B** | 16 384 | summarize (все режимы, вкл. «Вопросы»), verification/run, interview-card, search-map |
| **chatbot** (по умолчанию) | cloud_ru | deepseek-ai/DeepSeek-V4-Flash | 16 384 | chat |

⚠️ **Расхождение с ожиданием:** подключалась GLM 5.2 через Cloud.ru, а в `ai_config.model` записано `Qwen/Qwen3.5-397B-A17B`. Строка model отправляется в API Cloud.ru как есть — значит либо реально отвечает Qwen, либо запись — заглушка. Решение: **модель пока не меняем**, но в П1 добавляем проверку, какая модель фактически отвечает (API Cloud.ru возвращает поле `model` в ответе — будем логировать его).

На диагноз расхождение не влияет: и GLM 5.2, и Qwen3.5-397B — **reasoning-модели**: перед видимым ответом генерируется блок «размышлений». Итог:

- **TTFT (время до первого токена)** — десятки секунд: thinking-токены не отдаются в `textStream`, пользователь смотрит на пустой экран;
- **скорость генерации** ниже, чем у компактных моделей;
- показательно: чат (chatbot-контур, DeepSeek V4 Flash) ощущается быстрым — на том же сервере и том же коде. Разница подтверждает: дело в thinking-фазе analysis-модели, а не в инфраструктуре.

### 1.2. Верификация и карточка интервью — вообще без стриминга

`verification/run.post.ts` и `interview-card.post.ts` используют блокирующий `generateObject`: клиент ждёт **весь JSON целиком** (по коду — «15–60 секунд»), путь идёт через background service worker (`chrome.runtime.sendMessage` → один ответ), который стримить не умеет. UI показывает только спиннер.

### 1.3. Тумблер «Глубокий анализ» — плацебо

Клиент шлёт `reasoning: reasoningEnabled.value` в `summarize` и `chat`, но серверные zod-схемы это поле **молча отбрасывают**. Управления thinking-режимом моделей нет нигде: reasoning-модель «думает» всегда, независимо от тумблера.

### 1.4. Стриминг саммари уже есть, но невидим в начале

`summarize.post.ts` отдаёт SSE, панель рендерит `aiText += delta` — это работает. Проблема только в TTFT (п. 1.1) и в том, что во время thinking-фазы ничего не показывается.

### 1.5. Мелкие находки

- **Баг кэш-ключа** (`summarize.post.ts:59`): в ключе `text.length`, а не хэш текста → возможны и ложные попадания (другой кандидат с тем же URL и длиной), и промахи (повторный захват той же страницы ±1 символ).
- Режим `questions` не кэшируется (`CACHEABLE = summary|fit|card`), хотя детерминирован так же.
- Кэш in-memory на контейнер — умирает при каждом деплое.
- **Телеметрии нет**: `logApiRequest` не пишет ни TTFT, ни общую длительность — деградации не видны.
- В `interview-card`/`verification` в промпт уходит до 24 000 символов профиля — для reasoning-модели это дорого и медленно.

## 2. Целевые метрики (принимаются по телеметрии из П1)

Модель analysis-контура не меняется, поэтому целей две группы:

| Метрика | Сейчас (оценка) | Цель |
| --- | --- | --- |
| Первый видимый отклик (мысли или текст) | 15–60 с пустого экрана | **< 3 с** — стрим «размышлений» на экране |
| TTFT ответа при выключенном «Глубоком анализе» (thinking off) | недоступно (тумблер-плацебо) | < 3 с |
| Первый видимый контент верификации/карточки | 15–60 с (весь JSON) | первая секция сразу после thinking-фазы |
| Пустой экран без индикации | вся thinking-фаза | 0 с — этап виден всегда |

## 3. Пакеты работ

### П1. Телеметрия скорости + проверка фактической модели (фундамент, полдня)

- В `summarize`/`chat`/`verification/run`/`interview-card`/`search-map` замерять: `ttft_ms` (до первого delta), `total_ms`, `tokens_per_sec`, модель/провайдера — и писать в существующий `logApiRequest`.
- Логировать **фактическую модель из ответа API Cloud.ru** (`response.modelId` в AI SDK) — закрыть вопрос «GLM 5.2 или Qwen»: если отвечает не та модель, что подключалась, поправить одну строку в настройках ИИ (это правка конфига, не кода).
- В SSE-событие `done` добавить `timing: { ttftMs, totalMs }`; в UI после ответа показывать мелкой строкой «5,2 с · DeepSeek V4 Flash» (как в Sider).
- Приёмка: по логам PostHog можно построить p50/p95 TTFT до и после остальных пакетов.

### П2. Purpose `interactive` — только архитектурная подготовка (отложено, ~0,5 дня)

По решению от 22.08 **модели не меняем**. Пакет сокращён до подготовки без смены поведения:

- Новый purpose **`interactive`** в `loadAiConfig` с фолбэком на analysis — все эндпоинты панели переводятся на него, но пока `is_default_interactive` не задан, фактически работает та же analysis-модель. Поведение не меняется ни на йоту.
- В настройках ИИ в ATS появляется третий переключатель «Быстрые задачи панели» — выключен по умолчанию.
- Это даёт возможность позже одним кликом (без деплоя) назначить быструю модель на саммари/вопросы, когда решим экспериментировать.
- Скрининг и продуктовый ассистент не затрагиваются: purpose меняется только в `server/api/extension/*`.

### П3. Честный контроль reasoning + «мысли» на экране (главный выигрыш, ~1 день)

- Принять поле `reasoning: boolean` в схемах `summarize`/`chat` (сейчас отбрасывается).
- Обёртка fetch для cloud_ru (по образцу `yandexFetch.ts`): при `reasoning=false` инжектить параметр отключения thinking — для GLM это `thinking: { type: "disabled" }`, для Qwen `chat_template_kwargs: { enable_thinking: false }`; выбор по имени модели (allowlist), у неизвестных моделей тело не трогаем. При `reasoning=true` — без изменений.
- Так как модель остаётся reasoning-класса, именно этот пакет даёт основной выигрыш по скорости: с выключенным thinking GLM/Qwen отвечает в разы быстрее, а с включённым пользователь с первых секунд видит стрим «размышлений» вместо пустого экрана.
- Читать `result.fullStream` вместо `textStream`: reasoning-дельты отдавать отдельным SSE-событием `{ thinking: "..." }`.
- UI: сворачиваемый блок «Рассуждение…» с приглушённым стримом мыслей (как в Sider/DeepSeek) — пользователь видит жизнь с первой секунды даже на reasoning-модели. По завершении блок сворачивается в строку «Думал 12 с».
- Приёмка: при выключенном тумблере thinking-токенов нет в ответе Cloud.ru; при включённом мысли стримятся на экран.

### П4. Стриминг структурированных отчётов (верификация, карточка) (~1–1,5 дня)

- Сервер: заменить `generateObject` на **`streamObject`** (AI SDK) в `verification/run` и `interview-card`; отдавать SSE `{ partial: <объект> }` по мере валидации + финальное `{ done, report }`. Схемы zod не меняются.
- Клиент: у `useVerificationRun`/`useInterviewCardRun` уйти от `chrome.runtime.sendMessage` на прямой `sseFetch` из панели (паттерн уже есть в `useSidekick.ts:528`) — background для этих вызовов больше не нужен.
- UI: секции отчёта (хронология → противоречия → проверяемость → флаги → вопросы) появляются по мере прихода: скелетоны секций заполняются, у последней строки — каретка. Порядок полей в zod-схеме уже совпадает с порядком секций — partial-рендер ложится естественно.
- Фолбэк: если стрим оборвался — одна повторная попытка блокирующим путём.
- Приёмка: первая секция верификации видна < 3 с (на fast-модели) / < 10 с (на analysis); спиннер «в никуда» удалён.

### П5. Диета промптов и кэш (~0,5 дня)

- Кэш-ключ: `sha1(нормализованный text)` вместо `text.length`; добавить `questions` в `CACHEABLE`.
- Лимиты текста под задачу: summary/questions — 10 000 симв. (сейчас 15 000), verification/interview-card — 16 000 (сейчас 24 000); срезать боилерплейт hh.ru (шапка поиска, футер) регуляркой до отправки.
- Ограничить выход: `maxOutputTokens` на интерактивных режимах 1 200–2 000 вместо орг-настройки 16 384 — меньше хвост генерации.
- (Опционально, если появится Redis) вынести кэш из памяти контейнера.
- Приёмка: повторный запрос той же страницы отдаётся из кэша мгновенно, включая «Вопросы».

### П6. UX мгновенного отклика (~0,5 дня, параллельно с П3/П4)

- Единый индикатор этапов над ответом: «Читаю страницу → Думаю → Пишу» + секундомер; этап «Думаю» подсвечивается во время thinking-стрима.
- Каретка-курсор у последнего символа стрима (сейчас текст просто дописывается).
- Кнопка «Остановить» — уже есть для саммари (`abortAi`), добавить для верификации/карточки (AbortController в `sseFetch` уже поддержан).
- Автоскролл к низу во время стрима с уважением ручного скролла вверх (как в ChatView).

### П7. Проверка и приёмка (~0,5 дня)

- Смоук на проде: TTFT по телеметрии П1 на реальном резюме hh.ru по всем режимам.
- Playwright-QA панели: скелетоны, partial-рендер, thinking-блок, каретка (светлая/тёмная тема, 380/320 px).
- Сборка, TS-чек по базлайнам, zip, деплой сервера.

## 4. Порядок и оценка

| Этап | Пакеты | Эффект | Оценка |
| --- | --- | --- | --- |
| 1 | П1 + П3 | главный выигрыш: мысли на экране < 3 с, быстрый режим без thinking, ясность с моделью | 1,5 дня |
| 2 | П4 + П6 | верификация/карточка перестают быть «чёрным ящиком», Sider-подобная визуализация | 1,5–2 дня |
| 3 | П5 + П7 | кэш, диета промптов, приёмка | 1 день |
| 4 (отложен) | П2 | архитектурная готовность к быстрой модели — включается позже одним кликом | 0,5 дня |

Итого ~4 рабочих дня на этапы 1–3. Этап 1 самодостаточен: если остановиться после него, основная жалоба уже закрыта.

## 5. Риски

- Параметры отключения thinking различаются между моделями Cloud.ru (GLM `thinking.type`, Qwen `chat_template_kwargs`) — обёртку делать по allowlist, при неизвестной модели поле не слать; первым делом в П1 выяснить, какая модель реально отвечает.
- Если фактическая модель окажется не той, что подключалась (Qwen вместо GLM 5.2), — это правится строкой в настройках ИИ организации; в рамках этого ТЗ код моделей не выбирает и не меняет.
- `streamObject` на openai-совместимых эндпоинтах Cloud.ru нужно проверить на первой же модели: если JSON-стрим нестабилен — фолбэк-режим из П4 обязателен.
- Скрининг не затрагивается ни одним пакетом: `autoScore` продолжает ходить в свой конфиг, purpose `interactive` (П2, отложен) вводится только для эндпоинтов `server/api/extension/*`.
