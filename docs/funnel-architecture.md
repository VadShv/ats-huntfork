# Воронка — канонический словарь системы

> **Статус:** действующий архитектурный документ (living doc).
> Обновляется при каждом изменении модели этапов, статусов, действий или состояний.
> История решений: `docs/tz-sprint-22-funnel-canonical.md` (Спринт 22), Фаза 1 «словарь = воронка» (август 2026).

## 1. Главный принцип

**В системе один словарь — воронка.** Везде, где пользователь видит положение кандидата
(фильтры, колонки, счётчики, аналитика, канбан), показываются **реальные названия этапов
воронки** с их цветами. Легаси-словарь из шести статусов (`new/screening/interview/offer/hired/rejected`)
в продуктовом UI не используется.

Источник истины о положении отклика — `application.currentStageId` → `pipeline_stage`.

## 2. Модель данных

### 2.1 `pipeline` — воронка организации

- Принадлежит организации, у организации может быть несколько воронок.
- `isSystem` — системный пресет (hh-совместимый), сидится один раз на организацию,
  нельзя редактировать/удалять — только клонировать. Системная hh-воронка: `a57a11a0-0000-4000-8000-000000000001`.
- `isDefault` — воронка по умолчанию для новых вакансий (ровно одна на организацию).
- `isArchived` — исключает воронку из выборок.

### 2.2 `pipeline_stage` — этап воронки

| Поле | Назначение |
| --- | --- |
| `type` | Семантический тип этапа (см. 2.3). Определяет поведение, а не название. |
| `bucket` | `working` \| `rejected` — разделение «В работе» / «Отказы». `hired` живёт в `working`. |
| `displayOrder` | Порядок в воронке. |
| `isTerminal` | Финальный исход (hired / отказные). |
| `isSystemStage` | Базовый этап: **нельзя менять, убирать или менять тип/bucket**. Можно только скрыть (`isHidden`) и добавлять к нему подэтапы. |
| `isHidden` | Скрыт из UI-списков, но данные не теряются. |
| `parentStageId` | Подэтап (например, причина отказа). Наследует `type`, `bucket`, терминальность от родителя. Вложенность — максимум один уровень. |

Корни системной hh-воронки: Все неразобранные (`new`), Подумать (`on_hold`),
Первичный контакт (`contact`), Тестовое задание (`assessment`), Интервью (`interview`),
Предложение о работе (`offer`), Выход на работу (`hired`), Отказ (`rejected`) + подэтапы-причины отказа.

### 2.3 Типы этапов (`pipeline_stage_type`)

- **Working:** `new`, `on_hold`, `contact`, `screening`, `assessment`, `interview`, `offer`
- **Terminal success:** `hired`
- **Terminal reject:** `not_fit`, `withdrawn`, `no_show`, `job_closed`, `transferred`
- **Legacy (не использовать для новых этапов):** `applied` (алиас `new`), `rejected` (алиас `not_fit`)
- **Пользовательский:** `custom`

### 2.4 Производное «Состояние» отклика

UI показывает три состояния, вычисляемых из текущего этапа (не хранится в БД):

```
bucket = 'rejected'  → «Отказ»
type   = 'hired'     → «Принят»
иначе                → «В работе»
```

Реализация — функция `appState()` на страницах Отклики / Кандидаты вакансии.

## 3. Действия и перемещения

**Единственный путь перемещения** отклика по воронке — `moveApplicationStage()`
(`server/utils/pipeline-move.ts`): guard-правила переходов, запись activity/событий,
синхронизация легаси-статуса через `stageTypeToLegacyStatus()`.

Создание отклика (`applications/index.post.ts`, hh-импорт `importResume.ts`,
импорт из сорсинга `import.post.ts`) ставит `currentStageId = entryStage` воронки вакансии
(`getEntryStageForPipeline()`) и `status = 'new'` — это консистентно и разрешено.

Быстрые действия (QuickActions), StagePicker, канбан, действия НМ — всё сводится
к `moveApplicationStage()`. Прямых `UPDATE application SET status/current_stage_id` вне
этого пути быть не должно.

## 4. Решение: `application.status` НЕ удаляем (ADR, август 2026)

**Контекст.** После Фазы 1 продуктовый UI не читает легаси-статус. Исходный план Фазы 2
предполагал выпил колонки `application.status` из БД.

**Решение.** Колонку **оставляем** как производную легаси-проекцию (денормализованный кэш).

**Причины:**

1. `status` пишут/читают критичные внешние контуры: hh-импорт и синк (`hh/importResume.ts`,
   `hh/sync.ts`), проверка из расширения Sidekick (`extension/check.post.ts`), дедупликация,
   AI-инструменты чата, трекинг событий — на момент решения ~18 серверных файлов.
2. Back-compat API (`?status=`, поле `pipeline` в jobs API) нужен Sidekick и внешним интеграциям.
3. Одно понятное поле упрощает SQL-аналитику и отладку по проду (без join на этапы).
4. Выигрыш от удаления — только «чистота схемы»; цена ошибки — поломка импорта с hh.ru.

**Правила жизни `status`:**

- **Ноль чтений в продуктовом UI.** Интерфейс читает только `currentStage*` и производное «Состояние».
- **Одна точка деривации** — `stageTypeToLegacyStatus()` внутри `moveApplicationStage()`.
  Маппинг: `hired→hired`, `offer→offer`, `interview→interview`, `screening→screening`,
  `applied/new→new`, `on_hold/contact/assessment→screening`, все reject-типы→`rejected`.
- Прямые записи `status: 'new'` допустимы только при создании отклика (вместе с entry stage).
- Поле read-only для API-потребителей; новые фичи на него не опираются.

**Пересмотренная Фаза 2** (когда-нибудь, без спешки): добить остаточные чтения `status`
в непродуктовых местах (dedup, hm-панель, AI-инструменты) — заменить на этапы. Колонку не трогать.

## 5. API-контракты

### 5.1 `/api/applications` (GET)

- `stageIds=id1,id2` — мультиселект по этапам (лимит 50, дедуп). **Подэтапы разворачиваются
  автоматически**: указание корня включает всех его детей.
- `stageId=` — точечный фильтр (+ дети). Back-compat.
- `status=` — легаси-фильтр, back-compat для Sidekick/интеграций. В UI не используется.
- Ответ содержит `currentStageId, currentStageName, currentStageColor, currentStageBucket, currentStageType`.

### 5.2 Справочник этапов

- `/api/pipelines/stages-summary` — все не-архивные воронки организации с этапами
  (id, name, color, type, bucket, parentStageId, isSystemStage, displayOrder), без скрытых.
- `/api/pipelines/:id` — этапы конкретной воронки (канбан, фильтр вкладки «Кандидаты»).

### 5.3 Ролл-ап для аналитики — `getOrgStageRollup()`

`server/utils/funnel-rollup.ts`. Возвращает `stageToRoot` (подэтап → корень) и `rootColumns`
(упорядоченные корневые этапы всех не-архивных воронок). Используется в:

- `/api/source-tracking/stats` — воронка `канал → корневой этап → count` + `funnelStages`;
- `/api/tracking-links/:id/stats` — `funnel` как массив корневых этапов с count.

Группировка — по `application.currentStageId`; отклики без этапа в воронку не попадают.

### 5.4 Jobs API

`/api/jobs` отдаёт `stages` (счётчики по корневым этапам с ролл-апом) — UI строит колонки динамически.
Легаси-поле `pipeline` (`{new..rejected}`) оставлено для back-compat, в UI не используется.

## 6. Правила UI

1. Фильтры по положению кандидата — **только этапы воронки** (чипы/чекбоксы с цветом этапа).
   Никаких захардкоженных списков из шести статусов.
2. Колонка «Состояние» (В работе / Принят / Отказ) — производная, см. 2.4.
3. Ссылки между экранами передают `?stage=<stageId>`; легаси `?status=`/`?stageId=` конвертируются
   на странице Откликов (маппинг `LEGACY_STATUS_TO_TYPES`), сохранённые виды мигрируются.
4. В аналитике отказные корни агрегируются в одну колонку/строку «Отказ».
5. Отклик без этапа — фолбэк «Без этапа»; кандидат без откликов — пометка «Без отклика».
6. Цвет этапа — из `pipeline_stage.color` (inline style), не из захардкоженных tailwind-классов.

## 7. Интеграция с hh.ru

- Импорт отклика/резюме ставит кандидата на **входной этап** воронки вакансии; статус `new`.
- Направление синхронизации — hh → система (отклики, сообщения). Публикации вакансий из системы в hh нет.
- Расхождение положения кандидата с hh подсвечивается индикатором (Спринт 22, A3).
- Обсуждаемое расширение: опциональное **распределение кандидатов по этапам как на hh.ru**
  при первичной привязке вакансии (см. ROADMAP). Ключевые требования: маппинг коллекций hh
  на этапы системной hh-воронки, отключённые авто-правила (авто-скрининг/авто-отказ) для
  кандидатов, импортированных сразу на продвинутые этапы.

## 8. Чего осознанно НЕ делаем

- Не удаляем `application.status` (см. раздел 4).
- Не редактируем и не удаляем системные этапы (`isSystemStage`) — только скрытие и подэтапы.
- Не даём двигать отклики мимо `moveApplicationStage()`.
- Не смешиваем словари: статус вакансии (`open/…`) и статус отклика — разные сущности;
  `query: { status: 'open' }` в диалогах выбора вакансии относится к вакансиям.
