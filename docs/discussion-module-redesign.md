# Модуль «Обсуждение» · разбор и предложение по редизайну

Дата: 07.10.2026 · Репозиторий: `VadShv/ats-huntfork`, ветка `main` (анализ по состоянию `feat/ai-usage` = main + учёт ИИ) · Статус: предложение, решения по открытым вопросам приняты 07.10.2026 (раздел 9), код не менялся.

Связанные документы: `docs/tz-collaboration-hub.md` (ТЗ «Обсуждения 2.0», этапы 1–4 реализованы), `docs/plan-realtime-updates.md` (план общего SSE-канала), `docs/role-model-and-permissions.md`.

---

## 1. Коротко

Модуль за два месяца вырос из плоского треда комментариев в «комбайн»: вкладки по откликам, контекст-виджеты, ИИ-резюме, снимки скрининга и риска, @ai-ассистент, slash-команды, шаблоны, стикеры, опросы, умные подсказки, подписчики, прочитавшие, печатает, фильтры, поиск, горячие клавиши, перевод по этапам из шапки, синхронизация с hh.ru. Всё это живёт в одном блоке длинной страницы отклика и показывается **одновременно**: в развёрнутом состоянии пользователь видит порядка 20 элементов управления до первого сообщения.

Предложение — оставить в кадре только то, что нужно для разговора о кандидате (как в чате Телеграма: лента, ответ, реакция, одно поле ввода), а рабочие действия ATS собрать по правилу Хантфлоу: **комментарий и смена этапа — одно действие**, закреплённое наверху, события в той же ленте. Всё остальное — во второй слой: меню «+» в поле ввода, меню «⋯» в шапке, панель поиска. Ничего из бэкенда удалять не нужно: API остаются, меняется поверхность.

Целевые цифры: 7 видимых элементов управления вместо ~20; 1 экран высоты вместо 3 «шапок»; комментарий + смена этапа за 1 отправку вместо 2 действий.

## 3. Проблемы, подтверждённые кодом

### 3.1 Перегруз и три «шапки»
Перед первым сообщением расположены вкладки, контекст-виджеты, шапка с 6 действиями, панель подписчиков, строка поиска и строка фильтров (`ApplicationCommentThread.vue` 232–372, `CandidateDiscussionTabs.vue` 130–253). В `compact`-режиме шторки это съедает заметную часть `max-h-[640px]`. Аналогия: в Хантфлоу форма комментария и лента действий лежат в одном «жёлто-зелёном блоке вакансии» без дополнительных панелей ([Хантфлоу · Комментарии](https://huntflow.ru/help/knowledge-base/comments/)).

### 3.2 Одно действие — три входа
- Снимок скрининга: кнопка над композером, slash `/score`, пункт в меню (ещё и в `DiscussionContextWidgets` ссылка «Подробнее»).
- Перевод по этапу: `InlineStageActions` в шапке и slash `/advance`.
- Вставка текста: шаблоны, умные подсказки, slash `/ai`.
- ИИ-резюме: кнопка в шапке и «обновить» на `AiSummaryCard`.

Каждый вход — отдельный компонент со своим состоянием и i18n (`slash.*`, `smart_suggestions.*`, `comment_snapshot.*`, `templates`).

### 3.3 Баг прав на «внутренний» комментарий
Клиент: `canSeeInternal = ['owner','admin','recruiter'].includes(role)` (`ApplicationCommentThread.vue` 120) → передаётся в `canMarkInternal` → переключатель `v-if="canMarkInternal"` (`ApplicationCommentComposer.vue` 401). Сервер: `INTERNAL_VISIBLE_ROLES = {owner, admin, member, recruiter, lead_recruiter}` с явным комментарием, что рекрутер — это org-роль `member` (`server/utils/comments/visibility.ts`). Следствие: рекрутер с ролью `member` **не видит переключатель** и не может оставить внутреннюю заметку, хотя сервер разрешает. Исправление — общий хелпер в `shared/` для обеих сторон.

### 3.4 Ответы без цитаты
`reply` создаёт `parentCommentId`, но в ленте ответ показывается хронологически с отступом и левой полосой (`ApplicationCommentThread.vue` 425), без текста и автора родителя. Пользователь не понимает, на что ответили. В Телеграме ответ — это цитата над сообщением с переходом по клику.

### 3.5 Тред без пагинации
Клиент грузит `/comments` без параметров (`useApplicationComments.ts` 141–144), сервер отдаёт `limit` по умолчанию 100, максимум 200 (`server/utils/schemas/applicationComment.ts` 20) и `total`, который клиент игнорирует. Тред длиннее 100 сообщений молча обрезается, причём отрезаются **старые** (сортировка по возрастанию), а новые есть — обрыв незаметен. Нужен курсор «вверх» (как в Телеграме — догрузка при прокрутке к началу).

### 3.6 Realtime перегружен рефетчем
SSE-пинг без полезной нагрузки → клиент перезагружает весь тред (`thread-stream.get.ts`, `connectStream`). Для треда на 100 сообщений с mentions/reactions/attachments это 4 запроса к БД на каждое событие у каждого подписчика (`comments/index.get.ts` 50–115). Шина `threadBus.ts`, `typing-store.ts` и rate-limit `@ai` (`index.post.ts` 24–31) — in-memory, не переживут второй инстанс; это отмечено в коде, план есть в `docs/plan-realtime-updates.md`.

### 3.7 Три потока общения на одной странице
На странице отклика друг под другом: «Обсуждение» (внутренняя команда + заказчик), внутри него — импортированные комментарии hh.ru с бейджами и отдельной кнопкой синхронизации, ниже — «Чат с кандидатом» (`CommsChatPanel`). Пользователь должен держать в голове, где он пишет и кто это увидит. Границы нужно сделать очевидными на уровне компоновки, а не бейджей.

### 3.8 Компоновка страницы
Обсуждение — предпоследний блок длинной страницы (`applications/[id].vue` 483), чтобы до него дойти, нужно пролистать резюме, оценки, вопросы и отчёт. В Хантфлоу лента действий и форма комментария — основная рабочая область карточки, при смене этапа «можно одновременно оставить комментарий», и всё попадает в историю работы по вакансии ([Хантфлоу · Смена этапа](https://huntflow.ru/help/knowledge-base/change-status/)).

## 4. Ориентиры: что взять у Хантфлоу и у Телеграма

| | Хантфлоу | Телеграм | Берём |
|---|---|---|---|
| Единица разговора | лента действий по вакансии: комментарии и события вместе, с фильтром ([источник](https://huntflow.ru/help/knowledge-base/comments/)) | чат | лента = сообщения + события, одна прокрутка |
| Главное действие | «Сменить этап подбора» + комментарий одной формой ([источник](https://huntflow.ru/help/knowledge-base/change-status/)) | отправить сообщение | поле ввода с чипом «+ сменить этап»: одна отправка создаёт событие и комментарий |
| Адресация | `@` только рекрутеры и заказчики на вакансии, упоминание нельзя скрыть, уведомление уходит на почту даже при выключенных общих ([источник](https://huntflow.ru/help/knowledge-base/comments/)) | `@`, ответ-цитата | `@` + ответ-цитата; упоминание заказчика во внутренней заметке — предупреждение |
| Закрепление | «Закрепить для себя / для всех», сверху блока ([источник](https://huntflow.ru/help/knowledge-base/comments/)) | полоса закреплённых сверху, переход по тапу ([Telegram](https://telegram.org/blog/pinned-messages-locations-playlists/world?setln=tr)) | оба варианта Хантфлоу + полоса Телеграма сверху ленты; в неё же — контекст «Скрининг · Риск» |
| Новое | индикатор новых событий на кандидате, пропадает при открытии карточки ([Huntflow Media](https://huntflow.media/indikator-novyh-sobytii/)) | непрочитанные, разделитель «новые», галочки | разделитель «Новые сообщения», бейдж на карточке и вкладке |
| Реакции / эмоции | — | реакции по наведению/долгому нажатию | реакции по наведению, без стикеров |
| Поиск | фильтр действий | иконка поиска → строка, перемещение по совпадениям | иконка поиска; фильтры «Внутренние / ИИ / События» внутри строки поиска |
| Форматирование | жирный, курсив, списки, ссылка ([источник](https://huntflow.ru/help/knowledge-base/comments/)) | markdown-подобное, предпросмотр ссылок | markdown как сейчас (`sanitize.ts`), без панели форматирования |
| Отправка | кнопка | Enter, Shift+Enter — перенос | Ctrl+Enter (как сейчас): в рабочем треде перенос строки нужен чаще, чем в мессенджере |

«Нечто среднее» — это **чат-лента Телеграма с одним ATS-действием Хантфлоу в поле ввода**. Остальное не удаляется, а уходит в два меню.

## 5. Продуктовое предложение

### 5.1 Принципы
1. **Один экран, одна прокрутка.** Над лентой — только компактная шапка и полоса закреплённого. Ничего, что раскрывается «само».
2. **Разговор важнее инструментов.** Видимые элементы — те, что нужны в каждом втором сообщении: написать, ответить, отметить, упомянуть, сменить этап, сделать внутренним.
3. **Второй слой — два меню.** «+» слева от поля ввода (что добавить к сообщению) и «⋯» в шапке (как настроить обсуждение). Slash «/» — клавиатурный вход в меню «+», не отдельная система.
4. **Событие и слово — вместе.** Смена этапа, письмо, интервью, снимок ИИ — это записи ленты, а комментарий к ним прикрепляется, а не лежит рядом.
5. **Видимость — одним взглядом.** Внутренние сообщения отличаются фоном и замком на всей группе; при упоминании заказчика во внутреннем сообщении — предупреждение до отправки.
6. **Ничего не ломаем.** API и таблицы остаются; UI переписывается поверх существующих эндпоинтов, новые поля — nullable.

```
├────────────────────────────────────────────────────────────────────────┤
│ [+]  Написать…                                   [⇢ Этап ▾] [🔒] [➤]   │
│      Михаил печатает…                                                    │
└────────────────────────────────────────────────────────────────────────┘
```

1. Шапка: заголовок, переключатель «Другие отклики (N)» (вместо панели вкладок), поиск, меню «⋯».
2. Полоса закреплённого: контекст ИИ (скрининг, риск) + закреплённое сообщение; клик — раскрыть; «устарело» — серый бейдж.
3. Лента: сообщения, события, ИИ-карточки, снимки, опросы — один список, разделители дат и «Новые сообщения».
4. Реакции и действия сообщения — по наведению (ответить, реакция, ⋯: изменить, закрепить, копировать ссылку, удалить).
5. Поле ввода: одна строка с авторостом, отправка по Ctrl+Enter.
6. Чип «Этап ▾»: выбрать этап → отправка создаёт событие + комментарий одной транзакцией. Пустой комментарий при переводе допустим (как сейчас), при возврате из терминального этапа — обязателен (`pipeline-move.ts` 204).
7. Замок «внутренний»: переключатель на поле ввода; при включённом — фон поля меняется, чтобы режим был виден до отправки.

### 5.3 Второй слой

**Меню «+» (слева от поля; «/» открывает его же):** Файл · Шаблон · Прикрепить результат ИИ (скрининг / риск) · Спросить ИИ (`@ai`) · Сводка обсуждения. Опросы — отложены (п. 9.3).

**Меню «⋯» (шапка):** Участники обсуждения (подписчики) · Закреплённые (список «мои» и «общие») · Синхронизировать с hh.ru (если кандидат связан с hh) · Только внутренние / Только события (быстрые фильтры).

**Строка поиска:** текст + чипы-фильтры «Внутренние · ИИ · События · С файлами»; стрелки ↑↓ по совпадениям.

**Другие отклики кандидата:** выпадающий список с этапом, счётчиком и бейджем непрочитанных; выбор открывает ленту другого отклика в режиме чтения с полосой «Просмотр · Frontend · только чтение» вместо розовой подсветки вкладок. Цветовая логика из `tz-collaboration-hub.md` §4.1 остаётся, но применяется к полосе, а не к панели.

### 5.4 Что убираем
- Стикеры (`StickerPicker.vue`, токен `:sticker[]:`, рендер в `ApplicationCommentItem.vue`). Реакции покрывают эмоциональную часть; стикеры в разговоре с заказчиком выглядят неуместно.
- Умные подсказки (`SmartSuggestions.vue`, `useSmartSuggestions.ts`, i18n `smart_suggestions.*`). Заменяются шаблонами в «+» и ИИ-сводкой.
- Создание опросов (пункт меню, `/poll`) — отложено; `PollCard.vue` и `polls/*` остаются, чтобы уже созданные опросы читались.
- Строка фильтров и постоянная строка поиска (переезжают в поиск).
- Панель «Прикрепить результат» над композером (переезжает в «+»).
- Блок «Прочитали» под лентой (`ReadReceipts.vue`) → маленькие аватары у последнего своего сообщения, как «галочки».
- Глобальные горячие клавиши j/k/c на `document`.
- Кнопки «Дальше / Отказ» и выпадашка этапов из шапки (`InlineStageActions`) → чип «Этап» в композере.

### 5.5 Границы с «Чатом с кандидатом»
Решение: **два разных блока, как сейчас**, без общего контейнера и без вкладок «Команда / Кандидат». Причина — риск случайно отправить внутренний комментарий кандидату: переключение вкладок внутри одного блока это риск увеличивает, а раздельные блоки с разным визуальным кодом — снижают. Что меняем в компоновке:
- «Обсуждение» и «Чат с кандидатом» остаются отдельными карточками на странице отклика и в шторке; между ними — отчётливый разрыв и разные заголовки с подписью аудитории: «Обсуждение · видит команда» и «Чат с кандидатом · видит кандидат».
- Разный визуальный код полей ввода: у обсуждения — нейтральный фон и замок, у чата с кандидатом — акцентная рамка и подпись канала (Telegram / e-mail). Одинаковых «➤» рядом быть не должно.
- Никакого переноса данных между блоками: комментарии hh.ru — внутренняя информация и живут только в «Обсуждении» (п. 5.6).

### 5.6 Автодобавление комментариев hh.ru в обсуждение
Цель: при появлении кандидата с hh.ru в системе — через отклик по API или через расширение холодным поиском — комментарии, оставленные на hh, автоматически появляются в «Обсуждении» как записи ленты с именем автора на hh, датой комментария на hh и текстом.

Что уже есть в коде:
- Фоновый импорт `server/utils/hh/commentImport.ts`: очередь pg-boss `hh-comment-import`, singleton на кандидата, постраничная выгрузка `GET /applicant_comments/{applicant_id}` (`server/utils/hh/applicantComments.ts`), дедуп по `hh_comment_id`, запись в `application_comment` с `author_user_id = null`, `hh_author_name`, `hh_direction = 'incoming'`, `hh_synced_at = дата на hh` (миграция `0118_applicant_comments_integration.sql`). Лента сортирует по `COALESCE(hh_synced_at, created_at)` (`comments/index.get.ts` 75), поэтому импортированные комментарии встают на своё место по времени.
- Триггер только один: синхронизация откликов hh (`server/utils/hh/sync.ts` 415–419) — `enqueueCommentImport` вызывается, когда у резюме есть `applicant_id`.
- Ручная кнопка «Синхр. hh» (`server/api/hh/comments/sync.post.ts`, rate-limit 30 с) — требует `application.source === 'hh'`.

Чего не хватает (пробелы):
1. Импорт из расширения (`server/api/extension/import.post.ts`, `source: 'hh-extension'`), захват страницы (`capture-confirm.post.ts`, `extension_capture`) и импорт из сорсинга (`server/api/sourcing-candidates/[id]/import.post.ts`, `source: 'hh_sourcing'`) **не ставят задачу импорта** комментариев.
2. `importApplicantCommentsForCandidate` ищет отклик только с `source = 'hh'` (`commentImport.ts` 39–46) — для холодного поиска задача завершится без результата, даже если её поставить.
3. Ручная синхронизация тоже отвергает отклики не из hh-откликов.

Предложение:
- Вынести общий триггер `enqueueCommentImport(candidateId, orgId)` во все точки появления hh-кандидата: hh-sync (есть), `extension/import.post.ts`, `extension/capture-confirm.post.ts` (если распознан hh-резюме), `sourcing-candidates/[id]/import.post.ts`. Условие — у кандидата есть `hh_applicant_id` или он извлекается из `hh_resume_raw` (`extractApplicantId`).
- В `importApplicantCommentsForCandidate` выбирать целевой отклик по правилу «последний отклик кандидата в организации, у вакансии которого есть связанный hh-аккаунт» (через `resolveHhAccountForJob`), а не по `source = 'hh'`. Если связанного аккаунта нет — брать любой активный hh-аккаунт организации: комментарии на hh привязаны к соискателю, а не к вакансии.
- Снять требование `source === 'hh'` в `hh/comments/sync.post.ts`, проверять наличие `hh_applicant_id`.
- Рендер в ленте: обычное сообщение с аватаром-заглушкой «hh», именем автора из `hh_author_name`, временем из `hh_synced_at` и бейджем «hh.ru · импорт»; группировка по автору как у обычных сообщений; редактирование и удаление запрещены (уже так: `author_user_id = null`). Сообщения всегда внутренние (`is_internal = true` при импорте — сейчас импорт пишет `false`, это нужно поменять, иначе заказчик с ролью `hiring_manager` увидит заметки рекрутёров с hh).
- При импорте в пустой тред — системная запись «Подтянуто N комментариев с hh.ru» одной строкой-пилюлей, чтобы было понятно происхождение.
- Повторная синхронизация: фоновая при открытии ленты с дебаунсом 30 с (вместо кнопки), кнопка — в «⋯» для принудительного запуска.

### 5.7 Закрепление «для себя» и «для всех»
Решение: делаем оба варианта, максимально просто.
- В меню сообщения один пункт «Закрепить ▸» с двумя подпунктами: «Для себя» и «Для всех» (второй — только у ролей, видящих внутренние, то есть у команды). Повторный клик — «Открепить».
- Полоса сверху ленты показывает одно закреплённое: приоритет у «моего», если его нет — общее. Если закреплённых несколько, клик по полосе листает их по кругу (как в Телеграме), в «⋯ → Закреплённые» — полный список двумя группами.
- Общее закрепление видят все, кому виден сам комментарий (внутренний общий пин заказчик не увидит — логика `visibility.ts` применяется и к пинам).
- Данные: общий пин — уже есть (`is_pinned`, `pinned_by_id`, `pinned_at`); личный — новая таблица `comment_pin_personal (user_id, comment_id, application_id, created_at)` с уникальным ключом `(user_id, comment_id)`. API: `POST /comments/:id/pin` получает `scope: 'me' | 'all'`.

## 6. Архитектурное предложение

### 6.1 Фронтенд

Разбить `ApplicationCommentThread.vue` (516 строк, 12 ответственностей) на слои с одним источником состояния:

```
app/components/discussion/
  DiscussionPanel.vue         шапка + полоса закреплённого + лента + композер; пропсы applicationId, candidateId, compact
  DiscussionHeader.vue        заголовок, «Другие отклики», поиск, меню «⋯»
  DiscussionPinnedBar.vue     контекст ИИ + закреплённое сообщение
  DiscussionFeed.vue          виртуализированная лента (группы, разделители дат/новых, догрузка вверх)
  feed/MessageGroup.vue       аватар + имя + время один раз на группу
  feed/MessageBubble.vue      текст, цитата ответа, вложения, реакции по наведению, меню
  feed/EventRow.vue           смена этапа, письмо, интервью, hh — центрированная строка-пилюля с прикреплённым комментарием
  feed/AiCard.vue             ai_summary, ai_response, снимки (один компонент с вариантами по kind)
  feed/PollCard.vue           как сейчас
  DiscussionComposer.vue      поле + «+» + «Этап» + замок + отправка; @-автодополнение; «/» → меню «+»
  composer/PlusMenu.vue       файл, шаблон, опрос, снимок, @ai, сводка
  composer/StagePicker.vue    выбор этапа (данные из useApplicationStages)
app/composables/useDiscussion.ts   единый стор на applicationId
```

`useDiscussion(applicationId)` заменяет `useApplicationComments` + `useThreadFilter` + `useThreadScroll` + `useUnreadComments` в части треда: элементы ленты (`items: FeedItem[]` с `kind`), курсор назад, `lastReadAt`, оптимистичные вставки, применение SSE-патчей без полного рефетча, кэш на модуль (как сейчас — один экземпляр на `applicationId`, `useApplicationComments.ts` 127–135).

Удаляются: `SlashCommandPalette` (логика команд → `PlusMenu` с клавиатурным открытием), `SmartSuggestions`, `StickerPicker`, `InlineStageActions`, `ReadReceipts`, `DiscussionContextWidgets` (сворачивается в `DiscussionPinnedBar`), `CandidateDiscussionTabs` (в `DiscussionHeader`). `TemplatePicker`, `WatcherPanel`, `PollCard`, `AttachmentPreview`, `CommentReactions`, `ApplicationMentionAutocomplete` переиспользуются.

### 6.2 Бэкенд

1. **Единая лента на сервере.** `GET /api/applications/:id/feed?before=<cursor>&limit=50` отдаёт элементы `{ kind: 'comment' | 'stage_event' | 'ai' | 'poll' | 'system', at, id, payload }`, собранные из `application_comment` и `application_stage_history` (а дальше — письма и интервью), отсортированные по `(at, id)` с курсором назад. Сейчас слияние на клиенте (`useApplicationComments.ts` 355–362) и два запроса; пагинации нет (п. 3.5). Старый `GET /comments` остаётся для совместимости.
2. **Комментарий + этап одной транзакцией.** `POST /comments` принимает `moveToStageId?`: внутри транзакции `moveApplicationStage({ comment })` и запись комментария с `kind='stage_comment'`, `payload_json: { fromStageId, toStageId, historyId }`. В ленте такая запись рендерится как событие с текстом. Валидации переводов (терминальные этапы, обязательный комментарий) уже в `pipeline-move.ts`.
3. **SSE с полезной нагрузкой.** `thread-stream` шлёт `{ type: 'comment.created' | 'comment.updated' | 'comment.deleted' | 'reaction' | 'stage_event' | 'typing', item }`, клиент применяет патч; полный рефетч — только при `resync`. Шина `threadBus` → адаптер с PG `LISTEN/NOTIFY` по плану `docs/plan-realtime-updates.md`; `typing-store` и rate-limit `@ai` → тот же канал или таблица без журнала (`UNLOGGED`), чтобы работать на нескольких инстансах.
4. **Права в одном месте.** `canSeeInternal(role)` переносится в `shared/access/` и используется сервером (`visibility.ts`) и клиентом (замок в композере) — закрывает баг п. 3.3. Там же — правило «упоминание заказчика во внутреннем сообщении → предупреждение» (сервер: мягкий `warning` в ответе, клиент: подтверждение).
5. **Прочитанность.** `thread_read_state` уже есть; `POST /read` вызывать при достижении низа ленты (а не при монтировании), чтобы разделитель «Новые сообщения» показывался честно. `GET /readers` — только для последнего своего сообщения.
6. **hh.ru.** Импорт комментариев — фоновой задачей при появлении кандидата и при открытии ленты (дебаунс 30 с), кнопка — в «⋯» как принудительный запуск; результат — бейдж в «⋯».
7. **Закрепление.** Два уровня: общий (`is_pinned`, `pinned_by_id`, `pinned_at` — есть) и личный (`comment_pin_personal`), см. п. 5.7. Полоса сверху берёт сначала личный, затем общий.
8. **Автоимпорт комментариев hh.ru** во всех точках появления hh-кандидата и выбор отклика без требования `source = 'hh'`, импорт как внутренние сообщения — см. п. 5.6.

### 6.3 Данные
Одна новая таблица `comment_pin_personal` (личные закрепления, п. 5.7). Изменения: `application_comment.kind` получает значение `'stage_comment'` (поле уже text, nullable); импорт hh пишет `is_internal = true`; при желании — индекс `(application_id, created_at DESC, id)` для курсора. Миграция аддитивная.

## 7. UX/UI-детали

### 7.1 Компоновка по поверхностям
- **Страница отклика.** Одноколоночная структура сохраняется; «Обсуждение» и «Чат с кандидатом» — две отдельные карточки, как сейчас, но с подписью аудитории в заголовке и разным визуальным кодом полей ввода (п. 5.5). Чтобы до обсуждения не нужно было листать всю страницу, предлагается кнопка-якорь «К обсуждению · N новых» в шапке карточки отклика (sticky), которая прокручивает к блоку.
- **Шторка в воронке.** Тот же `DiscussionPanel compact`: шапка в одну строку, полоса закреплённого сворачивается в бейдж, поле ввода одной строкой; «Чат с кандидатом» — ниже отдельной карточкой, как сейчас.
- **Страница вакансии.** Только лента последнего отклика с кнопкой «Открыть карточку».

### 7.2 Визуальная система ленты
- Все сообщения слева с аватаром (групповой чат, а не диалог); свои — лёгкий брендовый фон, как сейчас (`isSelf`-тон). Выравнивать свои вправо не нужно: в рабочем треде важнее имя автора.
- Внутренние: фон `warning-50/10` на всей группе + замок у имени; бейдж «видит заказчик» не нужен — обычный вид и есть «видимый».
- События — центрированная пилюля `⟶ Ольга перевела на «Тех. интервью»`, под ней комментарий обычным текстом с отступом.
- ИИ — акцентный (`accent-*`) бордер и иконка ✦, карточки сворачиваются до 3 строк.
- hh.ru — маленький бейдж «hh» у имени автора, без отдельного аватара.
- Ответ — цитата: тонкая полоса слева, автор и 1 строка текста, клик прокручивает к оригиналу и подсвечивает (механика `highlightedCommentId` уже есть).
- Разделители: дата по центру; «Новые сообщения» — тонкая линия с подписью, появляется по `lastReadAt`.
- Непрочитанные: бейдж на вкладке «Команда», на пункте «Другие отклики» и на карточке в воронке (индикатор Хантфлоу).

### 7.3 Поле ввода
- Одна строка с авторостом до 6 строк; плейсхолдер «Написать команде…» / «Внутренняя заметка…» при замке.
- Слева «+» (меню), справа «Этап ▾» (чип становится «→ Тех. интервью» после выбора, с крестиком), замок, «➤».
- Ctrl/Cmd+Enter — отправить (как сейчас), Enter — перенос строки; `↑` в пустом поле — редактировать своё последнее сообщение (Телеграм); Esc — отмена ответа/редактирования. Подсказка «Ctrl+Enter» — серым в углу поля, а не отдельной строкой.
- Черновик в `localStorage` (есть) + сохранение выбранного этапа и замка в черновике.
- Вложения — через «+» и перетаскиванием (есть).

### 7.4 Пустое состояние
«Обсуждения ещё нет. Напишите первое сообщение или переведите кандидата на этап — это тоже появится здесь». Без 6 чипов подсказок.

## 9. Решения по открытым вопросам (07.10.2026)

1. **Отправка** — остаётся Ctrl+Enter, Enter — перенос строки. Настройка не нужна.
2. **Закрепление** — делаем оба варианта, «для себя» и «для всех», одним пунктом меню с подвыбором; полоса сверху, приоритет у личного (п. 5.7).
3. **Опросы** — отложены: пункт меню и `/poll` убираем, API и `PollCard` оставляем для уже созданных.
4. **Комментарии hh.ru** — только в «Обсуждении», переносить в «Чат с кандидатом» нельзя (внутренняя информация). Автоимпорт при появлении кандидата через отклик по API и через расширение холодным поиском: имя автора на hh, дата комментария на hh, текст (п. 5.6). Сейчас триггер есть только у hh-откликов — это пробел, закрываем на этапе 3.
5. **Компоновка** — две колонки и общий блок «Коммуникации» не делаем; «Обсуждение» и «Чат с кандидатом» остаются разными блоками, усиливаем их визуальное различие (п. 5.5, 7.1).

Следующий шаг — ТЗ на этапы 0–1 (быстрые починки и новая оболочка) и HTML-прототип целевого вида, затем реализация.
