# ТЗ · «Карта поиска 2.0» — документ-вид, гипотезы с фактами, решения с HM, экономная генерация

**Репозиторий:** `VadShv/ats-huntfork` · **База:** main после PR #14 и #15 · **Предыдущее ТЗ:** `docs/tz-search-map.md` (v1, модель данных и глобальный модуль — действуют, здесь только доработки)
**Дата:** 2026-10-06 (ред. 2 — добавлены R0 «контекст генерации» и §3.6 «точечное дополнение блоков») · **Статус:** на согласование

## 0. Резюме для чтения за две минуты

Карта поиска v1 работает как редактор: секции, доноры, сегменты, версии, PDF. Проверка показала три проблемы продукта (не бага):

1. **На экране меньше, чем в PDF.** Сводка (`job_search_map.summary`) вообще не отображается; у сегментов не видно тайтлов, гео и строк запросов. Рекрутёр читает карту в PDF, а не в системе.
2. **Карта ничего не знает о результатах.** hh-поиски привязаны к сегменту, но ни пул, ни касания, ни ответы, ни этапы кандидатов в карту не попадают. Статус гипотезы — ручной клик без данных. Поэтому непонятно, какие решения принимать.
3. **Карта не меняет бриф.** Нет места, где фиксируется «что мы поняли о рынке и о чём договорились с нанимающим менеджером». Версии есть, но причина версии не связана с решением.

Плюс генерация: три вызова с полным контекстом в каждом, самая дорогая модель для всего, токены не учитываются. И найден баг контекста: **бриф почти не попадает в промпт** — `buildGeneratePrompt.ts` читает поля, которых нет в `job_brief` (совпадает только `niceToHave`), описание режется до 2000 символов, существующие гипотезы модели не показываются. «Дополнить по брифу» сегодня работает по названию, критериям и половине описания.

**Что делаем (хотфикс + четыре релиза, каждый самостоятельно полезен):**

| Релиз | Суть | Миграция | Оценка |
|---|---|---|---|
| **R0 · Контекст** | Хотфикс: правильный маппинг брифа, полное описание, существующие гипотезы в промпте, `sourcingHints`/`idealProfile` для гипотез | нет | 1 день |
| **R1 · Документ** | Сводка на экране, режим «Документ» = тот же шаблон, что и PDF, гипотезы вместо «сегментов» с полной информацией в строке, кнопки «Дополнить» по блокам с подсказкой | нет | 4–5 дней |
| **R2 · Факты** | Метрики гипотезы из hh-поисков, трекинг-ссылок и этапов воронки; подсказки по статусу; еженедельная ревизия | 1 колонка | 5–6 дней |
| **R3 · Решения** | Сущность «решение для калибровки»: вопрос → доказательства из гипотез → ответ HM → версия карты | 1 таблица | 4–5 дней |
| **R4 · Экономия** | Учёт токенов, маршрутизация моделей, строки запросов кодом, компактный профиль вакансии с кэшем, частичная регенерация | 1 таблица | 4–5 дней |

**Чего не делаем сейчас (§12):** пресеты семейств ролей с содержимым, few-shot из своих карт, обучение доноров на найме, эмбеддинги, A/B промптов, варианты запросов, карта на роль, вид для руководителя подбора. Это следующий этап — после того как увидим реальные траты и реальные данные по гипотезам.

## 2. Ground truth — на что опираемся

Уже есть и используется:

- `job_search_map.summary` — заполняется генерацией (`generate.post.ts`, scope `summary`/`section`), редактируется через `PATCH /api/jobs/[id]/search-map`; **на странице не выводится**.
- `job_search_map_segment`: `titles[]`, `keywords[]`, `geo[]`, `channelId`, `queryString`, `queryUrl`, `priority`, `poolEstimate`, `responseLikelihood`, `accessDifficulty` (оценки 1–3 уже в схеме), `hypothesisStatus`, `rationale`, `resultNote`, `origin`.
- `hh_saved_search.searchMapSegmentId` (nullable) и `hh_saved_search.lastRunFound` — **фактический размер пула по hh уже сохраняется**, в карту не попадает.
- `hh_sourcing_candidate`: `savedSearchId`, `state` ∈ `new | reviewed | approved | imported | rejected | contacted`, `score`, `scoreGaps`, `applicationId`.
- `application_stage_history` + `pipeline_stage.type` ∈ `new | screening | interview | offer | hired | rejected`.
- `tracking_link` (`jobId`, `channel`, `clickCount`, `applicationCount`) и `application_source.trackingLinkId` — трекинг для не-hh каналов есть, к карте не привязан.
- `sourcing_channel.urlTemplate`, `targetSite`, `queryLanguageHint` — заготовка под шаблоны запросов.
- `ai_config`: четыре назначения — `chatbot | analysis | interactive | structuring`; карта использует только `analysis`.
- `analysis_run.promptTokens/completionTokens` — образец учёта токенов.
- `exportPdf.ts` / `exportMarkdown.ts` — шаблон документа, который нравится пользователю.
- hh-сорсинг (`jobs/[id]/sourcing.vue`, `server/utils/hh/*`) — **не трогаем** (решение v1 остаётся в силе).
- `POST /generate` уже принимает `scope ∈ full | section | donors | segments | summary | query_string`, `mode ∈ append | fill_empty | replace`, `hint`; UI вызывает только `scope: 'full', mode: 'append'` (`search-map.vue:81`).
- `buildGeneratePrompt.ts` передаёт модели: название, бриф (с неверным маппингом — см. R0), критерии (`name/category/weight`), `description.slice(0, 2000)`, существующие секции и доноров, активные каналы, `hint`. Существующие **гипотезы не передаются** — дедуп только по точному имени в `generate.post.ts:279–282`.

## 2a. R0 · Контекст генерации (хотфикс, до всего остального)

### 2a.1. Проблема
`buildGeneratePrompt.ts:50–59` ожидает `brief.roleProfile / seniority / format / location / salaryFrom / salaryTo / mustHave / niceToHave`. Схема `job_brief` (`server/database/schema/app.ts`): `hardMustHave jsonb`, `niceToHave jsonb`, `dealBreakers jsonb`, `redFlagsToWatch jsonb`, `responsibilities`, `teamContext`, `interviewProcess`, `compensationNotes`, `idealProfile`, `sourcingHints`, `freeform` (text). Совпадает одно поле. Must-have, deal-breakers, идеальный профиль и подсказки по сорсингу до модели не доходят.

### 2a.2. Маппинг брифа → промпт
`buildBriefContext(brief)` в `buildGeneratePrompt.ts` (чистая функция, покрыта unit-тестом):

| Поле `job_brief` | Строка в промпте | Кому обязательно |
|---|---|---|
| `hardMustHave` (jsonb: массив строк или объектов `{text}`) | `Must have (обязательно):` список | все части |
| `niceToHave` | `Nice to have:` список | секции, гипотезы |
| `dealBreakers` | `Не рассматриваем (deal-breakers):` список | секции (`exclusions`), гипотезы |
| `redFlagsToWatch` | `Красные флаги:` список | секции (`notes`) |
| `idealProfile` | `Идеальный профиль:` текст | доноры, гипотезы |
| `sourcingHints` | `Подсказки по поиску от HM/рекрутёра:` текст | **гипотезы — в отдельном блоке в конце промпта, с указанием «учти в первую очередь»** |
| `responsibilities` | `Обязанности:` текст ≤ 1500 символов | секции |
| `teamContext` | `Команда и контекст:` текст ≤ 800 символов | доноры (откуда похожие команды) |
| `compensationNotes` | `Компенсация:` текст | вердикт (реалистичность) |
| `freeform` | `Прочее из брифа:` текст ≤ 1000 символов | все части |
| `interviewProcess` | не передаём | — |

jsonb-массивы нормализуются: строка → как есть, объект → `text ?? value ?? label`, пустые отбрасываются. Если бриф пуст целиком — строка `Бриф не заполнен — опирайся на описание и критерии`.

### 2a.3. Описание вакансии
- Лимит `slice(0, 2000)` → **6000 символов**; если длиннее — первые 4000 + последние 2000 (требования обычно в конце), с пометкой `[… пропущено N символов …]`.
- HTML-теги вычищаются (`description` на hh-вакансиях часто приходит с разметкой): `stripHtml` → схлопывание пробелов.
- После R4 §6.4 описание в сырых частях заменяется компактным профилем; до этого — как здесь.

### 2a.4. Существующие гипотезы в промпте
В `promptBase` добавляется `existingSegments: { name, donorLayer, channelCode, titles: string[] }[]` (не архивные). В промпт части `segments`: `Уже есть гипотезы (не повторяй их по смыслу, предлагай другие слои/каналы/тайтлы):` компактным списком `— {name} · {layer} · {channel} · {titles[0..3]}`. Дедуп на сервере дополняется семантическим ключом `normalize(donorLayer + channelCode + sorted(titles).join())` помимо точного имени.

### 2a.5. Инструкция части «гипотезы»
В `scopeInstructions.segments` добавить: «Строй гипотезы из трёх источников: (1) must-have и идеальный профиль из брифа — где такие люди работают сейчас; (2) требования из описания — какие формулировки тайтлов и навыков они используют у себя в резюме; (3) подсказки по поиску — обязательны к использованию. Для каждой гипотезы в `rationale` укажи, из какого источника она выведена». `queryString` остаётся в схеме до R4 §6.3, после — убирается.

### 2a.6. Приёмка R0
- Unit: `buildBriefContext` на фикстуре с заполненным брифом содержит все must-have и `sourcingHints`; на пустом — fallback-строку.
- Лог `[search-map:generate]` печатает длину промпта по частям; на тестовой вакансии с брифом длина части `segments` выросла и содержит блок «Подсказки по поиску».
- Повторное «Дополнить» на карте с 5 гипотезами не создаёт гипотез с тем же слоем+каналом+тайтлами.

## 3. R1 · Документ-вид и сводка

### 3.1. Цель
То, что рекрутёр видит в PDF, он видит на вкладке карты без экспорта. Один шаблон для экрана, печати и PDF.

### 3.2. Компонент `SearchMapDocumentView.vue`
Новый компонент `app/components/searchMap/SearchMapDocumentView.vue`, props: `snapshot: SearchMapSnapshot` (тот же формат, что в версиях, §5.4 v1) + `jobTitle`, `versionLabel`, `metrics?` (R2), `decisions?` (R3). Рендерит документ в порядке:

1. **Вердикт по рынку** — `summary` абзацем; под ним строка фактов: число гипотез по статусам, число доноров, дата последней генерации, модель.
2. **Кого ищем** — секции карты (`title_synonyms`, `keywords`, `geo`, `exclusions`, `notes`): значение + `note` серым рядом. Пустые необязательные секции не показываются.
3. **Откуда берём** — доноры по слоям (ядро / смежные / школы / alumni / свои); у каждого приоритет, статус, `rationale`, `resultNote`.
4. **Гипотезы поиска** — таблица: название · слой · тайтлы · гео · канал · приоритет · оценки пул/отклик/доступ · статус · факты (R2) · строка запроса (моноширинная, с кнопкой «копировать» и ссылкой «открыть в канале», если есть `queryUrl`).
5. **Решения** (R3) — карточки.
6. **Версии** — список с `diffSummary` и `comment`.

`server/utils/searchMap/exportPdf.ts` переписывается на рендер **того же HTML** (общая функция `renderDocumentHtml(snapshot, ...)` в `shared/searchMap/renderDocument.ts`, без Vue-зависимостей; компонент Vue оборачивает её либо дублирует разметку по той же спецификации — выбрать при реализации, критерий: расхождений между экраном и PDF быть не должно).

### 3.3. Страница `jobs/[id]/search-map.vue`
- Переключатель в шапке: **Документ | Редактор** (`UiTabs` или сегмент-контрол), запоминается в `localStorage` на пользователя; по умолчанию «Документ».
- Блок **«Вердикт по рынку»** виден в обоих режимах над содержимым: текст `summary`; в редакторе — клик по тексту открывает `UiTextarea`, сохранение через `PATCH` (debounce 800 мс); кнопка «Обновить вердикт» → `POST /generate` со `scope: 'summary'`, `mode: 'replace'`. Пустой `summary` → placeholder «Вердикт появится после генерации или напишите сами».
- В режиме «Документ» кнопки действий остаются в шапке (Дополнить по брифу, Сохранить версию, История, Экспорт). Клик по строке гипотезы или карточке донора в документе открывает соответствующий drawer (как в редакторе) — документ не read-only, но без inline-редактирования.
- `Экспорт → PDF` и `Печать` вызывают один и тот же шаблон; добавить `@media print` стили.

### 3.4. Таблица гипотез (`SearchMapSegmentTable.vue`)
Колонки: Гипотеза (название + вторая строка: тайтлы · гео) · Канал · Приоритет · Оценка (три мини-шкалы 1–3 из `poolEstimate / responseLikelihood / accessDifficulty`) · Факты (R2; до R2 — число hh-поисков) · Статус · Действия (иконки: копировать запрос, открыть в канале, «hh-поиски (n)» как ссылка на вкладку сорсинга с фильтром по `searchMapSegmentId`). Клик по строке → `SegmentDrawer` (как сейчас). Сортировка по умолчанию: приоритет ↓, затем статус (`working`, `in_progress`, `untested`, `rejected`). Архивные скрыты за переключателем.

### 3.5. Точечное дополнение блоков
Принцип: ИИ **дополняет**, а не перегенерирует. Перегенерация с заменой стирает правки рекрутёра и статусы гипотез, поэтому её в этом этапе нет (возможна позже только через контракт «предложения → принять», как у решений в R3).

| Где | Кнопка | Вызов | Что передаётся дополнительно |
|---|---|---|---|
| Шапка карты | «Дополнить по брифу» (как сейчас) | `scope: 'full'`, `mode: 'append'` | — |
| Блок «Вердикт» | «Обновить вердикт» | `scope: 'summary'`, `mode: 'replace'` | единственное место с заменой — вердикт не содержит ручных правок, которые жалко; текущий текст показывается в диффе «было/стало» перед сохранением |
| Блок «Кого ищем» | «Дополнить» + поле подсказки | `scope: 'section'`, `mode: 'append'`, `hint` | существующие пункты (уже есть) |
| Блок «Доноры» | «Предложить доноров» + подсказка | `scope: 'donors'`, `mode: 'append'`, `hint` | существующие доноры (уже есть) |
| Блок «Гипотезы» | «Предложить гипотезы» + подсказка | `scope: 'segments'`, `mode: 'append'`, `hint` | существующие гипотезы (R0 §2a.4) |
| Drawer гипотезы | «Ещё похожие» | `scope: 'segments'`, `mode: 'append'`, `hint = "похожие на: {name}; слой {layer}; канал {channel}; тайтлы …"`, `limit: 3` | та же часть, другой hint — новых эндпоинтов нет |
| Drawer гипотезы | «Собрать запрос» | **без ИИ** — `buildQueryString` (R4 §6.3; до R4 — текущая кнопка «Собрать») | — |
| Drawer гипотезы | «Переписать запрос с ИИ» + обязательная подсказка | `scope: 'query_string'`, `segmentId`, `hint` | единственный ИИ-путь для запроса: только одна гипотеза, только по явной подсказке («под LinkedIn x-ray», «добавь синонимы на английском»); результат показывается «было/стало», сохраняется по кнопке |

Поле подсказки — однострочный `UiInput` с placeholder («например: добавь гипотезы через Telegram-сообщества») рядом с кнопкой; пустое — допустимо. В `generateInputSchema` добавить `limit?: number (1–10)` и `segmentId?: string` (для `query_string`); `scope: 'query_string'` без `segmentId` — 400. Все ИИ-пункты помечаются `origin: ai`; принятие = оставить, отклонение = удалить (как сейчас).

Ограничение (R4 §6.6 действует и здесь): не более 10 запусков на карту в сутки суммарно по всем кнопкам; счётчик показывается в tooltip кнопок.

### 3.6. Приёмка R1
- Открыть карту с заполненным `summary` — текст виден без экспорта; изменение в редакторе сохраняется и отражается в PDF.
- Переключение Документ/Редактор без перезагрузки; выбор запоминается.
- PDF и экран содержат одинаковый набор блоков и значений (ручная сверка на двух картах).
- В строке гипотезы видны тайтлы, гео, запрос; копирование работает; «открыть в канале» открывает `queryUrl` в новой вкладке.
- «Предложить гипотезы» с подсказкой «через Telegram» добавляет только гипотезы с каналом `telegram`, существующие не меняются; «Ещё похожие» из drawer добавляет ≤ 3 гипотез того же слоя; «Переписать запрос с ИИ» без подсказки заблокирована, с подсказкой показывает «было/стало» и не сохраняет без подтверждения.

## 4. R2 · Факты из воронки в гипотезы

### 4.1. Цель
Статус гипотезы опирается на цифры. Рекрутёр видит по каждой гипотезе: сколько профилей в пуле, сколько касаний, сколько ответов, сколько дошло до скрининга и до HM — и получает подсказку, что с гипотезой делать.

### 4.2. Модель данных
Одна миграция `0123_search_map_v2_facts.sql`:
```sql
ALTER TABLE tracking_link ADD COLUMN search_map_segment_id text
  REFERENCES job_search_map_segment(id) ON DELETE SET NULL;
CREATE INDEX tracking_link_search_map_segment_idx ON tracking_link(search_map_segment_id);
```
Никаких таблиц метрик: считаем на лету по индексам, объём на одну вакансию мал.

### 4.3. `SegmentMetrics` — `server/utils/searchMap/computeSegmentMetrics.ts`
Вход: `mapId`. Выход: `Record<segmentId, SegmentMetrics>`:

| Поле | Источник | Правило |
|---|---|---|
| `poolActual` | `hh_saved_search.lastRunFound` | сумма по поискам сегмента (не архивным); `null`, если поисков нет |
| `touched` | `hh_sourcing_candidate` по `savedSearchId` ∈ поиски сегмента; + `tracking_link.clickCount` | число уникальных `hhResumeId` + клики по ссылкам |
| `contacted` | `hh_sourcing_candidate.state ∈ {contacted, imported}` | количество |
| `responded` | `hh_sourcing_candidate.applicationId IS NOT NULL` + `application_source.trackingLinkId` ∈ ссылки сегмента | число заявок, возникших из гипотезы |
| `screening` | `application_stage_history` для этих заявок: достигнут `pipeline_stage.type ∈ {screening, interview, offer, hired}` | количество заявок |
| `hm` | достигнут `type ∈ {interview, offer, hired}` | количество |
| `hired` | `type = hired` | количество |
| `rejectedGaps` | `hh_sourcing_candidate.scoreGaps` у `state = rejected` | топ-3 повторяющихся формулировок (нормализация: lower/trim), для подсказки минус-слов |
| `lastActivityAt` | max(`lastSeenAt`, `movedAt`, `clickCount` обновление) | дата |
| `daysSinceStart` | `segment.statusChangedAt` для `in_progress` или `createdAt` | дни |

Выдаётся в `GET /api/jobs/[id]/search-map` полем `metrics` (по умолчанию включено; `?metrics=0` отключает для лёгких запросов). Кэш не нужен; при росте — `unstorage` на 60 с.

### 4.4. Подсказки по статусу (детерминированно, без LLM)
`suggestStatus(segment, metrics)` в том же файле, возвращает `{ suggestion: 'mark_working' | 'mark_rejected' | 'start' | 'add_exclusions' | null, reason: string }`:

- `untested` и `poolActual > 0` → `start` «Пул N резюме, гипотеза не запускалась».
- `in_progress`, `touched ≥ 20`, `responded = 0`, `daysSinceStart ≥ 10` → `mark_rejected` «N касаний, 0 ответов за M дней».
- `in_progress` или `untested`, `screening ≥ 2` или `hm ≥ 1` → `mark_working`.
- `rejectedGaps` содержит формулировку ≥ 3 раз → `add_exclusions` «K отказов: “нет консолидации” — добавить исключение?».
Подсказка показывается в строке таблицы и в drawer кнопкой «Принять»; принятие = обычный `PATCH` статуса. Статус **никогда** не меняется автоматически.

### 4.5. Привязка не-hh каналов
В `SegmentDrawer` для каналов с `code ≠ 'hh'` кнопка **«Создать трекинг-ссылку»** → существующий API трекинг-ссылок с `jobId`, `channel = channel.code`, `name = segment.name`, `searchMapSegmentId`. Ссылка показывается в drawer с кнопкой копирования. Вкладка трекинга вакансии получает колонку «Гипотеза».

### 4.6. Еженедельная ревизия
Cron (существующий механизм задач Nitro) раз в неделю (пн 09:00 по TZ организации) на активные карты: для каждой считает `suggestStatus` по всем гипотезам, и если есть хотя бы одна подсказка или карта `stale` — одно уведомление владельцу вакансии через существующий `notification`: «Карта поиска “Менеджер МСФО”: 2 гипотезы без движения, 1 готова к запуску, бриф изменился». Ссылка на вкладку. Без email в этом релизе.

### 4.7. UI
- Таблица гипотез: колонка «Факты» — компактная воронка `пул · касания · ответы · скрининг · HM` цифрами, подсказка иконкой с tooltip и кнопкой «Принять».
- Drawer гипотезы: блок «Факты» с теми же цифрами крупно, `rejectedGaps` списком с кнопкой «Добавить в исключения» (создаёт item в секции `exclusions` и дописывает `NOT "…"` в `queryString`, если канал поддерживает boolean — определяется по `sourcing_channel.queryLanguageHint`).
- Документ-вид (R1) выводит `poolActual` и воронку в таблице гипотез.
- Панель статистики (`SearchMapStatsPanel`) дополняется: «гипотез с фактами: N из M», «ответов всего», «лучшая гипотеза по ответам».

### 4.8. Приёмка R2
- Для гипотезы с привязанным hh-поиском после запуска поиска `poolActual` = `lastRunFound`; после импорта кандидата `contacted` растёт; после перевода заявки на этап типа `screening` растёт `screening`.
- Трекинг-ссылка из drawer создаётся с `searchMapSegmentId`; переход и заявка увеличивают `touched`/`responded`.
- Подсказки появляются по правилам §4.4; принятие меняет статус; автоматических изменений нет.
- Уведомление ревизии приходит один раз в неделю и только при наличии причин.

## 5. R3 · Решения для калибровки с HM

### 5.1. Цель
Зафиксировать, что карта говорит о реалистичности брифа, и превратить это в решение HM с датой, ответом и следствием (новая версия карты, правка брифа).

### 5.2. Модель данных
Миграция `0124_search_map_decisions.sql`, таблица `job_search_map_decision`:

| Поле | Тип | Назначение |
|---|---|---|
| `id`, `organization_id`, `map_id` | text | стандартно, FK с cascade |
| `title` | text NOT NULL | вопрос решения («Расширяем воронку до финконтролёров без опыта консолидации?») |
| `priority` | enum `decision_priority`: `p0 | p1 | p2` | p0 — блокирует поиск |
| `status` | enum `decision_status`: `open | accepted | declined | deferred` | |
| `evidence` | jsonb `{ segmentIds: string[], donorIds: string[], criterionIds: string[], facts: string[] }` | ссылки на гипотезы/доноров/критерии + текстовые факты (снимок на момент создания) |
| `options` | jsonb `{ label: string; isChosen: boolean }[]` | варианты ответа (2–4) |
| `resolution` | text | формулировка принятого решения |
| `affects` | jsonb `{ brief: boolean, criteria: boolean, sections: ('title_synonyms'|'keywords'|'geo'|'exclusions')[] }` | что меняет |
| `owner_role` | enum `decision_owner`: `hm | recruiter | hrbp` | кто решает |
| `due_at`, `resolved_at`, `resolved_by_id` | timestamp / text | |
| `origin` | существующий enum `search_map_origin`: `manual | ai` | |
| `resulting_version_no` | integer | номер версии карты, зафиксировавшей решение |
| `created_by_id`, `created_at`, `updated_at` | | |

RBAC: чтение — `search_map.read`; создание/правка — `search_map.write`; **смена статуса на `accepted/declined`** — `search_map.write` или роль HM на вакансии (HM получает в карте только это действие).

### 5.3. API — `server/api/jobs/[id]/search-map/decisions/`
- `GET /` — список (с фильтром `status`).
- `POST /` — создать (Zod `decisionInputSchema`).
- `PATCH /[decisionId]` — поля и статус. При переходе в `accepted`/`declined`: записать `resolved_*`, и если `affects.brief || affects.criteria || affects.sections.length` — автоматически создать версию карты с `trigger: 'calibration'` (enum уже есть) и `comment = resolution`, записать `resulting_version_no`.
- `DELETE /[decisionId]` — только `open`.
- `POST /suggest` — ИИ-предложение решений (§5.5), возвращает **черновики без сохранения**; сохранение — отдельным `POST /` по каждому выбранному. Это тот самый контракт «предложения → принять», которого не хватало генерации в v1; для решений он обязателен, потому что решение — это обязательство.

### 5.4. Детерминированные кандидаты в решения (без LLM)
`detectDecisionCandidates(map, metrics, criteria)` предлагает карточки-черновики, когда:
- все гипотезы приоритета `high` имеют `responded = 0` при `touched ≥ 30` суммарно → «Ядро не отвечает: расширяем слой / меняем условия?»;
- `poolActual` по всем hh-гипотезам < 50 → «Пул узкий: смягчаем must-критерий?» (в evidence — критерии категории must из `scoring_criterion`);
- в `rejectedGaps` одна формулировка ≥ 5 раз по карте → «Критерий “…” режет воронку: обязательный или плюс?»;
- гео-секция без `remote`/релокации, а `poolActual` по Москве < 30 → «Рассматриваем регионы?».
Эти правила дешёвые и объяснимые; ИИ (§5.5) формулирует их человеческим языком и добавляет варианты.

### 5.5. ИИ-предложение решений
Один вызов модели `structuring` (не `analysis`): вход — компактный профиль вакансии (R4 §6.4), сводка метрик по гипотезам (числа), список кандидатов из §5.4. Выход — до 4 черновиков `{ title, priority, options[], facts[], affects }`. Нормализация enum'ов как в `normalizeAiVocab.ts`. Ограничение: не чаще раза в час на карту.

### 5.6. UI
- Блок **«Решения для калибровки»** на вкладке карты (документ и редактор): карточки `P0/P1/P2 · статус · срок`, заголовок, факты (с ссылками на гипотезы — клик открывает drawer), варианты как кнопки-чипы (для роли HM кликабельны и фиксируют решение), «Влияет на: …», владелец.
- Кнопки: «+ Решение», «Предложить решения» (ИИ-черновики в модалке с чекбоксами «добавить»), «Повестка калибровки» — экспорт только открытых решений в Markdown/PDF (тот же шаблон документа, фильтр).
- Принятое решение показывает «зафиксировано в v{N}» со ссылкой на версию.
- История версий: у версий с `trigger: calibration` отображается связанное решение.

### 5.7. Приёмка R3
- Создание решения вручную и из ИИ-черновика; HM на вакансии видит карту (read) и может выбрать вариант; при `accepted` с `affects` создаётся версия `calibration` с комментарием.
- Правила §5.4 срабатывают на тестовых данных; без данных — блок пуст с подсказкой «Решения появятся, когда по гипотезам накопятся факты».

## 6. R4 · Экономная генерация (только актуальное сейчас)

Принцип релиза: сначала измерить, потом убрать очевидные потери. Решения, требующие накопленных данных (few-shot, обучение доноров, A/B), — в §12.

### 6.1. Учёт токенов
Таблица `search_map_generation_run` (миграция `0125_search_map_generation_run.sql`): `id, organization_id, map_id, job_id, user_id, scope, part ('sections'|'donors'|'segments'|'summary'|'decisions'|'profile'), provider, model, prompt_tokens, completion_tokens, cached_tokens (nullable), duration_ms, status ('ok'|'error'|'timeout'), error_message, items_proposed, created_at`. Пишется из `generate.post.ts` на каждую часть (`generateStructuredOutput` уже возвращает usage — проверить и при необходимости расширить возврат). Стоимость считается на чтении по `ai_config.inputPricePer1m/outputPricePer1m`.

UI: в `SearchMapStatsPanel` строка «Генерация: N запусков · ~X ₽ · последняя Y сек» и в настройках организации → Карта поиска → вкладка «Расход» с таблицей по вакансиям за 30 дней. Этого достаточно, чтобы «реальные траты посмотреть по факту».

### 6.2. Маршрутизация моделей
- `sections`, `summary`, `profile` (§6.4), `decisions` → `ai_config` с назначением **`structuring`**.
- `donors`, `segments` → **`analysis`**.
- Если для организации не задан `structuring` — fallback на `analysis` (как сейчас), с предупреждением в UI настроек «Назначьте дешёвую модель для структурирования — карта поиска будет дешевле».
- В настройках ИИ у моделей семейства reasoning (`o3`, `o4-mini` и аналоги по `ModelInfo`) показывать пометку «не рекомендуется для карты поиска»; жёсткого запрета нет.

### 6.3. Строки запросов — кодом
`buildQueryString(segment, channel)` в `shared/searchMap/queryBuilder.ts` (уже есть прототип «Собрать» в drawer — переносится в shared и становится единственным путём):
- Берёт `titles`, `keywords`, `geo`, исключения из секции `exclusions`.
- Шаблон по `sourcing_channel.queryLanguageHint`: `boolean` (hh, LinkedIn) → `("t1" OR "t2") AND ("k1" OR "k2") NOT ("e1")`; `xray` → `site:{targetSite} ("t1" OR "t2") ("k1") "geo"`; `plain` (Telegram, рефералы) → ключевые слова через пробел.
- Генерация **перестаёт просить у модели `queryString`**: в схеме `segments` остаются только `name, donorLayer, titles, keywords, geo, channelCode, priority, estimates, rationale`; строка собирается после нормализации. Это убирает самую длинную и самую ошибочную часть ответа.
- Рекрутёр может переписать строку руками (как сейчас); флаг `queryStringManual` не вводим — достаточно того, что «Собрать» перезаписывает по явному клику.

### 6.4. Компактный профиль вакансии с кэшем
- `buildJobProfile(jobId)`: один вызов `structuring` превращает бриф + критерии + описание в JSON ≤ 400 токенов: `{ roleFamily, seniority, mustHave[], niceToHave[], dealBreakers[], geoMode, compensationHint, teamContext, sourcingHints[] }`.
- Хранится в `job_search_map.job_profile jsonb` + `job_profile_hashes jsonb` (те же хэши источников, что для stale; добавить колонки в миграцию §6.1). Пересчитывается только при изменении хэшей.
- Все части генерации получают **профиль вместо сырого брифа**; сырой текст описания в промпт больше не идёт. Ожидаемое сокращение входа — в 3–5 раз на часть, итог на «full» — кратно, точную цифру покажет §6.1.
- Порядок промпта: системные инструкции → словарь каналов организации → профиль → задача части. Стабильная часть впереди — чтобы работал кэш префикса у провайдеров, которые его поддерживают; специально ничего не настраиваем.

### 6.5. Частичная регенерация по изменившимся источникам
Маппинг в `server/utils/searchMap/staleImpact.ts`: `brief → sections + segments + summary`, `criteria → sections(keywords, exclusions) + summary`, `description → sections(title_synonyms) + summary`. Баннер stale получает кнопку **«Обновить затронутое»**, которая вызывает `generate` с вычисленным набором частей и `mode: 'append'`; доноры при stale не регенерируются (они накапливаются, а не пересобираются).

### 6.6. Ограничители
- Не более 10 запусков генерации на карту в сутки (409 с понятным текстом); «Обновить вердикт» — не более 1 в 10 минут.
- Таймаут одной части 120 с (вместо 300): с профилем и без строк запросов этого достаточно; при таймауте — предупреждение и возможность повторить только эту часть.

### 6.7. Приёмка R4
- После каждой генерации в `search_map_generation_run` есть строки по частям с токенами; панель показывает расход.
- Для организации с назначенным `structuring` секции и вердикт генерируются этой моделью (видно в `model` записи).
- Ответ модели для `segments` не содержит `queryString`; строка собрана по шаблону канала и совпадает с результатом кнопки «Собрать».
- Повторная генерация без изменения брифа не пересчитывает профиль (нет записи `part = 'profile'`).
- Кнопка «Обновить затронутое» регенерирует только части из маппинга.

## 10. Тестирование

- Unit: `buildBriefContext` (полный и пустой бриф, jsonb-массивы строк и объектов); обрезка описания 4000+2000 и `stripHtml`; семантический дедуп гипотез; `computeSegmentMetrics` (фикстуры с поисками, кандидатами, заявками, этапами); `suggestStatus` (все ветки §4.4); `detectDecisionCandidates`; `buildQueryString` для трёх `queryLanguageHint`; `staleImpact`; нормализация ответа `segments` без `queryString`.
- Интеграционные: `GET search-map` с метриками; `PATCH decision → accepted` создаёт версию `calibration`; лимиты генерации (409); запись `search_map_generation_run` на ошибке и таймауте.
- Ручной сценарий приёмки (сквозной): заполнить бриф с `sourcingHints` → создать карту → дополнить по брифу (гипотезы отражают подсказки) → «Предложить гипотезы» с подсказкой → «Ещё похожие» из drawer → документ-вид совпадает с PDF → привязать hh-поиск, запустить → факты появились → подсказка «запустить/отклонить» → принять → ИИ предложил решение → HM выбрал вариант → версия `calibration` → «Обновить затронутое» после правки брифа → расход виден в панели.
