# ТЗ — Публикация вакансий из системы на hh.ru

> **Статус:** проект ТЗ на обсуждение (v1, 19.08.2026).
> Связано: `docs/funnel-architecture.md`, `docs/idea-hh-stage-distribution-import.md`,
> существующий hh-контур (`server/utils/hh/*`, `hhAccount`, `hhVacancyLink`).

## 0. Цель и ценность

Рекрутёр создаёт вакансию в системе и публикует её на hh.ru **не покидая систему**.
После публикации существующий синк переговоров автоматически подтягивает отклики —
вакансия сразу живёт в нашей воронке. Система становится первичным рабочим местом,
hh.ru — каналом привлечения.

**Ключевая связка:** публикация → авто-создание `hhVacancyLink` → штатный синк откликов.
Ничего нового для приёма откликов писать не нужно — контур уже есть.

## 1. Главное архитектурное решение: карточку НЕ перестраиваем

**Наша карточка вакансии остаётся канонической и не ломается.** Публикация на hh — это
**проекция + hh-паспорт**, а не замена модели:

```
job (каноническая карточка)          job_hh_publication (hh-паспорт)
  title            ──────────────►    name (≤100)
  description      ──автоген──►       description (HTML, 150–10000)
  salary*          ──────────────►    salary_range
  remoteStatus     ──маппинг──►       work_format[]
  location         ──резолв──►        area {id} (справочник /areas)
                                      professional_roles [ровно 1] (hh-специфично)
                                      experience {id}                (hh-специфично)
                                      employment_form {id}           (hh-специфично)
                                      key_skills[] ≤30               (hh-специфично)
                                      contacts {name, phones[]}      (hh-специфично)
                                      address, test, branded_template, … (опционально)
```

Почему так:

1. **Скрининг и ассистент не страдают** (см. раздел 7) — они читают канонические
   `job.title` + `job.description`, которые никуда не деваются.
2. Карьерный сайт, SEO (`JobPosting` schema.org), публичные страницы — всё работает как раньше.
3. hh-поля нужны только вакансиям, которые публикуются на hh; остальные не захламляются.
4. Один канонический словарь, hh-пейлоад — адаптер (симметрично решению «словарь = воронка»).

UI карточки вакансии получает **новый блок/вкладку «Публикация на hh.ru»**, а не редизайн.

## 2. Требования API hh.ru (сверено с api.hh.ru, август 2026)

### 2.1 Обязательные поля POST /vacancies

| Поле | Ограничения | Откуда берём |
| --- | --- | --- |
| `name` | 1–100 символов | `job.title` (обрезка/валидация) |
| `description` | HTML, **150–10 000** символов, без дискриминационных формулировок (закон 1032-1) | из `job.description` (конвертация md/plain → HTML) |
| `area` | объект `{id}` из справочника `/areas` | резолв из `job.location` + ручной выбор |
| `professional_roles` | **ровно 1** элемент, справочник `/professional_roles` | выбор в форме (+ AI-подсказка) |
| `billing_type` → `vacancy_properties` | `billing_type` deprecated; актуально `vacancy_properties.properties[]` (например `HH_STANDARD`) | из выбранного варианта публикации |
| `type` | deprecated: `open/closed` → `closed_for_applicants`, `anonymous/direct` → `vacancy_properties` | по умолчанию открытая |

### 2.2 Важные опциональные поля

- `salary_range` (актуальная замена deprecated `salary`): `currency` + `gross` + `mode`
  обязательны внутри объекта; `frequency`, `from`, `to` — опционально.
- `experience {id}`: noExperience / between1And3 / between3And6 / moreThan6.
- `employment_form {id}` (замена deprecated `employment`), `work_format[]`
  (ON_SITE / REMOTE / HYBRID / FIELD_WORK), `work_schedule_by_days[]`, `working_hours[]`
  (замена deprecated `schedule`).
- `key_skills[]` ≤30, `languages[]`, `address {id}` (адрес из справочника работодателя),
  `contacts` (если передаётся — `phones[]` обязателен, 7–21 символ номер),
  `response_letter_required`, `accept_incomplete_resumes`, `allow_messages`,
  `auto_response`, `test {id, required}`, `branded_template {id}`, `code` (внутренний код),
  `manager {id}` (от чьего имени публикуем), `previous_id` (восстановление из архива).
- `fly_in_fly_out_duration` — hh анонсировал, что поле станет обязательным; заложить в маппер.

### 2.3 Черновики `/vacancy_drafts` — наш основной путь

Черновик принимает те же поля и возвращает:
`publication_ready`, `validation_errors[] {reason: too_short/too_long/…, value: поле}`,
`ignored_fields[]`, `completed_fields_percentage`, проверку дубликатов
(`{found, has_duplicates, items[]}`), `insufficient_publications` / `insufficient_quotas` /
`required_publications`.

**Решение:** публикуем всегда через черновик: создать → провалидировать → показать ошибки
и дубликаты → опубликовать. Это бесплатно и снимает 90% ошибок до списания публикации.

### 2.4 Типы публикаций, квоты, деньги

- Варианты публикации: метод по `employer_id` (+ `area_id`, `professional_role_id`) →
  `publication_variants[]` с `available_publications_count` и `suitable_packages[]`
  (пакеты по регионам, признак `invalid`).
- Права менеджера: метод по `employer_id` + `manager_id` → какие типы публикаций доступны
  этому менеджеру и сколько осталось (`vacancy_billing_type`: free / standard /
  standard_plus / premium; `vacancy_types`: open / closed).
- **Публикация списывает оплаченную публикацию из пакета работодателя.** Это денежная
  операция → обязательный confirm-шаг с явным указанием типа и остатка.

### 2.5 Жизненный цикл после публикации

- Ответ создания: `{id}` — hh vacancy id.
- Модерация: вакансия может быть `approved=false` до премодерации; непремодерированную
  нельзя продлить (`vacancy_not_premoderated`).
- Редактирование `PUT /vacancies/{id}`: составные поля (`salary_range`, `contacts`,
  `professional_roles`) — **только целиком**; `billing_type`/`manager` — отдельными запросами;
  `ignore_replacement_warning=true` при значительном изменении → **риск блокировки** (не форсим).
- Продление: стоит как новая публикация; причины отказа — `not_enough_quotas` и др.
- Архивирование: метод по `employer_id`+`vacancy_id`; восстановление — новая публикация
  с `previous_id` архивной.

## 3. Модель данных

### 3.1 Новая таблица `job_hh_publication`

```
id, organizationId, jobId (уникально: одна активная публикация на вакансию)
hhAccountId              — от чьего аккаунта публикуем (токены, managerId)
status                   — enum: draft | validating | ready | publishing |
                           moderation | published | edit_pending | archived | failed
hhDraftId                — id черновика на hh
hhVacancyId              — id вакансии на hh (после публикации)
hhVacancyUrl
publicationType          — free | standard | standard_plus | premium
payloadJson              — последний отправленный hh-пейлоад (снапшот-проекция)
validationErrorsJson     — ошибки последней валидации черновика
duplicatesJson           — результат проверки дубликатов
areaId, professionalRoleId — денормализация для выборок
publishedAt, expiresAt   — срок размещения (для напоминаний о продлении)
lastError, lastSyncedAt, createdAt, updatedAt
```

hh-паспорт (area, professional_role, experience, employment_form, work_format, key_skills,
contacts, address и пр.) храним в `payloadJson` + редактируемой форме — отдельные колонки
не плодим, кроме денормализованных для выборок.

### 3.2 Связь с существующим контуром

- После успешной публикации **автоматически создаём `hhVacancyLink`**
  (jobId ↔ hhVacancyId) — штатный синк переговоров начинает работать без доработок.
- `hhAccount` уже хранит `hhEmployerId`/`hhManagerId` и шифрованные токены — переиспользуем.
- Проверить scope OAuth-приложения hh: нужны права на публикацию вакансий
  (employer-методы). Если текущего scope не хватает — реконнект аккаунта с новым scope.

### 3.3 Кэш справочников hh

Новая таблица `hh_dictionary_cache (kind, dataJson, fetchedAt)`:
`/areas` (дерево регионов), `/professional_roles`, `/dictionaries`
(experience, employment_form, work_format, currency, …), адреса работодателя,
брендированные шаблоны. TTL ~24 ч, ленивое обновление. Без кэша каждая форма публикации
будет дёргать тяжёлые справочники hh.

## 4. Бэкенд API

| Эндпоинт | Назначение |
| --- | --- |
| `GET  /api/hh/dictionaries?kind=` | справочники из кэша (areas, roles, dictionaries, addresses, templates) |
| `GET  /api/jobs/:id/hh-publication` | текущее состояние публикации |
| `POST /api/jobs/:id/hh-publication/draft` | собрать проекцию карточки → создать/обновить черновик на hh → вернуть валидацию + дубликаты |
| `GET  /api/jobs/:id/hh-publication/variants` | доступные типы публикаций (по area + role + manager limits) с остатками |
| `POST /api/jobs/:id/hh-publication/publish` | опубликовать черновик выбранным типом; создать `hhVacancyLink`; статус → moderation/published |
| `PUT  /api/jobs/:id/hh-publication` | редактирование опубликованной (diff → PUT /vacancies/{id}, составные поля целиком) |
| `POST /api/jobs/:id/hh-publication/archive` | архивировать на hh |
| `POST /api/jobs/:id/hh-publication/prolongate` | продлить (после confirm — тоже денежная операция) |

Правила:

- Все вызовы hh — через существующий `server/utils/hh/client.ts` (refresh-токены, ретраи,
  обработка 403 limit).
- Маппер `jobToHhPayload(job, hhPassport)` — единственная точка проекции; юнит-тестируемый.
- Конвертация описания: канонический `job.description` (markdown/plain) → валидный hh-HTML;
  при заполненных секциях обязанности/требования — структурированный HTML
  (см. `docs/adr-job-description-sections.md`)
  (белый список тегов hh: p, ul/ol/li, strong, em, br и т.п.), проверка длины 150–10 000.
- Идемпотентность: повторный `draft` обновляет существующий черновик, не плодит новые.

## 5. UI

### 5.1 Блок «hh.ru» на странице вакансии

Состояния: не опубликована → черновик (с % готовности и ошибками) → на модерации →
опубликована (ссылка, тип, срок, остаток дней) → архив / ошибка.

### 5.2 Мастер публикации (3 шага)

1. **Данные** — форма hh-паспорта. Автозаполнение из карточки (name, description-превью,
   salary_range, work_format из remoteStatus, area из location). hh-специфичные поля:
   регион (автокомплит по дереву /areas), профроль (поиск по справочнику), опыт, занятость,
   ключевые навыки (чипы, ≤30), контакты, адрес. Подсказки AI (раздел 7.3) — опционально.
2. **Проверка** — создаём черновик на hh, показываем `validation_errors` по-русски,
   предупреждение о дубликатах (`has_duplicates` + ссылки), дискриминационные формулировки
   (наша превалидация: пол/возраст/семейное положение — закон 1032-1).
3. **Тип публикации и подтверждение** — варианты с описанием и остатками
   (`available_publications_count`), выбор менеджера (если аккаунтов несколько).
   Явный confirm: «Будет списана 1 публикация „Стандарт“ (осталось 9)».

### 5.3 Правки и жизненный цикл

- Кнопка «Обновить на hh» при расхождении карточки и `payloadJson` (показываем diff).
  Предупреждение hh о значительном изменении показываем как есть — не форсим
  `ignore_replacement_warning`.
- Напоминание о сроке размещения (`expiresAt`), кнопка продления с confirm.
- Закрытие вакансии в системе → предложение заархивировать на hh (не автоматически).

## 6. RBAC и безопасность

- Публикация/продление/архив — только роли с правом управления вакансиями (admin/recruiter);
  НМ — read-only статус.
- Денежные операции (publish, prolongate) — только через confirm-шаг, в activity log
  пишем кто/когда/каким типом опубликовал.
- Токены hh — существующий шифрованный контур `hhAccount`; новых секретов нет.
- Rate limits hh — существующие ретраи клиента; справочники только из кэша.

## 7. Скрининг и ассистент — что меняется

### 7.1 Скрининг: НИЧЕГО не меняется (по решению)

Скрининговый контур (Qwen/Yandex, `scoring.ts`, `autoScore.ts`, `autoReject.ts`)
читает `jobTitle` + `jobDescription` — **канонические поля, которые остаются источником
истины**. Публикация на hh — проекция «наружу», она не трогает вход скрининга.
Отклики с опубликованной вакансии приходят штатным синком и скринятся как обычно.

Единственное требование к качеству: канонический `description` должен оставаться
полноценным (не «см. hh»). Правило: **редактируем описание всегда в карточке**,
на hh уходит проекция — не наоборот.

### 7.2 Ассистент

Аналогично — ассистент (`chatTools.ts`) работает с каноническими сущностями и не требует
изменений. Опционально (отдельным решением, не в этом ТЗ): дать ассистенту read-only
инструмент «статус публикации на hh» (опубликована/модерация/срок/остаток публикаций).

### 7.3 AI-помощь в форме публикации (опционально, Фаза D)

Новые изолированные AI-фичи поверх существующего провайдера (скрининговые промпты
не трогаем):

- генерация hh-описания из канонической карточки (HTML, 150–10 000, без дискриминации);
- подсказка professional_role и key_skills по названию и описанию;
- превалидация дискриминационных формулировок до отправки на hh.

### 7.4 Бонус для скрининга (Фаза 2+, отдельным решением)

Структурированные поля hh-паспорта (key_skills, experience) — потенциальное обогащение
контекста скрининга. **Не делаем сейчас**: скрининговый контур заморожен.

## 8. Фазы реализации

| Фаза | Объём | Результат |
| --- | --- | --- |
| **A. Фундамент** | scope-аудит OAuth, кэш справочников, маппер `jobToHhPayload`, таблица `job_hh_publication`, черновик + валидация + дубликаты | Черновик на hh из карточки, ошибки видны в UI |
| **B. Публикация** | варианты публикаций и лимиты менеджера, мастер (3 шага), publish + авто-`hhVacancyLink`, статусы модерации | Вакансия публикуется из системы, отклики текут в воронку |
| **C. Жизненный цикл** | редактирование (diff, составные поля целиком), продление, архив/восстановление (`previous_id`), напоминания о сроке | Полное управление без захода на hh |
| **D. AI-помощь** | генерация описания, подбор роли/навыков, антидискриминационная превалидация; предпосылка — секции описания (`docs/adr-job-description-sections.md`) | Публикация «в один клик» из карточки |

Фазы A и B — MVP. C и D — по результатам эксплуатации.

## 9. Риски

| Риск | Митигация |
| --- | --- |
| Не хватает OAuth scope на публикацию | Проверка в Фазе A на реальном аккаунте; реконнект с расширенным scope |
| Публикация — платная, ошибка = потерянные деньги | Draft-first валидация; confirm с типом и остатком; никаких авто-публикаций |
| Модерация hh отклонит вакансию | Статус moderation в UI; наша превалидация формулировок |
| `ignore_replacement_warning` → блокировка вакансии | Не форсим; показываем предупреждение hh пользователю |
| Дубликаты (вакансия уже размещена вручную) | Проверка дубликатов черновика; предложить привязку к существующей вместо публикации |
| Рассинхронизация: правки напрямую на hh | `lastSyncedAt` + периодическое сравнение с GET /vacancies/{id}, индикатор расхождения (паттерн A3) |
| hh эволюционирует API (deprecated-поля) | Используем только актуальные поля (`salary_range`, `employment_form`, `work_format`, `vacancy_properties`); `fly_in_fly_out_duration` заложен в маппер |
