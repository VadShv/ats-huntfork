# RBAC v2 — Глоссарий ролей (источник правды по названиям)

> Зачем: в системе слово «рекрутер» встречается в РАЗНЫХ смыслах, а ключ
> org-роли «Рекрутер» технически называется `member` (наследие Better Auth).
> Этот документ фиксирует, что есть что, чтобы не путать в коде и в разговорах.
> Сверено с фактической БД (ВМ). Названия в БД НЕ меняем (см. §«Почему так»).

---

## ⚠️ Две РАЗНЫЕ оси ролей — не путать

| | **Org-роль** (права) | **Job-роль** (привязка к вакансии) |
|---|---|---|
| Отвечает на вопрос | ЧТО человек может в организации | ГДЕ (на каких вакансиях) он работает и в каком качестве |
| Таблица / колонка | `member.role` | `job_member.member_role` |
| Сколько на человека | одна на всю орг | много (по одной на каждую назначенную вакансию) |
| Значения | owner / admin / lead_recruiter / hrbp / member / external_recruiter / hiring_manager | recruiter / hiring_manager (+резерв watcher/assignee) |

Один человек имеет **одну** org-роль (права), но может быть привязан к **разным**
вакансиям с **разными** job-ролями. Пример: у Ивана `member.role='lead_recruiter'`
(права), при этом на вакансии A он `job_member(recruiter)`, а на вакансии C —
`job_member(hiring_manager)`.

## 1. Org-роли (права) — таблица `role` / `member.role`

| Ключ в БД (`key`) | Название в UI (`name`) | Смысл |
|---|---|---|
| `owner` | Владелец | Полный доступ + биллинг. Ключ Better Auth. |
| `admin` | Администратор | Полный доступ к настройкам/ролям. Ключ Better Auth. |
| `lead_recruiter` | Ведущий рекрутер | Рекрутер + продвинутые функции (песочница воронки, промпты, суфлёр); scope по умолчанию — вся орг. |
| `hrbp` | HR бизнес-партнёр | Scope по назначенным компаниям/департаментам (org_scope_assignment). |
| **`member`** | **Рекрутер** | ⭐ Основная роль рекрутера. Ключ `member` — наследие Better Auth (НЕ переименовывать). scope по умолчанию — вся орг. |
| `external_recruiter` | Внешний рекрутер | Агентства/подрядчики: минимум прав, БЕЗ ИИ и PII, scope `assigned`. |
| `hiring_manager` | Нанимающий менеджер | Только чтение; решения через отдельный кабинет `/hm/*`. |

> **Главное:** `member` **и есть** «Рекрутер». `member` — это техническое имя ключа,
> «Рекрутер» — то, что видит пользователь. Это одно и то же.

**Ретайренные (soft-retire, невидимы пользователям, назначить нельзя):**
| Ключ | Что было |
|---|---|
| `recruiter_deprecated` | бывший org-пресет-синоним `recruiter` → схлопнут в `member` (Спринт E) |
| `junior_recruiter_deprecated` | бывший «Младший рекрутер» → заменён на `external_recruiter` (§8) |

## 2. Job-роли (привязка к вакансии) — `job_member.member_role`

| Значение в БД | Смысл |
|---|---|
| **`recruiter`** | рекрутер, назначенный на ЭТУ вакансию |
| `hiring_manager` | НМ, назначенный на ЭТУ вакансию |
| `watcher`, `assignee` | зарезервированы (в коде помечены, пока не используются) |

### Основной vs дополнительный рекрутер вакансии
Различие — НЕ по названию роли (у всех `member_role='recruiter'`), а по флагу
**`job_member.is_primary`**:
- `is_primary = true` → **Основной** рекрутер вакансии (в UI бейдж «★ Основной»).
  На вакансию — только один основной (partial unique `uq_job_member_primary_recruiter`).
  По нему считается статистика «вакансий в работе».
- `is_primary = false` → **дополнительный** рекрутер («просто рекрутер»).
- Сменить основного: `PATCH /api/jobs/[id]/members/[userId]/primary`.

## 3. Коллизия слова «recruiter» — как не перепутать в коде

Слово `recruiter` встречается в двух смыслах:
- **org**: «Рекрутер» = ключ `member` (НЕ строка `'recruiter'`!).
- **job**: `job_member.member_role === 'recruiter'` (привязка к вакансии).

⚠️ Правило для кода/агентов:
- Проверяешь **права/org-роль** → сравнивай с `'member'` (это «Рекрутер»),
  `'lead_recruiter'`, и т.д. Строки `'recruiter'` в org-контексте НЕТ.
- Проверяешь **привязку к вакансии** → это `job_member.member_role === 'recruiter'`.
- Право писать в чат (§G2) = `lead_recruiter` (org) И `job_member(recruiter)` (job)
  на вакансии диалога — это как раз пересечение ДВУХ осей.

Исторический баг этого класса: `comments/visibility.ts` использовал несуществующую
org-роль `'recruiter'` вместо `'member'` → рекрутер не видел внутренние комментарии
(исправлено в Спринте 3).

## Почему НЕ переименовываем `member` в БД

`member` / `owner` / `admin` — встроенные ключи **Better Auth organization plugin**
(автопровижн владельца, инвайты, смена ролей через `authClient.organization.*`,
дефолтные statements, сессии). Переименование `member` → что-либо сломает Better
Auth (приглашения/вход) при чисто косметическом выигрыше (пользователь и так видит
«Рекрутер»). Поэтому имена в БД оставлены как есть; ясность обеспечивает этот
глоссарий. Кастомные ключи (`lead_recruiter`, `hrbp`, …) технически переименовать
можно, но без унификации с неизменяемым `member` смысла мало.

Опционально в будущем (не сейчас): ввести константы `ORG_ROLE.RECRUITER='member'` /
`JOB_ROLE.RECRUITER='recruiter'` в коде, чтобы сравнения были самодокументируемыми.
